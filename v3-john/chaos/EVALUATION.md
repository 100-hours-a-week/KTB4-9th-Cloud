# 실험 평가: 무엇을 증명했고 무엇을 증명하지 못했나

`REPORT.md`의 비교표는 실험에서 측정한 값 그대로다. 이 문서는 그 값이 "개선이 효과가 있었다"를 얼마나 뒷받침하는지 비판적으로 다시 본다. 2026-11-24 작성.

## 1. S1은 제대로 된 실험이었나

**결론: 단계 1·2는 의미가 있었지만, 단계 3·4의 "사용자 영향 0"은 이중화나 카나리의 효과를 증명하지 못한다.** 개선 전과 같은 결함을 다시 넣은 것이 아니라, 개선 때문에 결함의 모양이 바뀌었기 때문이다.

### 1.1 단계 3을 살린 것은 레플리카 2가 아니었다

| 조건 | 새 파드(448Mi)의 운명 | 옛 파드 | 사용자 영향 |
|---|---|---|---|
| 개선 전(레플리카 1, 힙 25%) | 준비 상태 검사 통과 → 옛 파드 교체 → 부하에서 OOMKilled | 교체되어 없음 | 핵심 5xx 163, 유실 6 |
| 단계 3(레플리카 2, 힙 75%) | **기동 중 OOMKilled**, 준비 한 번도 못 함 | 롤링 업데이트가 남겨 둠 | 0 |

- 롤링 설정 `maxUnavailable: 0, maxSurge: 1`은 개선 전부터 차트 기본값이었다(2026-11-05 차트 생성 때부터). 새 파드가 준비되지 못하면 옛 파드를 내리지 않는 것은 레플리카 수와 상관없다
- 따라서 **레플리카 1에 힙 75%만 바꿨어도 결과는 같았을 가능성이 크다.** 단계 3의 효과는 "힙 비율이 결함을 기동 시점으로 앞당겼고, 원래 있던 롤링 설정이 그 결함을 막았다"에 가깝다
- 단계 3은 레플리카 2, PDB, 노드 분산, 힙 비율을 한 번에 넣었다. 무엇이 효과를 냈는지 나눌 수 없다

### 1.2 같은 결함을 다시 넣지 않았다

- 주입값 448Mi는 개선 전 구성(힙 25%)에서 "준비 검사는 통과하고 부하에서 죽는" 값으로 골랐다(`scenarios/s1/README.md`)
- 힙 75% 구성에서 이 값은 "기동조차 못 하는" 결함이 된다. 이런 결함은 어떤 준비 상태 검사로도 막힌다. 실험 도구도 이 차이 때문에 두 번 중단됐고, 결국 `S1_REQUIRE_READY=0`으로 판정 기준을 바꿨다
- 개선을 시험하려면 **새 구성에서도 "준비 검사는 통과하고 부하에서 죽는" 값을 다시 찾아야 했다.** 힙 75%라면 대략 한도 700~900Mi 근처일 것으로 보이지만 찾지 않았다
- 그 결함이 들어오면 레플리카 2는 이렇게 될 것이다: 새 파드 A가 준비 → 옛 파드 1 종료 → 새 파드 B가 준비 → 옛 파드 2 종료 → 부하에서 A, B가 차례로 죽는다. 레플리카 2는 두 파드가 같은 시각에 죽지 않는 동안만 시간을 번다. 이것이 S1 단계 3이 실제로 답해야 했던 질문이다

### 1.3 단계 4(카나리)도 같은 이유로 쉬운 문제를 풀었다

- 카나리 파드는 기동 중 죽어 트래픽을 한 건도 받지 않았다. 분석의 "재시작 0" 조건이 첫 재시작을 잡아 93초에 중단했다
- 카나리의 핵심인 "트래픽 일부에서 오류율이 오르면 중단"은 시험되지 않았다. 게다가 트래픽이 없을 때 정상 배포가 막히는 문제를 고치느라 오류율 조건을 `max(... >= 0) or vector(0)`으로 바꿔, 트래픽이 적을 때는 오류율 조건이 사실상 항상 통과한다
- 레플리카 2에서 `setWeight: 50`은 카나리 파드 1개를 뜻한다. 트래픽 분할 없이 파드 수로만 나누므로, 카나리 파드가 준비되는 순간 사용자 요청의 절반이 바로 간다

### 1.4 단계 1·2는 무엇을 보여 줬나

- 단계 1(`PodCrashLooping`)은 정확히 측정했다. 원인 알림이 증상 알림보다 45초 늦었다. 이것은 반증 결과로서 의미가 있다
- 단계 2(트레이싱)는 "메모리로 죽는 장애는 트레이스에 남지 않는다"를 보였다. 다만 에이전트가 메모리를 더 써서 같은 448Mi가 더 심한 장애가 되었고(5xx 938), 개선 전과 수치를 직접 비교할 수 없다

### 1.5 S1 전체에 걸린 한계

- **회차가 1회씩이다.** 같은 조건의 448Mi 탐색 3회에서 첫 알림이 240·360·255초로 흩어졌다. 단계 사이 탐지 시간 차이(240 → 360초)는 이 흩어짐 안에 있다
- **증상 알림이 합성 부하 지표다.** 모든 단계의 첫 증상 알림 `JudgeJobLost`는 k6가 만든 지표다. 실제 운영에는 없다. 실제 사용자 지표 기반 알림(`CoreErrorBudgetBurnFast`, `CoreUnavailable`)은 S1에서 한 번도 울리지 않았다
- **대응자가 원인을 알았다.** 완화 시간은 대응 절차가 아니라 실험 설계자의 반응 속도다

## 2. 모든 실험에 걸친 방법 문제

| 문제 | 어디서 드러났나 | 영향 | 개선 |
|---|---|---|---|
| 단계마다 여러 변경을 한 번에 | S1 단계 3(4가지), S3a 단계 2(Hikari와 대시보드) | 효과를 나눌 수 없음 | 단계당 변경 하나. 묶을 때는 하나씩 빼는 실험을 추가 |
| 결함을 구성에 맞춰 다시 고르지 않음 | S1 단계 2·3·4 | 개선이 결함을 바꿔 버림 | 단계마다 "같은 증상을 내는 결함"을 다시 찾는 탐색 단계 |
| 회차 1회 | 거의 모든 단계 | 흩어짐보다 작은 차이를 효과로 읽음 | 단계당 3회, 중앙값과 범위로 비교 |
| 닫힌 부하 모델(k6 constant-vus) | S3a | 요청이 묶이면 요청 수가 줄어 실패율이 작게 나옴 | `constant-arrival-rate`(열린 모델)로 초당 요청 수 고정 |
| 합성 지표 기반 증상 알림 | S1, S2, S3a | 운영에서 같은 탐지를 기대할 수 없음 | 실제 요청(Envoy downstream) 기반 SLI 알림을 1순위로 두고 k6 알림은 보조 |
| SLI 사각지대 | S3a(엔드포인트 0개, none_healthy 0) | 장애를 작게 보고 늦게 탐지 | downstream 5xx·시간 초과를 SLI에 포함 |
| 대응자가 원인을 앎 | 전부 | 탐지·완화 시간이 실제보다 짧음 | 주입 내용을 모르는 사람이 대응하는 회차(팀원) |
| 배치를 통제하지 않음 | S2 전 단계 | "그 노드에 무엇이 있었나"가 결과를 정함 | 실험 전 배치를 기록하고 같은 배치로 맞춘 뒤 비교, 또는 여러 노드로 반복 |
| 실험 도구를 실험 중에 고침 | S1 단계 3, S3a | 단계 사이 판정 기준이 달라짐 | 도구 변경 뒤 개선 전 실험을 한 번 다시 돌려 기준선 확인 |
| 측정 수단과 대상이 같은 노드 | S2 개선 전, 실제 스팟 회수 | 모니터링이 함께 사라짐 | 모니터링을 별도 노드 그룹(온디맨드)에 |

## 3. 실험별 한계와 개선점

### S1 잘못된 배포

| 실험 | 증명한 것 | 증명하지 못한 것 | 다시 한다면 |
|---|---|---|---|
| 값 탐색(640·512·448Mi) | JVM 기본 힙 25%가 메모리 축소를 숨긴다 | 512Mi는 396초 만에 vCPU 중단 조건으로 멈춰 충분히 보지 못했다 | 512Mi를 다시 10분, 3회 |
| 개선 전 | 레플리카 1 + 동기 채점이 배포 결함을 채점 유실로 키운다 | - | 3회 반복해 기준선 범위를 만든다 |

| 단계 2 | 메모리 장애는 트레이스에 남지 않는다 | 트레이스가 원인 파악을 빠르게 하는 장애 유형 | 지연형 결함(예: 특정 쿼리에 인덱스 제거, 외부 호출 지연)을 주입해 원인을 모르는 대응자가 트레이스로 찾는 시간 비교. 에이전트 메모리만큼 한도를 올린 구성에서 비교 |

| 단계 5 | 같은 PR을 CI가 실패시킨다 | 병합을 막지 않는다(필수 검사 아님) | main 필수 검사 지정 뒤 같은 PR로 다시 확인. 힙 밖 256Mi 기준은 추정값이라 실제 기동 실패 경계를 값 탐색으로 확인 |

## 4. 다시 한다면 우선순위

1. **S1 재설계**: 힙 75% 구성에서 "준비 통과 + 부하에서 OOM" 값을 찾고, 레플리카 1·2, 힙 25%·75%를 나눠 4개 조건으로 3회씩. 이것이 S1 단계 3의 진짜 질문이다
2. **카나리 오류율 경로 시험**: 준비는 통과하고 일부 요청만 실패하는 결함으로 단계 4를 다시
3. **열린 부하 모델과 실제 요청 SLI**: k6 `constant-arrival-rate`, downstream 지표 기반 알림. 이후 모든 실험의 수치를 이 기준으로 다시
4. **S2 배치 통제**: 모니터링 별도 노드, judge-api 이중화 뒤 같은 배치로 반복
5. **원인을 모르는 대응자**: 팀원이 대응하는 회차를 시나리오마다 하나씩
