# S1' 요약: 채점 장애가 core 연결 풀을 통해 핵심 경로로 번지는 연쇄

2026-11-24. 주입은 부하(RATE 30) 중 채점 워커 5분 중단(KEDA 일시 정지)이다. 단계는 누적이고 각 3회다. 설계는 `docs/superpowers/specs/2026-11-24-v3-john-fault-injection-round2-design.md` 6.1(재설계본)이다.

## 출발점

- 2026-11-24 03:30 기준선 측정 중 실제 스팟 회수로 채점 노드가 사라졌다. 문제 조회 5xx 최대 23/s, 핵심 1분 오류율 최대 30%였다(`round2-baseline.md` 4절)
- 처음 설계(core 풀 확대 PR → 공유 RDS 고갈 → auth 배포 실패)는 보정 1회차와 사전 측정으로 성립하지 않음을 확인하고 버렸다(`s1p-calibration.md`, `s1p-pilot.md`)

- 문제 조회 + major-core 5xx는 회차마다 약 6천 또는 약 1.1만 두 무리로 갈렸다(개선 전 5,824 / 11,279 / 6,034, 단계 1 11,036 / 12,023 / 11,785). 단계 1의 증가는 이 흩어짐 범위 안이다
- 채점 유실(900~1,000)과 제출 5xx(약 1,000)는 모든 단계에서 그대로다. 채점 워커가 없으면 피할 수 없는 손실이다
- 핵심 SLO 유지율(0.57~0.62)은 단계마다 거의 같다. 핵심 묶음에 제출 경로가 들어 있어 제출 오류만으로 1분 창 기준을 넘기 때문이다. 이 연쇄의 효과는 영향 경로 수와 경로별 5xx로 본다
- DB 연결 합 최대는 단계 3에서 93~108로 늘었지만 RDS 예산 242(303의 80%) 안이다

## 판단과 배운 것

1. **증상 경로와 원인이 다르다**: 문제 조회가 터졌지만 원인은 채점이었다. 단계 1은 그 연결 고리(풀 고갈) 알림을 사람에게 보내 원인 쪽을 가리키게 했다
2. **게이트웨이 격벽은 제한 시간 정렬이 전제다**: 격벽(단계 2)은 한 번도 작동하지 않았다. Envoy 기본 경로 제한 15초가 백엔드 연결 점유(최대 30.4초)보다 짧아 게이트웨이 슬롯이 먼저 풀렸다. 제한 시간을 맞춘 2b에서도 넘침은 0이었고 감소의 기전은 확인하지 못했다. 효과가 증명되지 않은 개선은 "보험"으로만 남긴다
3. **작은 여유의 차이가 연쇄를 만든다**: 채점 중단 중 core가 실제로 쓴 연결은 파드당 11~13이었다. 풀 10은 수요를 겨우 밑돌았고 그 차이로 대기가 100건 넘게 쌓였다. 풀 40(측정 수요의 3배)으로 연쇄가 사라졌다
4. **키운 값은 예산으로 묶는다**: 풀을 키우면 공유 RDS 위험이 생긴다. CI 연결 예산 검사가 (HPA 최대 + 배포 추가 파드) x 풀 합계를 RDS 상한의 80% 안으로 묶는다. 처음 설계의 131은 이 검사에서 594로 막힌다

## 남은 것

- 촉발 제거(채점 워커 이중화·노드 분산)는 S2'와 백엔드 제안으로 넘긴다
- 근본 해법(제출이 채점 결과를 기다리는 동안 DB 연결을 놓는 구조, 비동기 조회)은 백엔드 담당 영역이라 보고서에 제안으로 적는다
- main 필수 검사 지정(연결 예산 CI)은 저장소 관리자 설정이다
