# S3a 개선 전 실험 예측 (실험 전 작성, 2026-11-23)

조건: auth, core, battle 레플리카 2·PDB·노드 분산(S1 단계 3)과 카나리가 이미 적용된 상태다. 준비 상태 검사는 `/actuator/health`(DB 포함), Hikari 연결 대기 기본 30초, 최대 풀 10. NetworkChaos로 세 서비스 → RDS(10.30.20.0/23) 5분 차단.

| 순서 | 예상 연쇄 | 예측 |
|---|---|---|
| 1 | Hikari 풀 고갈, 요청 스레드 묶임 | 일어남. 연결 대기 30초라 요청이 30초씩 걸린 뒤 실패한다. `DbConnectionPoolExhausted`는 대기 스레드가 생겨 울릴 것이다 |
| 2 | 준비 상태 검사 실패로 모든 파드가 서비스에서 빠짐 | 일어남. 헬스 검사의 DB 확인이 시간 초과로 DOWN이 되어 15초 안에 6개 파드 모두 빠진다 |
| 3 | DB가 필요 없는 요청까지 503 | 일어남. Envoy가 건강한 대상이 없다고 503을 돌려준다. 핵심·주요 기능이 함께 전면 불가 |
| 4 | AI 서비스 실패 | 확인 못 함(AI 부하 끔) |
| 5 | 차단이 풀려도 바로 회복되지 않음 | 작게 일어남. 헬스 검사 통과와 엔드포인트 복귀에 15~30초 |
| 6 | 회복 순간 재연결 몰림 | 작게 일어남 |

- 첫 증상 알림: `CoreErrorBudgetBurnFast` 또는 `CoreUnavailable`(전면 불가라 5분 평균도 넘는다), 2~4분
- 예상 등급: SEV1(핵심 기능 전면 불가)
- 대응: RDS 장애 확인(CloudWatch, 연결 시험) 뒤 할 수 있는 완화가 없다. 차단이 풀리기를 기다린다. 이것이 단계 1(준비 상태 검사에서 DB 제외)의 근거가 되는지 본다
