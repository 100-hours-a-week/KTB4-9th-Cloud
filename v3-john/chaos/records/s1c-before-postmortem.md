# INC-20261124-S1C 포스트모템: 채점 워커 중단이 core 연결 풀을 통해 핵심 경로로 번짐(S1' 개선 전 3회)

비난 없는 형식이다. 같은 주입(채점 워커 5분 중단, 부하 RATE 30)을 3회 반복했고 대표 회차는 2회차(12:32)다. 실제 근거는 2026-11-24 03:30 실제 스팟 회수(`round2-baseline.md` 4절)다.

## 시각(대표 회차 s1c-before-20261124-1232)

| 항목 | 시각(KST) |
|---|---|
| 발생(채점 워커 0) | 12:35:36 |
| 첫 알림(`JudgeJobLost`, 사람에게 감) | 12:36:06(+30초) |
| 원인 위치 알림(`DbConnectionAcquireFailed`) | 12:36:21(+45초), 개선 전 구성에서는 blackhole이라 사람에게 가지 않음 |
| 증상 알림(`ServiceErrorHigh`) | 12:38:51(+195초) |
| 완화(워커 복구) | 12:40:31(일시 정지 해제), 12:40:37 Ready |
| 종료(핵심 오류율 1분 창 회복) | 주입 후 390초 |

- 탐지 방법: 알림. 사람이 받은 첫 알림은 `JudgeJobLost`(채점 유실), 이어서 `ServiceErrorHigh`(경로 오류)
- 발생 지점: 채점 워커 → core 제출 경로 → core 연결 풀 → 문제 조회·major-core
- 복구 방법: 채점 워커 복구(실험에서는 주입 시간 종료 후 원복)

영향 경로는 3회 모두 `journey-core-problem`, `journey-core-submit`, `journey-major-core`다. 알림 순서도 3회 같다: `JudgeJobLost`(30~45초) → `DbConnectionAcquireFailed`(45초) → `ServiceErrorHigh`(180~195초) → `ReadLatencyHigh`(360~390초). `CoreBurnFastAll`은 울리지 않았다(1시간 창 조건을 5분 장애가 넘지 못함). 3회 모두 재현해 주입값으로 확정한다.

## 개요

채점 워커가 사라지자 제출 요청이 채점 결과를 기다리며 core DB 연결을 쥐었다. core 풀(파드당 10)이 가득 찼고 대기가 97~146까지 쌓였다. 같은 풀을 쓰는 문제 조회와 major-core 요청이 연결 획득 제한(3초)에 걸려 5xx를 냈다. 채점과 상관없는 핵심 경로가 채점 워커 한 대 때문에 멈췄다.

## 영향

| 묶음 | 실패율(측정 구간) | p95 | 지속 시간 |
|---|---|---|---|
| 핵심 | 3.6~5.8% | 1.1~2.7초(측정 구간 전체 경로, 평소 조회 24ms) | 약 6분(주입 후 390~405초) |
| 주요 | 4.6~8.9% | 2.7~3.7초 | 같음 |

- 채점: 회차마다 906~934건 유실(k6 기준, 결과를 받지 못한 제출)
- 데이터 손실: 없음(유실은 채점 결과 미수신, 제출 기록은 남음)
- 오류 예산: 핵심 4주 예산의 0.27~0.43%를 한 번에 씀

## 근본 원인

제출 요청이 채점 결과를 기다리는 동안 DB 연결을 놓지 않는 구조에서, core 풀 크기(10)가 채점 대기 시 동시 제출 수보다 작다. 채점이 멈추면 제출이 풀을 모두 차지하고 같은 풀을 쓰는 다른 경로가 굶는다.

## 기여 요인

- 채점 워커가 1개이고 스팟 노드 한 대에 있다(KEDA 최소·최대 1). 노드 회수 = 채점 정지
- 제출 경로와 조회 경로가 같은 풀을 쓴다. 격벽이 없다
- 풀 고갈을 직접 알리는 `DbConnectionAcquireFailed`는 45초에 울렸지만 Alertmanager 경로가 blackhole이었다
- 사람이 받은 증상 알림(`ServiceErrorHigh`)은 경로만 알려 주고 원인(채점) 쪽을 가리키지 않는다

## 연쇄 경로

| 순서 | 서비스·구성 요소 | 일어난 일 | 근거 |
|---|---|---|---|
| 1 | judge-worker | 0으로 내려감 | `s1c-events`, 파드 수 |
| 2 | core 제출 경로 | 채점 대기로 요청이 길어지며 연결을 쥠 | 제출 p95, Envoy 제출 동시 요청 |
| 3 | core Hikari 풀 | 활성 10/10, 대기 97~146 | `hikaricp_connections_active`, `_pending` |
| 4 | 문제 조회, major-core | 연결 획득 시간 초과 → 5xx | 경로별 5xx, `DbConnectionAcquireFailed` |
| 5 | 사용자 | 문제 목록·대결 화면 오류, 제출 결과 미수신 | k6 실패, 채점 유실 |

## 탐지 주체

알림이 먼저였다. 다만 사람에게 간 첫 알림 두 개(`JudgeJobLost`, `ServiceErrorHigh`)만으로는 "채점이 멈춰서 조회가 터진다"는 연결을 바로 짓기 어렵다. 그 연결 고리인 풀 고갈 알림은 울렸지만 사람에게 가지 않았다.

## 등급과 판정 근거

- 등급: SEV1
- 판정 근거: severity.md SEV1 ②(채점 결과 유실, `JudgeJobLost`). 핵심 기능 전면 불가(SEV1 ①)는 아니다(성공 비율 50% 이상 유지)
- 예산 소진량(핵심): 0.27~0.43%

## 잘된 점

- 3회 모두 같은 연쇄, 같은 알림 순서로 재현되어 개선 효과를 비교할 기준이 분명하다
- 워커 복구 뒤 약 100초 안에 핵심 경로가 회복됐다

## 아쉬운 점

- 풀 고갈 알림이 사람에게 가지 않았다
- 채점 장애의 영향이 채점 기능에 갇히지 않고 조회까지 번졌다

## 운이 좋았던 점

- DB 연결 합은 60~70으로 RDS 상한(303)과 거리가 멀어 auth·battle로는 번지지 않았다
