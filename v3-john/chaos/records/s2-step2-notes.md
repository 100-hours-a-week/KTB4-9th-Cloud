# S2 단계 2(핵심 기능 우선순위 클래스) 실험 메모 (2026-11-23)

변경: PriorityClass `cosmos-core-journey`(200000, 낮은 우선순위 선점 허용)를 auth, core에 적용. 단계 1(이중화)과 노드 최대 3대는 그대로다.

대상 노드 `ip-10-30-38-27`에는 core 1개와 **auth 2개가 모두** 있었다. 노드 분산이 `ScheduleAnyway`(가능하면)라서 한쪽에 몰렸다. 이 약점을 보려고 이 노드를 골랐다.

| 항목 | 개선 전 | 단계 1 | 단계 2 |
|---|---|---|---|
| 첫 증상 알림 | `JudgeJobLost` 120초 | 없음 | 없음 |
| 핵심 5xx | 216/13,424 | 0/13,766 | 0/13,663 |
| 주요 5xx | 163/13,021 | 0/13,299 | 0/13,215 |
| 채점 유실 | 57 | 0 | 0 |

- 18:34:45 회수 알림, 18:35:28 대체 노드, 18:36:00 첫 auth를 다른 노드로 옮김(옛 노드의 auth 하나가 남아 서비스), 18:36:32 새 auth 준비, 18:37:04 옛 노드 회수로 남은 auth 종료, 18:37:36 세 번째 auth 준비
- auth 두 개가 한 노드에 있어도 PDB(minAvailable 1)가 비우기를 한 번에 하나씩으로 막아 무중단이었다. 다만 회수가 비우기보다 빨랐다면(관리형 노드 그룹이 알림을 늦게 받는 경우) auth가 함께 사라졌을 것이다
- 실험 뒤 core 두 개가 다시 한 노드(`ip-10-30-32-11`)에 모였다. `ScheduleAnyway`는 자리가 모자라면 분산을 포기한다
- 우선순위 클래스는 이번에 쓰이지 않았다. Pending이 생기지 않았기 때문이다(대체 노드가 회수 전에 준비됨). 단계 2의 효과는 이 실험으로 보이지 않는다. 대체 노드가 늦거나 안 뜨는 경우(스팟 용량 부족)에만 의미가 있다

## 후속 후보

- 분산을 `DoNotSchedule`로 바꾸면 한 노드 몰림은 막지만 노드 3대가 꽉 찰 때 파드가 뜨지 못한다. 노드 여유와 함께 정해야 한다
- 실제 효과를 보려면 대체 노드가 뜨지 못하는 상황(노드 그룹 최대 2로 낮춘 상태에서 회수)을 별도 실험으로 돌려야 한다
