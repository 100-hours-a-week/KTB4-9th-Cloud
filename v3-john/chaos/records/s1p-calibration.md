# S1' 주입값 N 보정 (Task 6)

## 1. 계산

실측(`round2-baseline.md` 1절): RDS 상한 M = 303. core 밖의 연결 = auth 2 x 10 + battle 2 x 10 + rdsadmin 2 = 42. core 평상시 2 x 10.

core 풀을 N으로 바꾼 뒤의 연결(Hikari 기본값은 최소 유휴 연결 = 최대 풀이라 파드가 뜨자마자 N개를 연다):

| 시점 | 연결 합 | 상한 아래 조건 |
|---|---|---|
| core 카나리(새 1 + 옛 2) | N + 20 + 42 | N ≤ 241 |
| core 승격 중(새 2 + 옛 1, `maxUnavailable` 0, 추가 1) | 2N + 10 + 42 | N ≤ 125 |
| core 안정(새 2) | 2N + 42 | N ≤ 130 |
| auth 롤링 재시작(새 auth 1 추가) | 2N + 42 + 10 | N ≤ 125 |

- auth 재시작 때 상한을 넘으려면 N ≥ 126이다. 그런데 core 승격 중의 순간 합(2N + 52)이 auth 재시작 때의 합과 같다. 즉 "core 배포는 상한 아래에서 끝나고 auth 재시작만 넘는다"는 N은 산술로는 없다
- 실제로는 core 승격 중 옛 파드 1개가 곧 종료되며 연결 10개를 돌려주므로, 새 core 파드가 잠시 연결 일부만 얻고 기동한 뒤 나머지를 채울 수 있다. 반면 auth 재시작 때는 옛 auth 파드가 연결을 쥔 채 남는다(`maxUnavailable` 0). 그래서 승격의 넘침은 순간이고 auth의 넘침은 지속된다
- 새 auth 파드가 연결을 하나도 얻지 못하려면 core 안정 상태에서 남는 연결이 0이어야 한다: 2N + 42 ≥ 303 → N ≥ 131
- N = 126~130이면 새 auth 파드가 연결 몇 개를 얻어 기동할 수 있다(Hikari는 연결 1개 이상이면 시작한다). 이 범위에서는 장애가 재현되지 않을 가능성이 크다

첫 후보는 **N = 131**이다. 재현되지 않으면 계획대로 한 단계(+10)씩 올린다.

## 2. 보정 실행

| 회차 | N | 결과 |
|---|---|---|
| calib-1(`s1p-calib-1-20261124-0418`) | 131 | 재현 안 됨 |

- core 풀 131 배포는 카나리를 통과했다(PR 병합 04:22:24, Healthy 04:28:35)
- core 파드가 실제로 연 연결은 23·30이었다. `hikaricp_connections_min`이 core 포함 모든 Spring 서비스에서 10이다. 앱 설정으로 최소 유휴 연결이 10으로 고정되어 있어, 풀을 키워도 수요만큼만 연다. 1절의 "Hikari 기본값(최소 유휴 = 최대)" 가정이 틀렸다
- auth 재시작(04:31:38) 뒤 새 auth 파드는 31초 만에 Ready, 롤링은 04:32:58에 오류 없이 끝났다
- 결론이 분명해 대응자 완화 신호로 04:33에 원복했다. DB 연결은 75로 돌아왔다

N을 올려도 최소 유휴 10 때문에 평상시 연결은 늘지 않으므로 이 설계로는 재현할 수 없다. 계획대로 멈추고 사용자에게 알렸고, 사용자가 "지연 사건 촉발"로 바꾸기로 했다. 이어진 사전 측정은 `s1p-pilot.md`에 있다.

이 회차에서 실행기 결함 두 가지를 찾아 고쳤다.

- 주입 시간이 core PR 병합부터 시작되어 auth 재시작 뒤 관찰이 1~2분뿐이었다 → 주입 준비 단계(`pre-inject.sh`) 분리(PR #94)
