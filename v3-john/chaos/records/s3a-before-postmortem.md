# INC-20261123-05 포스트모템 (S3a 개선 전 실험)

비난 없는 형식이다. 장애 주입 실험이며 대응자가 원인(연결 차단)을 미리 알고 있었다. 기록은 `s3a-before-20261123-1934/response.log`, `watch.log`, Prometheus에서 왔다.

## 시각

| 항목 | 시각(KST) |
|---|---|
| 발생 | 19:37:24 NetworkChaos 적용(auth, core, battle → RDS 10.30.20.0/23 차단) |
| 탐지 | 19:39:11 `DbConnectionPoolExhausted`, 이어서 `JudgeJobLost`(주입 후 210초) |
| 완화 | 없음. 대응자가 할 수 있는 조치가 없었다(RDS available, 경로 문제) |
| 종료 | 19:42:27 차단 해제, 19:42:39 파드 준비 복귀, 1분 창 기준 주입 후 345초 |

- 탐지 방법: 원인 알림 `DbConnectionPoolExhausted`가 증상 알림보다 먼저 울렸다
- 발생 지점: Spring 3개 → RDS
- 복구 방법: 차단 해제(실험 종료) 뒤 자동 복구

## 개요

Spring 3개에서 RDS로 가는 연결이 5분 동안 끊겼다. 준비 상태 검사(`/actuator/health`)가 DB를 포함해 약 45초 뒤 6개 파드가 모두 서비스에서 빠졌다. 요청은 503이 아니라 Envoy 경로 제한 시간 15초까지 묶인 뒤 실패했다.

## 영향(판정 구간 19:37:20~19:53:30)

| 묶음 | 실패율 | p95 | 지속 시간 |
|---|---|---|---|
| 핵심 | 0.83%(69/8,351) | 24ms | 차단 5분 동안 사실상 불가 |
| 주요 | 1.35%(109/8,102) | 43ms | 같음 |

- 차단 중 Envoy 처리량: 초당 27건 → 1건 미만, 그중 약 70%가 5xx
- 건수 기반 실패율이 작은 이유: 부하 생성기가 응답을 받아야 다음 요청을 보낸다. 요청이 15초씩 묶여 요청 수 자체가 줄었다
- 채점 유실 3건, 데이터 손실 없음

## 근본 원인

앱이 RDS에 닿지 못했다(주입). 이 장애를 키운 구조적 원인은 거의 모든 요청이 DB를 쓰고, DB 장애를 빨리 실패로 돌려주지 않는다는 점이다.

## 기여 요인

- Hikari 연결 대기 30초가 Envoy 경로 제한 15초보다 길다. 요청이 끝까지 묶인다
- 준비 상태 검사가 DB를 포함해 DB가 필요 없는 요청까지 받을 파드가 없어진다
- 엔드포인트가 0개인데 Envoy `upstream_cx_none_healthy`가 0이었다. 클러스터 지표 기반 SLI가 이 장애를 작게 본다
- RDS 지표(연결 수, 지연)를 Grafana에서 볼 수 없었다(CloudWatch 데이터 소스 없음)

## 연쇄 경로

| 순서 | 서비스·구성 요소 | 일어난 일 | 근거 |
|---|---|---|---|
| 1 | Spring 3개 | 새 연결 시도가 시간 초과, Hikari 대기열 증가 | 로그, `DbConnectionPoolExhausted` |
| 2 | kubelet | 헬스 검사의 DB 확인 실패로 6개 파드 준비 해제 | `kube_pod_status_ready` |
| 3 | Envoy | 대상 없음, 요청 15초 시간 초과 | downstream 5xx, 처리량 |
| 4 | core → Judge | 제출 경로 실패, 채점 유실 3 | k6 `judge_lost` |

## 잘한 점

- 원인 알림이 증상 알림보다 먼저 울렸다
- RDS 상태를 바로 확인해 "RDS 장애가 아니라 경로 문제"를 2분 안에 가렸다

## 운이 좋았던 점

- 실험이라 차단이 5분 뒤 스스로 풀렸다. 실제 장애에서는 대응자가 할 수 있는 일이 없는 상태가 계속된다
