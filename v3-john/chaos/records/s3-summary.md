# S3 RDS 장애: 단계별 비교

S3a(연결 차단)는 `s3a-summary.md`에 있다. 이 문서는 S3b(삭제와 복원)와 S3 전체 요약이다.

## S3b 삭제와 복원

10초마다 테스트 사용자 쿠키로 `/api/auth/me`를 불러 서비스 상태(5xx·연결 실패 = 불가)와 데이터 표식(401·404 = 시드 이후 만든 사용자 행 없음)을 함께 기록했다(`probe.log`). 삭제 전 두 실험 모두 안전망 수동 스냅샷을 만들었다(측정에는 쓰지 않음).

| 단계 | 설정 | 실험 | 삭제 요청 | 서비스 불가 | 시드 상태·데이터 복구 | 데이터 손실 | 복구 방법 |
|---|---|---|---|---|---|---|---|
| 개선 전 | 자동 백업 0, 삭제 보호 없음, 최종 스냅샷 없음 | s3b-before-20261123-2055 | 20:58:21 | 20:58:31~21:11:04(12분 33초), 21:12:55~21:16:47 다시 불가(덤프 복원) | 21:16:47, 삭제 후 18분 26초 | 시드 이후 전부(표식 404) | Terraform 재생성(시드 스냅샷) → 시드 덤프 복원 → 테스트 데이터 재생성 |
| 3 | 자동 백업 1일, 삭제 보호, 최종 스냅샷 | s3b-step3-20261123-2124 | 21:27:46 | 21:27:56~21:34:59(7분 3초), 21:41:54 한 번 503(Spring 재시작) | 21:34:59, 삭제 후 7분 13초 | 복원 가능 끝(21:24:56) 이후 쓰기, 약 3분(표식 200) | 남은 자동 백업에서 특정 시점 복원 → Terraform import |

- **삭제 보호**: 보호가 켜진 상태에서 `delete-db-instance`는 거부됐다("Cannot delete protected DB Instance", `s3b-step3-protection-check.log`). 단계 3 실험은 보호를 일부러 끄고 지웠다(보호를 푼 뒤 실수로 지운 상황)
- **복원 시각**: 삭제 1분 전(21:26:46)으로 복원하려 했으나 복원 가능 끝이 21:24:56이었다. 트랜잭션 로그 업로드가 몇 분 늦다. 마지막 몇 분의 쓰기는 자동 백업으로도 잃는다
- **복원 직후 Terraform**: import 뒤 plan에 `skip_final_snapshot`, 태그, 비밀번호 차이가 남아 한 번 더 적용했다. 이후 plan 변경 없음
- **자동 백업을 켜는 순간**: 0 → 1로 바꾸는 적용은 약 5분 걸렸다(첫 백업). 이 동안 서비스 영향은 따로 재지 않았다

## 복구 목표(측정 뒤 정함)

설계서는 "측정 후 목표"를 정하기로 했다. 측정값을 보고 다음을 목표로 기록한다.

| 지표 | 개선 전 측정 | 단계 3 측정 | 목표 |
|---|---|---|---|
| 복구 시간(삭제 → 서비스) | 18분 26초 | 7분 13초 | 15분 이내 |
| 데이터 손실 | 시드 이후 전부 | 약 3분 | 5분 이내 |

## 단계 4(Multi-AZ, 선택)

하지 않았다. 인스턴스 비용이 두 배가 되고, 이번 장애(경로 차단, 삭제)는 Multi-AZ로 막히지 않는다. Multi-AZ는 인스턴스·AZ 장애에 대한 대비다.

## S3 전체에서 배운 것

- DB 경로 장애(S3a)는 설정만으로 시간을 줄이기 어렵다. 거의 모든 요청이 DB를 쓰기 때문이다. 캐시·읽기 복제본 같은 앱 구조 변경이 필요하다
- DB 소실(S3b)은 설정 세 줄(자동 백업, 삭제 보호, 최종 스냅샷)로 복구 시간이 절반 아래, 데이터 손실이 "시드 이후 전부"에서 "몇 분"으로 줄었다. 비용 대비 효과가 가장 큰 개선이었다
