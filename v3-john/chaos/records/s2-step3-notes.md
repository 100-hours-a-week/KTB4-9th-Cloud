# S2 단계 3(AZ 두 곳, 인스턴스 유형 5개) 실험 메모 (2026-11-23)

변경: application 노드 그룹 서브넷 a·c, 유형 t3.xlarge, t3a.xlarge, m5.xlarge, m6i.xlarge, m5a.xlarge. Terraform이 노드 그룹을 교체했다(교체 중 약 10분 동안 application 파드 전부 내려감, 실험 없는 시간에 적용).

## 교체 직후 발견

- 노드 그룹 교체 뒤 core, auth, battle 6개가 모두 한 노드에 떴다. 처음 준비된 노드에 몰렸고 `ScheduleAnyway` 분산은 이후 다시 나누지 않는다. 재시작으로 나눈 뒤 실험했다
- 새 노드는 a 2대, c 1대였고 모두 m5.xlarge였다. RDS는 ap-northeast-2c다. 이전에는 모든 노드가 a라 RDS와 다른 AZ였다

## 결과(s2-step3-20261123-1908)

대상은 AZ c 노드 `ip-10-30-63-164`였다. 이 노드에 core, auth, battle 각 1개와 함께 **judge-api(레플리카 1)와 Envoy 두 개가 모두** 있었다.

| 항목 | 개선 전 | 단계 1 | 단계 2 | 단계 3 |
|---|---|---|---|---|
| 첫 증상 알림 | `JudgeJobLost` 120초 | 없음 | 없음 | `JudgeJobLost` 180초 |
| 핵심 5xx | 216/13,424 | 0/13,766 | 0/13,663 | 33/9,861 |
| 주요 5xx | 163/13,021 | 0/13,299 | 0/13,215 | 0/9,536 |
| 채점 유실 | 57 | 0 | 0 | 38 |
| 조회 p95 | 39ms(핵심 전체) | - | - | 24.8ms(조회) |

- 대체 노드는 회수 알림(19:11:54) 37초 뒤 AZ c에 떴다(19:12:31). 이전 실험(38~43초)과 같다(2026-11-24 정정: 처음에 "약 3분"으로 잘못 적었다)
- 유실과 5xx는 AZ 변경 때문이 아니라 배치 때문이다. 레플리카 1인 judge-api와 게이트웨이(Envoy) 두 개가 모두 회수 노드에 있었다. Envoy 분산(`topologySpreadConstraints`, ScheduleAnyway)도 노드 그룹 교체 뒤 한 노드로 몰렸다
- k6 Job이 대기 시간 안에 끝나지 않아 k6 요약(클라이언트 쪽 실패 수)이 없다. Envoy가 사라진 동안 실패한 요청은 Envoy 지표에 잡히지 않으므로 위 5xx는 실제보다 작을 수 있다
- 조회 p95는 24.8ms로 기준선(24.0ms)과 같다. core 하나가 RDS와 같은 AZ(c)에 있었지만 차이는 보이지 않았다

## 판단

단계 3의 목적(같은 AZ·같은 유형 동시 회수와 용량 부족 위험 감소)은 이 실험으로 검증되지 않는다. 회수 한 대 실험에서는 AZ 분산의 이득이 드러나지 않고, 오히려 노드 그룹 교체가 배치를 한쪽으로 몰아 결과를 나쁘게 만들었다.

후속 후보(보고서):
- judge-api 레플리카 2와 PDB
- Envoy 분산을 `DoNotSchedule`로 강화
- 노드 그룹 교체·확장 뒤 파드를 다시 나누는 descheduler(또는 재시작 절차를 런북에 넣음, `runbooks/spot-node-loss.md`)
