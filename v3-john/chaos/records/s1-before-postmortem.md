비난 없는 형식이다. 장애 주입 실험이며 원인을 대응자가 미리 알고 있었다(아래 "운이 좋았던 점").

- 복구 방법: 이전 메모리 값으로 되돌리는 PR 병합(Argo CD 자동 동기화)

## 개요

core 메모리를 2Gi에서 448Mi로 낮춘 PR이 병합됐다. 새 파드는 준비 상태 검사를 통과해 배포는 성공으로 보였지만, 부하를 받자 약 4분 뒤 OOMKilled로 재시작했다. 레플리카가 1개라 재시작 동안 core 요청이 실패했고, 처리 중이던 채점 6건이 결과 없이 끝났다.

## 영향(판정 구간 16:12:18~16:32:54)

|---|---|---|
| 핵심 | 1.35%(163/12,011) | 47ms |
| 주요 | 1.46%(169/11,595) | 49ms |

- 채점 완료율 98.5%(유실 6, 업무 거절 7)
- 예산 소진량(핵심): 4주 예산의 0.1%
- 데이터 손실: 없음

## 근본 원인

메모리 제한이 core의 부하 시 실제 사용량(작업 메모리 최대 약 560Mi)보다 작았다.

## 기여 요인

- 레플리카 1: 파드 하나가 죽으면 core 전체가 멈춘다
- 준비 상태 검사가 메모리 여유를 보지 않는다. 기동 직후에는 사용량이 작아 검사를 통과한다
- 값 파일 변경을 막는 검사가 없다(제한이 실사용보다 작은지, JVM 힙 비율과 맞는지)
- core가 Judge 결과를 동기로 기다리므로 core가 죽으면 진행 중 채점이 함께 사라진다

## 탐지 주체

알림이 먼저였다(`JudgeJobLost`). 원인 알림 `PodCrashLooping`이 꺼져 있어 증상 알림이 첫 신호였다.

## 등급과 판정 근거

- 등급: SEV1
- 판정 근거: 채점 결과 유실(SEV1 ②). 핵심 기능 전면 불가(SEV1 ①)는 아니다
- 가설("10분 안 탐지, 30분 안 완화"): 성립(탐지 4분, 완화 4분 32초)

## 잘된 점

- 증상 알림이 4분 안에 울렸다
- 되돌림이 PR 한 번으로 끝났고 1분 안에 배포됐다

## 아쉬운 점

- 첫 알림이 원인(OOMKilled)이 아니라 결과(채점 유실)라, 최근 배포를 의심하는 근거를 사람이 찾아야 했다
- 핵심 5xx가 1.35%라 `CoreUnavailable`, `CoreErrorBudgetBurnFast` 어느 쪽도 울리지 않았다. 채점 유실 알림이 없었다면 탐지가 늦었다

## 운이 좋았던 점

- 대응자가 주입 내용을 알고 있었다. 원인 파악 8초는 실제 장애의 값으로 볼 수 없다. 단계별 비교에서는 같은 조건(대응자가 알고 있음)끼리만 비교한다
- k6 트래픽이 작아(10 VU) 재시작 뒤 몰림이 크지 않았다
