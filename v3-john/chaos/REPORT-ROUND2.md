# v3-john 장애 주입 2차 보고서: DB·큐 노드 교체 뒤 채점이 회복하지 못하는 장애의 대응

작성 2026-11-25. 실험 기간 2026-11-24~25. 1차 보고서는 `REPORT.md`, 2차 설계서는 `docs/superpowers/specs/2026-11-24-v3-john-fault-injection-round2-design.md`다. 원자료는 `chaos/records/`에 있다.

## 0. 판단 기준: SLI, SLO, 에러 예산

이 보고서의 모든 판정은 아래 기준을 따른다. v3-john은 작업할 때만 켜고 트래픽은 k6가 만든다. 목표와 예산은 "운영이라면 이렇게 둔다"는 가정이고, 실험의 합격 여부는 실험 구간 안의 수치로 판정한다.

### 0.1 기능 묶음

| 묶음 | 기능 | 이유 |
|---|---|---|
| 핵심 | 로그인, 문제 조회, 코드 제출과 채점 | 서비스의 본래 가치인 "문제를 풀고 채점받기" |
| 주요 | 대결, 랭킹, 알림, 활동 기록 | 잠시 실패해도 나중에 따라잡을 수 있다 |
| 부가 | AI 힌트, 풀이 평가 | 외부 LLM에 의존하고, 없어도 문제 풀이는 된다 |

묶음은 Envoy Gateway 경로(HTTPRoute)로 나누고 `journey` 라벨로 기록한다.

### 0.2 SLI와 SLO

| SLO | SLI(측정 방법) | 목표 |
|---|---|---|
| 핵심 기능 가용성 | 핵심 묶음 요청 중 5xx가 아닌 비율(Envoy 업스트림 응답 코드) | 99.5% |
| 주요 기능 가용성 | 주요 묶음 요청 중 5xx가 아닌 비율 | 99% |
| 부가 기능 가용성 | 부가 묶음 요청 중 5xx가 아닌 비율 | 95% |
| 조회 지연 | 로그인·문제 조회 p95 | 기준선 p95의 2배 이하 |
| 채점 처리 | 제출부터 결과 수신까지 p95(k6) | 30초 이하 |

2차에서 SLI 정의를 한 번 고쳤다. 시험 경로로 실측해 보니 Envoy는 요청 제한 시간 초과(504)와 연결 실패(503)를 이미 5xx에 센다. 처음 2차 규칙은 이 둘을 5xx에 더해 오류를 두 번 셌다. 지금은 5xx만 오류로 세고, 연결 실패 요청이 빠지지 않도록 분모를 응답 코드별 합으로 잡는다(PR #93).

### 0.3 에러 예산

- 기간은 최근 4주(40,320분)다. 핵심 기능 99.5%면 4주 동안 완전히 멈춰도 되는 시간은 약 200분이다
- 소진 속도는 현재 오류 비율이 허용 비율(0.5%)의 몇 배인지다. 14.4배면 약 2일 만에 예산을 다 쓴다(빠른 소진 알림 기준)
- 장애 한 건의 예산 소진량 = (실패 비율 x 지속 시간) ÷ 4주 허용 실패 시간

### 0.4 등급과 대응 목표

| 등급 | 기준 | 탐지 목표 | 완화 목표 |
|---|---|---|---|
| SEV1 | 핵심 기능 전면 불가, 채점 결과 유실, 데이터 손실 | 5분 | 30분 |
| SEV2 | 핵심 기능 빠른 소진(14.4배), 핵심 지연 목표 위반, 주요 기능 전면 불가, 모니터링·알림 경로 장애 | 5분 | 30분 |
| SEV3 | 주요 기능 빠른 소진, 부가 기능 장애, 이중화 상실 | - | 다음 작업 세션 |

## 1. 요약

- **배경**: 비용 때문에 모든 노드를 스팟으로 운영하다가 이틀 동안 실제 회수를 7번 넘게 겪었고, 한 번은 모니터링이 26분 동안 사라졌다. 데이터를 가진 DB·큐, 시스템 애드온, 모니터링을 온디맨드 전용 노드로 옮기는 배치 기준을 세웠다(2장)
- **장애**: DB·큐 노드가 바뀐 뒤 채점 워커가 "살아 있지만 일을 못 하는" 상태가 되어 47분 동안 제출이 실패했다. 쿠버네티스는 컨테이너가 Running이라 아무것도 하지 않았고 사람이 재시작해 끝났다. 노드 교체는 온디맨드에서도 패치·업그레이드·점검 때마다 일어나므로 배치로는 막을 수 없다(3장)
- **대응**: 대기열 처리 진척을 보는 생존 검사(자동 재시작), 워커 상시 2대와 자동 확장, 원인 위치를 알려주는 알림, 런북(4장)
- **결과**: 같은 장애를 세 구성에서 3회씩 주입했다. 원래 구성은 10분 동안 회복하지 못했고(제출 실패 중앙값 1,830건, 사람 개입 필요), 대응 후에는 3회 모두 3분 만에 사람 없이 회복했다(416건, -77%). 정상 상황 오판 재시작 0번(5.2)
- **남은 것**: DB·큐 노드 교체 때 약 1분의 제출 중단은 그대로다. 단일 레플리카 DB·큐의 한계라 이중화나 관리형 전환이 다음 단계다(5.1, 7장)

## 2. 배경: 운영하며 발견한 설계 결함

### 2.1 처음 구성

비용 때문에 모든 노드를 스팟으로 운영했다(임시 결정). 데이터를 가진 DB·큐(채점 Postgres, 채점 대기열 Redis, RabbitMQ, AI Postgres, 레플리카 1)와 모니터링(Prometheus, Alertmanager)까지 스팟 위에 있었다.

### 2.2 실제로 일어난 일

| 시각(KST) | 사건 | 영향 |
|---|---|---|
| 11-24 02:46 | application 노드 회수(`instance-terminated-no-capacity`) | 클러스터 기동 중 |
| 11-24 03:30 | 채점 노드 회수 | 문제 조회 5xx 최대 23/s, 핵심 1분 오류율 최대 30%(채점 경로 장애가 core DB 연결 풀을 통해 번짐) |
| 11-24 07:50, 08:51, 09:47 | application, stateful, 채점 노드 회수 | 부하 없던 시간. stateful 회수로 DB·큐 파드가 이동 |
| 11-24 18:38~19:04 | 회수 실험 중 Prometheus가 다시 뜰 자리를 못 찾음(볼륨 존 2c, 남은 2c 노드 CPU 부족) | **모니터링 약 26분 공백**. 그동안 장애가 나도 알 수 없었다 |

이틀 동안 실제 스팟 회수가 7번 넘게 일어났다. 사유는 모두 스팟 용량 부족이었다.

### 2.3 바로잡은 구성(운영 기준 구성, PR #110)

| 구성 요소 | 바꾼 뒤 | 이유 |
|---|---|---|
| DB·큐(stateful 노드) | 온디맨드 | 데이터를 가진 단일 레플리카는 스팟에 두지 않는다 |
| 시스템 애드온 노드 | 온디맨드 | CoreDNS, 컨트롤러 |
| 모니터링 | 온디맨드 전용 노드(볼륨 존 2c) | 감시자가 장애와 같이 사라지지 않게 한다 |
| 무상태 서비스(로그인, 문제, 대결, 채점) | 스팟 유지 | 이중화되어 있고 비용 절감 효과가 크다 |

전용 노드 그룹과 taint·nodeSelector로 배치한다. 이 구성이 이후 장애 대응 실험의 출발점이다.

## 3. 장애: DB·큐 노드 교체 뒤 채점이 회복하지 못함

### 3.1 발견(2026-11-24 19:44)

stateful 노드 회수 실험 중 DB·큐 네 파드는 약 45초 만에 새 노드에서 떴다. 그런데 채점은 사람이 채점 파드를 재시작한 20:31까지 약 47분 동안 회복하지 않았다. 그동안 제출 실패 623건 이상, 채점 유실 827건, 핵심 SLO 유지율 0.37이었다. 쿠버네티스는 채점 워커 컨테이너가 Running이라 아무것도 하지 않았다.

### 3.2 배치를 고쳐도 남는 이유

DB·큐 노드는 온디맨드에서도 바뀐다. AMI 보안 패치(보통 매달), EKS 버전 업그레이드(연 1~2회 필수), EC2 예정 점검·하드웨어 장애가 모두 노드 교체다. 노드가 바뀌면 단일 레플리카 DB·큐는 EBS를 새 노드로 옮기며 끊긴다.

### 3.3 원인(로그 근거)

| 순서 | 일 | 근거 |
|---|---|---|
| 1 | 노드 교체로 채점 대기열 Redis가 약 50초 끊김 | 상태 저장 파드 Ready 기록 |
| 2 | 채점 워커의 채점 프로세스(resque)가 `Redis::CannotConnectError`로 죽음(`rake aborted`) | Loki 19:44:27, 21:15:06 |
| 3 | 관리 스크립트가 프로세스를 다시 띄움(`Starting workers`) | Loki |
| 4 | 19:44 사례에서는 다시 뜬 뒤 처리 속도가 평소의 약 70%(분당 약 150건 대 200건)에 머물러 대기열을 따라잡지 못함 | Loki 분당 처리 건수 |
| 5 | 컨테이너는 Running → 쿠버네티스 생존 검사 없음 → 사람이 재시작할 때까지 지속 | 파드 상태, 재시작 0 |

같은 노드 교체를 계획 교체로 3회 재현했을 때(아래 5.1)는 3회 모두 스스로 회복했다. 장기 장애는 매번 나는 것이 아니라 "가끔, 나면 사람이 개입할 때까지"인 위험이다.

## 4. 대응 장치

결정 기록은 `decisions/s3r-step1.md`(대안 비교 포함)다.

| 목적 | 장치 | 지속성 |
|---|---|---|
| 자동 복구 | 채점 워커 생존 검사(livenessProbe): 이 파드에 등록된 채점 프로세스가 없거나, 대기열에 일이 있는데 90초 동안 처리 건수가 늘지 않으면 실패 → 쿠버네티스가 재시작. Redis 자체가 불통이면 통과(재시작으로 고쳐지지 않는 의존 장애) | 값 파일. 워커가 몇 대든 파드마다 작동 |
| 처리 여유 | 채점 워커 상시 2대(KEDA 2~3), 채점 노드 2~3대(Terraform) | KEDA·노드 그룹 |
| 탐지 | `JudgePathDegraded`: 제출 경로 실패율 5% 1분 → 원인 위치(상태 저장 파드, 채점 워커)와 런북 안내 | 알림 규칙, promtool 테스트 |
| 운영 절차 | 런북 `runbooks/stateful-node-loss.md`: 확인 순서, 완화, 계획 교체 절차 | 문서 |

비교한 대안: Redis·Postgres 이중화(끊김 자체 제거, 범위·운영 부담 큼), 채점 대기열 관리형 전환(ElastiCache, 이전 작업 필요). 둘 다 후속 과제로 남겼다.

## 5. 실험과 결과

### 5.1 계획 노드 교체(s3r): 평상시 피해

부하(RATE 30) 중 새 stateful 노드를 띄우고 옛 노드를 drain해 DB·큐 네 파드를 옮겼다.

| 회차 | DB·큐 끊김 | 제출 실패(503, 교체 후 11분) | 원인 위치 알림 | 일반 경로 알림 | 사람 개입 |
|---|---|---|---|---|---|
| 대응 전 1 / 2 / 3 | 49 / 50 / 62초 | 165 / 155 / 126 | 없음(규칙 없음) | 195 / 165 / 180초 | 불필요 |
| 대응 후 1 / 2 / 3 | 50 / 61 / 56초 | 172 / 108 / 178 | 120 / 105 / 120초 | 180 / 165 / 180초 | 불필요 |

- 측정 기준: 알림 시각은 옛 노드 drain 시작(DB·큐 끊김 시작) 기준이다. 실험 기록(`record.json`)의 탐지 시각은 주입 시작 기준이라 약 57초(새 노드 기동 대기) 더 크다. 제출 실패(503)는 Envoy 경로 지표(`envoy_cluster_upstream_rq`, 응답 코드 503)의 증가량을 Prometheus에서 따로 계산했다. 알림 시각은 Prometheus `ALERTS` 시계열에서 읽었다
- 제출 실패는 DB·큐가 끊긴 약 1분 동안만 났다(15초 단위 실측, 대응 후 1회차 22:44:15~22:45:15). 단일 레플리카 DB·큐의 한계라 대응 장치로 줄지 않았다. 이 피해를 없애려면 DB·큐 이중화가 필요하다(7장)
- 새 알림은 일반 경로 알림보다 약 60초 빨리, 원인 위치를 적어 울렸다. 채점 유실 알림(`JudgeJobLost`)은 원래 15~30초에 울리고 있어 탐지 시간 자체의 개선은 작다
- 생존 검사가 정상 상황에서 잘못 재시작한 경우는 0번이다

### 5.2 채점 워커 정지(s3w): 장기 장애에 대한 대응

계획 교체 3회에서는 장기 장애가 다시 나지 않았다. 그래서 47분 장애 때의 상태, 곧 컨테이너는 살아 있지만 일을 못 하는 워커를 직접 만들었다. 부하(RATE 30) 중 그 순간 있던 모든 채점 워커 파드의 채점 프로세스를 SIGSTOP으로 멈추고, 600초 뒤 재개한다. 재개는 "사람이 알아채고 고친 시점"에 해당한다.

세 구성에서 각 3회 측정했다. 회복 시점은 15초 구간 안에 제출 실패가 없고 정상 응답이 다시 흐르기 시작한 첫 시점이다.

| 구성 | 회복까지(1/2/3회) | 제출 실패(503, 1/2/3회) | 회복시킨 것 | 사람 개입 |
|---|---|---|---|---|
| 원래 구성: 워커 1대 고정, 생존 검사 없음 | 회복 안 됨(재개 뒤 645 / 660 / 660초) | 1,816 / 1,830 / 1,850 | 없음. 재개할 때까지 10분 내내 실패 | 필요 |
| 자동 확장만: 워커 2~3대, 생존 검사 없음 | (90) / 285 / 285초 | 171 / 761 / 787 | 대기열을 보고 KEDA가 띄운 세 번째 워커 | 불필요 |
| 대응 후: 워커 2~3대 + 생존 검사 | 180 / 180 / 180초 | 432 / 388 / 416 | 생존 검사가 멈춘 워커를 135초에 재시작 | 불필요 |

- **원래 구성은 스스로 회복하지 못했다.** 3회 모두 10분 동안 모든 제출이 실패했고 쿠버네티스 재시작은 0번이었다. 실제 47분 장애와 같은 모습이다. 재개(사람 개입)하고 나서야 약 1분 뒤 회복했다
- **대응 후에는 3회 모두 3분 만에 사람 없이 회복했다.** 제출 실패는 중앙값 1,830건에서 416건으로 77% 줄었다. 10분 정지 기준이라, 사람이 더 늦게 알아챌수록 차이는 커진다(47분 장애라면 원래 구성의 실패는 약 8,600건으로 늘고, 대응 후는 그대로 3분에서 멈춘다)
- **자동 확장만으로도 회복은 됐다.** 멈춘 워커는 그대로 두고 새로 뜬 워커가 일을 대신했다. 다만 이 회복은 새 워커를 띄울 여유에 달려 있다. 최대 대수를 이미 쓰고 있거나 새 워커도 같은 원인에 걸리면 회복하지 않고, 멈춘 워커 두 대는 재개 때까지 멈춰 있다. 생존 검사를 더하면 멈춘 워커 자체를 고치므로 여유와 무관하고, 회복이 105초 빨랐다(285 → 180초). 제출 실패도 약 45% 적었다(중앙값 761 → 416)
- 자동 확장만 1회차(90초)는 주입 직전에 세 번째 워커가 이미 뜨는 중이어서 비교에서 뺐다
- **설계와 다르게 나온 점을 그대로 적는다.** 처음에는 생존 검사만 끈 구성을 "대응 전"으로 잡았다. 그런데 같은 대응에 포함된 자동 확장이 회복을 만들어, 원래 구성 대비 효과를 보여주지 못했다. 그래서 원래 구성(KEDA 1/1, 생존 검사 없음)을 Git으로 잠시 되돌려 따로 측정했다(PR #116, 되돌림 #117)
- **알림**: 원인 위치 알림(`JudgePathDegraded`) 120~135초, 일반 경로 알림(`ServiceErrorHigh`) 180~195초, 채점 유실 알림(`JudgeJobLost`) 0~45초. 세 구성 모두 같다. 원래 구성에서도 알림은 울렸다. 문제는 알림 뒤 사람이 고칠 때까지 장애가 이어진다는 점이었고, 대응은 그 사이를 자동 재시작으로 메운다
- **생존 검사가 잡지 못하는 상태**: 생존 검사는 "처리가 완전히 멈춘" 워커만 잡는다. 실제 47분 장애는 처리가 평소의 약 70%로 "느려진" 상태였고, 파드마다 채점 프로세스가 2개라 하나만 멈춰도 처리 건수는 늘어 검사를 통과한다. 이번 실험(SIGSTOP)은 완전 정지를 검증한 것이다. 부분 저하는 자동 확장(대기열이 쌓이면 세 번째 워커)과 원인 위치 알림이 맡는다. 등록된 채점 프로세스 수가 설정값(2)보다 적으면 실패시키는 검사가 다음 개선 후보다
- **채점 Postgres 장애 때 재시작 반복 가능**: Redis 불통은 검사 통과로 예외 처리했지만 Postgres 불통은 예외가 아니다. 채점이 DB에서 막힌 채 대기열에 일이 있으면 약 2분마다 재시작하고, 재시작 간격이 최대 5분까지 늘어 DB 복구 뒤 회복이 늦어질 수 있다. 같은 이유로 90초 넘게 걸리는 채점이 두 프로세스를 동시에 붙잡으면 재시작될 수 있다. 계획 교체 6회에서는 일어나지 않았다(DB 끊김 약 1분)
- **워커 일부만 재시작**: 대응 후 1·3회차에서는 두 워커 중 한 대만 재시작됐다. 먼저 살아난 워커가 대기열을 비우면 남은 워커는 "대기열에 일이 있는데 처리가 없다"는 조건에 걸리지 않는다. 서비스에는 영향이 없고, 일이 다시 쌓이면 90초 안에 걸린다
- 정상 상황에서 생존 검사가 잘못 재시작한 경우는 0번이다(계획 교체 6회와 평상시 구간)

## 6. 측정을 바로잡은 일과 실패한 시도

- **측정 정정**: 계획 교체 실험에서 처음에 "서비스 회복 150초"로 읽었지만, 이는 1분 창 오류율과 1분 유지 조건이 만든 지연이었다. 15초 단위로 다시 재니 실제 실패는 DB·큐 끊김 시간과 같은 약 1분이었다. 대응 장치의 효과를 과장하지 않도록 이 정정을 그대로 남긴다
- **SLI 이중 집계**: 0.2 참고(PR #93)
- **처음 S1' 설계 기각**: "core 연결 풀 확대 PR이 공유 RDS를 고갈시켜 auth 배포가 실패"를 재현하려 했으나, 앱의 최소 유휴 연결이 10으로 고정돼 풀을 131로 키워도 연결이 늘지 않았다. 측정으로 가설을 버리고 실제 관찰한 연쇄(채점 장애 → core 연결 풀 고갈)로 바꿨다(부록 A)
- **효과 없던 격벽**: 제출 경로 동시 요청 제한(Envoy 회로 차단기)은 한 번도 작동하지 않았다. Envoy 기본 경로 제한 15초가 백엔드 연결 점유 30초보다 짧아 게이트웨이 슬롯이 먼저 풀렸다(부록 A)
- **실험 도구 결함**: 주입 시간이 PR 병합부터 계산되던 문제(PR #94), Argo Rollouts `workloadRef`라 배포 완료 판정이 동작하지 않던 문제(PR #99), 모니터링 공백을 중단 조건으로 보던 문제(PR #108), 볼륨 존 고정 가정(PR #107)을 실험 중에 찾아 고쳤다

## 8. 이력서·포트폴리오

### 8.1 이력서용(3~4줄)

- 비용 때문에 전부 스팟으로 운영하던 EKS에서 이틀 동안 실제 회수 7회와 모니터링 26분 공백을 겪고, DB·큐·시스템 애드온·모니터링을 온디맨드 전용 노드 그룹(taint·nodeSelector, Terraform)으로 분리하는 배치 기준을 세웠다
- DB·큐 노드 교체 뒤 채점 워커가 Running인 채 일을 멈춰 47분 동안 제출이 실패한 장애를 Loki 로그로 추적했다(Redis 끊김 → 채점 프로세스 사망·재기동 → 처리 정지, 쿠버네티스는 감지 못 함)
- 대기열 처리 진척 기반 생존 검사(자동 재시작), 워커 상시 2대·자동 확장(KEDA), 원인 위치 알림(PromQL, promtool 테스트), 런북으로 대응했다
- 같은 장애를 구성별 3회씩 주입해 검증: 회복 "10분 내내 실패, 사람 개입 필요" → 3분 자동 회복, 제출 실패 1,830 → 416건(-77%), 정상 상황 오판 재시작 0회

### 8.2 포트폴리오에서 강조할 판단

- **설계 결함을 운영 중에 찾았다**: 전부 스팟 구성은 임시 결정이었다. 실제 회수와 모니터링 공백을 겪고 "무엇을 스팟에 둬도 되는가"(이중화된 무상태 서비스만)라는 배치 기준으로 바꿨다
- **배치를 고쳐도 남는 장애를 골랐다**: 온디맨드도 패치·업그레이드·점검 때 노드가 바뀐다. 그래서 노드 교체를 계획 교체로 재현하고, 교체 뒤 회복하지 못하는 경우에 대비했다
- **장애가 재현되지 않을 때 상태를 직접 만들었다**: 계획 교체 3회 모두 스스로 회복했다. 장기 장애를 만든 상태(살아 있지만 일을 못 하는 워커)를 SIGSTOP으로 주입해 대응 장치를 검증했다
- **비교가 잘못 잡힌 것을 측정으로 찾아 고쳤다**: 생존 검사만 끈 비교에서 자동 확장이 회복을 만들고 있었다. 원래 구성을 Git으로 되돌려 다시 재고, 두 장치가 각각 무엇을 하는지 나눠 적었다
- **효과가 없는 부분도 적었다**: DB·큐 끊김 약 1분의 제출 중단은 대응 전후 같다(제출 실패 중앙값 155 → 172건). 단일 레플리카의 한계라 이중화가 다음 단계다. 측정 착시("회복 150초")도 15초 단위로 다시 재어 정정했다

### 8.3 사용 기술

EKS 관리형 노드 그룹, Terraform, Argo CD(GitOps), KEDA, 쿠버네티스 livenessProbe, Envoy Gateway, Prometheus·Alertmanager(기록 규칙, promtool 단위 테스트), Grafana, Loki, k6, AWS FIS
