# v3-john 장애 주입과 장애 대응 최종 보고서

2026-11-20~23에 v3-john(EKS, 모든 노드 스팟)에서 세 가지 장애를 주입하고, 개선을 한 단계씩 넣으며 같은 실험을 다시 재서 비교했다. 설계서는 `docs/superpowers/specs/2026-11-10-v3-john-fault-injection-design.md`, 실험 원자료는 `chaos/records/`와 `s3://cosmos-db-backup-352635536602/chaos/`에 있다. 이 보고서의 비교표 수치는 `lib/verify-report.py`로 기록 JSON과 대조했다.

| 시나리오 | 무엇을 주입했나 | 왜 골랐나 |
|---|---|---|
| S1 잘못된 배포 | core 메모리를 448Mi로 낮추는 PR을 main에 병합(Argo CD 자동 배포) | 사람이 만든 변경. 가장 자주 일어난다 |
| S2 스팟 노드 회수 | AWS FIS로 core가 있는 application 노드에 회수 2분 전 알림 | 모든 노드가 스팟. 인프라가 사라진다 |
| S3 RDS 장애 | S3a: Chaos Mesh로 Spring → RDS 연결 5분 차단 / S3b: RDS 인스턴스 삭제 후 복구 | 데이터 계층 소실. 가장 치명적이다 |

공통 조건: 클러스터 안 k6 Job 10 VU, 정상 상태 확인 뒤 주입, 주입 최대 10분, 회복 관찰 10분. 중단 기준은 Spot vCPU 28 초과, Prometheus·Alertmanager 장애, 주입 시간 초과다.

## 2. 밝혀낸 연쇄 경로

### S1: 배포 → OOMKilled → 채점 유실

1. PR 병합, Argo CD 자동 동기화, 새 파드는 준비 상태 검사를 통과한다(기동 직후 메모리가 작다)
2. 부하를 받자 OOMKilled. 레플리카 1이라 core 전체가 재시작 동안 멈춘다
3. core는 Judge 결과를 동기로 기다리므로 처리 중이던 제출이 결과 없이 끝난다(`JudgeJobLost`)
4. `PodCrashLooping`은 재시작 대기 시간이 늘어야 울려 증상보다 약 75초 늦다

트레이싱(단계 2) 뒤 서비스 호출 지도(Tempo metrics-generator, 6시간 합계)는 다음과 같다. 화면 캡처 대신 같은 지표를 표로 남긴다.

| 호출 | 요청 수 | 실패 |
|---|---|---|
| 사용자 → cosmos-core | 215,452 | 887 |
| 사용자 → cosmos-auth | 60,035 | 405 |
| 사용자 → cosmos-battle | 59,923 | 352 |
| cosmos-core → RDS(MySQL) | 1,827,518 | 12 |
| cosmos-battle → RDS | 182,672 | 8 |
| cosmos-auth → RDS | 131,530 | 7 |

- core는 요청 하나에 DB를 평균 약 8.5번 부른다. 조회가 반복되는 구간(N+1 후보)이 있을 수 있다(앱 코드 제안)
- judge-api, ai-llm은 지도에 없다. judge-api(Judge0)는 SDK가 없고, ai-llm은 이미지에 SDK가 있지만 앱이 초기화하지 않는다
- 메모리로 죽는 파드는 스팬을 보내기 전에 강제 종료되어 트레이스에 남지 않는다. S1 원인 파악에는 트레이스가 쓰이지 않았다

### S2: 노드 회수 → 같은 노드의 단일 레플리카 동시 소실

1. 관리형 노드 그룹이 회수 알림을 받으면 대체 노드를 먼저 띄우고 옛 노드를 비운다(강제 종료 아님)
2. 비우는 순간 레플리카 1인 서비스가 내려간다. core 57초, judge-api 약 150초
3. judge-api가 없는 동안 제출은 모두 유실된다
4. 결과는 "그 노드에 무엇이 있었나"로 정해진다. 노드 그룹 교체 뒤에는 파드가 한쪽에 몰려 judge-api와 Envoy 두 개가 같은 노드에 있었다

### S3a: DB 경로 차단 → 전 기능 대기

1. Hikari가 연결을 30초 기다리고 Envoy는 15초에 요청을 끊는다
2. 헬스 검사가 DB를 포함해 45초 뒤 모든 파드가 서비스에서 빠진다
3. 엔드포인트가 0개인데 Envoy `upstream_cx_none_healthy`는 0이다. SLI가 장애를 작게 본다
4. 차단 해제 뒤 15~30초에 회복한다

## 4. 도입하지 않은 결정

- **Spot 한도 증가 요청**: 하지 않았다. 계정 한도 32 vCPU 안에서 실험 중단 기준을 28로 두었다
- **노드 최대 수 증가**: 이중화 뒤 CPU 요청이 모자랐지만 Spring CPU 요청을 1에서 500m으로 낮췄다(실사용 30m 안팎). 노드를 늘리면 vCPU 중단 기준 여유가 없어진다
- **S2 단계 4(회수 알림 EventBridge → Discord, 종료 정리 시간)**: 선택 단계라 하지 않았다. 관리형 노드 그룹이 이미 알림을 받아 비우므로 효과가 작을 것으로 본다
- **RDS Multi-AZ(S3b 단계 4)**: 켜지 않았다. 비용이 두 배가 되고, 이번 실험의 장애(경로 차단, 삭제)는 Multi-AZ로 막히지 않는다
- **monitoring 네임스페이스 NetworkPolicy**: 지금 정책이 하나도 없어 일부만 넣으면 경로가 어긋난다. 이식하지 않았다
- **노드 분산 `DoNotSchedule`**: 노드 3대가 꽉 차면 파드가 뜨지 못한다. `ScheduleAnyway`를 유지하고 런북에 재분산 절차를 넣었다
- **CI 값 검사를 필수 검사로 지정**: 저장소 관리자 설정이라 하지 않았다. 지금은 실패해도 병합이 막히지 않는다

## 5. 앱 코드 개선 제안

인프라·설정으로 고칠 수 없어 팀원에게 넘기는 항목이다.

1. **처리 중 채점 정리**: core가 Judge 결과를 동기로 기다린다. 종료 신호를 받으면 새 제출을 거절하고 처리 중인 것을 끝낸 뒤 내려가거나, 비동기 결과 조회로 바꾼다(S1, S2 유실의 직접 원인)
2. **`/actuator/health/**` 허용**: Spring Security가 `/actuator/health` 정확한 경로만 허용해 준비·생존 그룹을 따로 쓸 수 없다
3. **ai-llm OTel 초기화**: SDK는 이미지에 있으나 초기화하지 않는다
4. **DB 호출 수**: core가 요청 하나에 평균 8.5번 DB를 부른다. 반복 조회를 줄이면 S3a 같은 장애의 영향 시간도 줄어든다
5. **DB 없이 되는 경로**: 문제 목록, 데일리 문제 같은 조회를 캐시(Valkey)에서 먼저 읽으면 DB 장애 중에도 일부 기능이 남는다
6. **PodSecurity restricted 경고**: auth, battle, core와 OTel init 컨테이너가 `runAsNonRoot`, `seccompProfile`, `capabilities.drop`을 지정하지 않아 경고가 난다(차트 기본값으로 넣을 수 있으나 이미지 사용자 확인이 필요)

## 6. 대응자 한 명의 한계

- 대응자는 실험 설계자 한 사람이고 원인을 미리 알았다. 탐지·완화 시간은 실제보다 짧다. 특히 S1 완화 107~391초는 "원인을 알고 있는 사람"의 수치다
- 선언, 원인 파악, 완화, 기록을 한 사람이 했다. 역할 체크리스트(`incident/roles.md`)의 지휘·소통 역할은 검증하지 못했다
- Discord 선언 대신 `records/<실험>/response.log`에 적었다(게시 전 허락 원칙). 실제 소통 지연은 재지 못했다
- S2, S3a처럼 대응자가 할 수 있는 완화가 없는 장애에서는 "기다리며 기록"만 했다. 이것도 실제 대응의 중요한 부분이지만 시간 지표에는 남지 않는다

## 7. 실험 순서를 바꾼 이유

- **S2 개선 전을 S1 단계 3보다 먼저 했다.** S1 단계 3(이중화)과 S2 단계 1이 같은 변경이라, 먼저 넣으면 S2 개선 전을 잴 수 없다
- **노드 최대 3대를 S2 개선 전부터 적용했다.** 설계 당시 이미 들어가 있었다(S2 단계 2의 일부). S2 단계 2에서는 우선순위 클래스만 더했다
- **S1 단계 3·S3a 단계 1에서 실험 도구를 고쳤다.** 주입 판정(롤아웃 완료 요구), 리비전 비교 기준, Chaos Mesh 내부 기록 처리. 각 메모에 이유를 적었다

## 8. 실험 중 실제로 일어난 일

- **실제 스팟 회수**: 2026-11-23 20:51 AWS가 application 노드를 회수했다(ASG: "EC2 Spot Instance interruption notice"). 그 노드에 Prometheus, Alertmanager, Tempo가 있어 약 2분 30초 동안 탐지 수단이 사라졌고 실행기가 실험을 중단했다. 같은 날 19:56에는 재조정 권고로 노드 하나가 교체됐다
- **잘못된 설정 배포**: S3a 단계 1의 첫 구현(`/actuator/health/readiness`, 401)이 core 카나리 자동 중단과 `maxUnavailable: 0`에 막혀 사용자 영향 없이 끝났다. 실험이 아닌 실제 실수를 개선 단계가 막은 사례다
- **트래픽 없을 때 카나리 중단**: 오류율 분석 질의가 트래픽이 없으면 NaN이라 정상 배포가 중단됐다. `max(... >= 0) or vector(0)`으로 고쳤다
- **Grafana 재시작 교착**: RWO 볼륨을 쓰는 Grafana를 롤링 재시작하면 새 파드가 볼륨을 붙이지 못한다. 옛 파드를 지워 풀었다

## 10. 이력서·포트폴리오용 요약

이 절은 보고서 내용을 개인 이력서와 포트폴리오에 옮기기 쉽게 다시 정리한 것이다. 모든 수치는 위 비교표와 `records/`의 원자료에 있다. 이 환경은 운영 서비스가 아니라 운영 구성을 재현한 실험 환경이므로 "장애 주입 실험", "운영 환경을 재현한 EKS"로 표기한다. 앱 코드 문제는 "개선 제안으로 넘겼다"로 적는다.

### 이력서 문장 후보

- EKS 환경에 SLO 기반 장애 주입 실험 체계를 설계·구현. 정상 상태 검증, 중단 조건(Spot vCPU, 모니터링 장애, 주입 시간), 비정상 종료 시 자동 원복, 실험 중 외부 배포 감지를 갖춘 실행기로 3개 시나리오 15회 실험(중단 3회 제외)을 재현 가능하게 수행
- 잘못된 배포 시나리오에서 레플리카·PDB·JVM 힙 비율 조정과 Argo Rollouts 카나리 자동 분석을 단계적으로 도입해 핵심 기능 5xx를 163건에서 0~5건, 채점 유실을 6건에서 0건으로 줄이고, 잘못된 배포를 사람 개입 없이 93초에 자동 중단
- RDS 삭제 시나리오에서 자동 백업·삭제 보호·최종 스냅샷과 특정 시점 복원 절차(Terraform import 포함)를 도입해 복구 시간을 18분에서 7분으로, 데이터 손실을 "시드 이후 전부"에서 약 3분으로 줄임
- 스팟 노드 회수를 AWS FIS로 재현(IAM을 클러스터·노드 그룹 태그로 제한, CloudWatch 알람 중단 조건). 관리형 노드 그룹 ASG가 그룹 지표를 기본으로 내지 않아 중단 알람이 울리지 않는 문제를 찾아 Terraform으로 해결. 이중화 뒤 회수 시 5xx·유실 0
- Prometheus 알림 규칙을 promtool 단위 테스트로 검증하는 CI를 만들고, 장애 실험에서 얻은 근거(힙 밖 메모리 112Mi에서 기동 실패)로 GitOps CI 값 검사를 추가해 같은 결함 PR을 병합 전에 검출
- OTel Java 에이전트를 init 컨테이너로 주입해 이미지 수정 없이 분산 트레이싱 도입, 조회 p95 증가 2~6%를 실측해 도입 기준(120% 이하) 판단

### 가정이 틀렸던 이야기

| 이야기 | 무엇을 배웠나 |
|---|---|
| 메모리를 줄였는데 왜 안 죽지? | 640Mi·512Mi에서 OOMKilled가 안 났다. JVM 기본 힙이 컨테이너 한도의 25%라 힙도 같이 줄었다. 448Mi에서야 재현됐고, 이 분석이 힙 비율 75%와 CI 힙 밖 메모리 검사로 이어졌다 |
| 원인 알림을 켜면 빨라진다? | `PodCrashLooping`은 증상 알림보다 75초 늦었다. 원인 알림이 탐지를 앞당기지 않는다 |
| 트레이싱이면 원인이 보인다? | 메모리로 죽는 파드는 스팬을 보내기 전에 죽는다. 트레이스는 영향 범위만 보여 줬고 오히려 에이전트 메모리가 장애를 키웠다 |

| 실패율이 낮으면 괜찮다? | DB 차단 중 실패율 0.83%였지만 실제로는 5분 동안 전 기능이 멈췄다. 닫힌 부하 모델과 SLI 사각지대가 장애를 작게 보이게 했다 |
