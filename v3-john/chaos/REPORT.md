# v3-john 장애 주입과 장애 대응 최종 보고서

2026-11-20~23에 v3-john(EKS, 모든 노드 스팟)에서 세 가지 장애를 주입하고, 개선을 한 단계씩 넣으며 같은 실험을 다시 재서 비교했다. 설계서는 `docs/superpowers/specs/2026-11-10-v3-john-fault-injection-design.md`, 실험 원자료는 `chaos/records/`와 `s3://cosmos-db-backup-352635536602/chaos/`에 있다. 이 보고서의 비교표 수치는 `lib/verify-report.py`로 기록 JSON과 대조했다.

| 시나리오 | 무엇을 주입했나 | 왜 골랐나 |
|---|---|---|
| S1 잘못된 배포 | core 메모리를 448Mi로 낮추는 PR을 main에 병합(Argo CD 자동 배포) | 사람이 만든 변경. 가장 자주 일어난다 |
| S2 스팟 노드 회수 | AWS FIS로 core가 있는 application 노드에 회수 2분 전 알림 | 모든 노드가 스팟. 인프라가 사라진다 |

공통 조건: 클러스터 안 k6 Job 10 VU, 정상 상태 확인 뒤 주입, 주입 최대 10분, 회복 관찰 10분. 중단 기준은 Spot vCPU 28 초과, Prometheus·Alertmanager 장애, 주입 시간 초과다.

## 1. 시나리오별 비교표

수치는 판정 구간(주입 시작~회복 관찰 끝) 합계다. 첫 알림은 증상 알림 기준이며, 증상 알림이 없으면 "없음"이다.

- **첫 알림**: 주입 시작부터 첫 증상 알림이 firing이 될 때까지
- **완화**: 주입 시작부터 대응자가 완화(S1은 메모리 값을 되돌리는 PR)를 시작한 시각까지. 대응자가 `records/<실험>/mitigate` 파일을 만든 순간이며, 되돌림 배포가 끝난 시각이 아니다. S2·S3a처럼 대응자가 할 수 있는 완화가 없던 실험은 비어 있다
- **복구**: 주입 시작부터 핵심 오류율(1분 창)이 목표(0.5%) 안으로 돌아와 1분 유지된 시각까지. 목표를 벗어난 적이 없으면 0초

## 2. 밝혀낸 연쇄 경로

### S1: 배포 → OOMKilled → 채점 유실

1. PR 병합, Argo CD 자동 동기화, 새 파드는 준비 상태 검사를 통과한다(기동 직후 메모리가 작다)
2. 부하를 받자 OOMKilled. 레플리카 1이라 core 전체가 재시작 동안 멈춘다
3. core는 Judge 결과를 동기로 기다리므로 처리 중이던 제출이 결과 없이 끝난다(`JudgeJobLost`)
4. `PodCrashLooping`은 OOMKilled 약 75초 뒤, 증상 알림보다 45초 늦게 울렸다(수집 30초, 규칙 평가, Alertmanager 그룹 대기 30초)

트레이싱(단계 2) 뒤 서비스 호출 지도(Tempo metrics-generator, 6시간 합계)는 다음과 같다. 화면 캡처 대신 같은 지표를 표로 남긴다.

| 호출 | 요청 수 | 실패 |
|---|---|---|
| 사용자 → cosmos-core | 215,452 | 887 |
| 사용자 → cosmos-auth | 60,035 | 405 |
| 사용자 → cosmos-battle | 59,923 | 352 |
| cosmos-core → RDS(MySQL) | 1,827,518 | 12 |
| cosmos-battle → RDS | 182,672 | 8 |
| cosmos-auth → RDS | 131,530 | 7 |

- core는 요청 하나에 DB를 평균 약 8.5번 부른다. 조회가 반복되는 구간(N+1 후보)이 있을 수 있다(앱 코드 제안)
- judge-api, ai-llm은 지도에 없다. judge-api(Judge0)는 SDK가 없고, ai-llm은 이미지에 SDK가 있지만 앱이 초기화하지 않는다
- 메모리로 죽는 파드는 스팬을 보내기 전에 강제 종료되어 트레이스에 남지 않는다. S1 원인 파악에는 트레이스가 쓰이지 않았다

### S2: 노드 회수 → 같은 노드의 단일 레플리카 동시 소실

1. 관리형 노드 그룹이 회수 알림을 받으면 대체 노드를 먼저 띄우고 옛 노드를 비운다(강제 종료 아님)
2. 비우는 순간 레플리카 1인 서비스가 내려간다. core 57초, judge-api 약 150초
3. judge-api가 없는 동안 제출은 모두 유실된다
4. 결과는 "그 노드에 무엇이 있었나"로 정해진다. 노드 그룹 교체 뒤에는 파드가 한쪽에 몰려 judge-api와 Envoy 두 개가 같은 노드에 있었다

### S3a: DB 경로 차단 → 전 기능 대기

1. Hikari가 연결을 30초 기다리고 Envoy는 15초에 요청을 끊는다
2. 헬스 검사가 DB를 포함해 45초 뒤 모든 파드가 서비스에서 빠진다
3. 엔드포인트가 0개인데 Envoy `upstream_cx_none_healthy`는 0이다. SLI가 장애를 작게 본다
4. 차단 해제 뒤 15~30초에 회복한다

## 4. 도입하지 않은 결정

- **Spot 한도 증가 요청**: 하지 않았다. 계정 한도 32 vCPU 안에서 실험 중단 기준을 28로 두었다
- **노드 최대 수 증가**: 이중화 뒤 CPU 요청이 모자랐지만 Spring CPU 요청을 1에서 500m으로 낮췄다(실사용 30m 안팎). 노드를 늘리면 vCPU 중단 기준 여유가 없어진다
- **S2 단계 4(회수 알림 EventBridge → Discord, 종료 정리 시간)**: 선택 단계라 하지 않았다. 관리형 노드 그룹이 이미 알림을 받아 비우므로 효과가 작을 것으로 본다
- **RDS Multi-AZ(S3b 단계 4)**: 켜지 않았다. 비용이 두 배가 되고, 이번 실험의 장애(경로 차단, 삭제)는 Multi-AZ로 막히지 않는다
- **monitoring 네임스페이스 NetworkPolicy**: 지금 정책이 하나도 없어 일부만 넣으면 경로가 어긋난다. 이식하지 않았다
- **노드 분산 `DoNotSchedule`**: 노드 3대가 꽉 차면 파드가 뜨지 못한다. `ScheduleAnyway`를 유지하고 런북에 재분산 절차를 넣었다
- **CI 값 검사를 필수 검사로 지정**: 저장소 관리자 설정이라 하지 않았다. 지금은 실패해도 병합이 막히지 않는다

## 5. 앱 코드 개선 제안

인프라·설정으로 고칠 수 없어 팀원에게 넘기는 항목이다.

1. **처리 중 채점 정리**: core가 Judge 결과를 동기로 기다린다. 종료 신호를 받으면 새 제출을 거절하고 처리 중인 것을 끝낸 뒤 내려가거나, 비동기 결과 조회로 바꾼다(S1, S2 유실의 직접 원인)
2. **`/actuator/health/**` 허용**: Spring Security가 `/actuator/health` 정확한 경로만 허용해 준비·생존 그룹을 따로 쓸 수 없다
3. **ai-llm OTel 초기화**: SDK는 이미지에 있으나 초기화하지 않는다
4. **DB 호출 수**: core가 요청 하나에 평균 8.5번 DB를 부른다. 반복 조회를 줄이면 S3a 같은 장애의 영향 시간도 줄어든다
5. **DB 없이 되는 경로**: 문제 목록, 데일리 문제 같은 조회를 캐시(Valkey)에서 먼저 읽으면 DB 장애 중에도 일부 기능이 남는다
6. **PodSecurity restricted 경고**: auth, battle, core와 OTel init 컨테이너가 `runAsNonRoot`, `seccompProfile`, `capabilities.drop`을 지정하지 않아 경고가 난다(차트 기본값으로 넣을 수 있으나 이미지 사용자 확인이 필요)

## 6. 대응자 한 명의 한계

- 대응자는 실험 설계자 한 사람이고 원인을 미리 알았다. 탐지·완화 시간은 실제보다 짧다. 특히 S1 완화 107~391초는 "원인을 알고 있는 사람"의 수치다
- 선언, 원인 파악, 완화, 기록을 한 사람이 했다. 역할 체크리스트(`incident/roles.md`)의 지휘·소통 역할은 검증하지 못했다
- Discord 선언 대신 `records/<실험>/response.log`에 적었다(게시 전 허락 원칙). 실제 소통 지연은 재지 못했다
- S2, S3a처럼 대응자가 할 수 있는 완화가 없는 장애에서는 "기다리며 기록"만 했다. 이것도 실제 대응의 중요한 부분이지만 시간 지표에는 남지 않는다

## 7. 실험 순서를 바꾼 이유

- **S2 개선 전을 S1 단계 3보다 먼저 했다.** S1 단계 3(이중화)과 S2 단계 1이 같은 변경이라, 먼저 넣으면 S2 개선 전을 잴 수 없다
- **노드 최대 3대를 S2 개선 전부터 적용했다.** 설계 당시 이미 들어가 있었다(S2 단계 2의 일부). S2 단계 2에서는 우선순위 클래스만 더했다
- **S1 단계 3·S3a 단계 1에서 실험 도구를 고쳤다.** 주입 판정(롤아웃 완료 요구), 리비전 비교 기준, Chaos Mesh 내부 기록 처리. 각 메모에 이유를 적었다

## 8. 실험 중 실제로 일어난 일

- **실제 스팟 회수**: 2026-11-23 20:51 AWS가 application 노드를 회수했다(ASG: "EC2 Spot Instance interruption notice"). 그 노드에 Prometheus, Alertmanager, Tempo가 있어 약 2분 30초 동안 탐지 수단이 사라졌고 실행기가 실험을 중단했다. 같은 날 19:56에는 재조정 권고로 노드 하나가 교체됐다
- **잘못된 설정 배포**: S3a 단계 1의 첫 구현(`/actuator/health/readiness`, 401)이 core 카나리 자동 중단과 `maxUnavailable: 0`에 막혀 사용자 영향 없이 끝났다. 실험이 아닌 실제 실수를 개선 단계가 막은 사례다
- **트래픽 없을 때 카나리 중단**: 오류율 분석 질의가 트래픽이 없으면 NaN이라 정상 배포가 중단됐다. `max(... >= 0) or vector(0)`으로 고쳤다
- **Grafana 재시작 교착**: RWO 볼륨을 쓰는 Grafana를 롤링 재시작하면 새 파드가 볼륨을 붙이지 못한다. 옛 파드를 지워 풀었다

## 10. 이력서·포트폴리오용 요약

이 절은 보고서 내용을 개인 이력서와 포트폴리오에 옮기기 쉽게 다시 정리한 것이다. 모든 수치는 위 비교표와 `records/`의 원자료에 있다. 이 환경은 운영 서비스가 아니라 운영 구성을 재현한 실험 환경이므로 "장애 주입 실험", "운영 환경을 재현한 EKS"로 표기한다. 앱 코드 문제는 "개선 제안으로 넘겼다"로 적는다.

### 이력서 문장 후보

- EKS 환경에 SLO 기반 장애 주입 실험 체계를 설계·구현. 정상 상태 검증, 중단 조건(Spot vCPU, 모니터링 장애, 주입 시간), 비정상 종료 시 자동 원복, 실험 중 외부 배포 감지를 갖춘 실행기로 3개 시나리오 15회 실험(중단 3회 제외)을 재현 가능하게 수행
- 잘못된 배포 시나리오에서 JVM 기본 힙 비율(25%)이 메모리 축소 결함을 숨기는 것을 실험으로 찾고, 힙 비율 고정·카나리 재시작 분석·CI 메모리 값 검사로 같은 결함 PR이 기동 단계에서 멈추게 함(사용자 영향 0, 93초 자동 중단). 개선 뒤 결함의 모양이 바뀌어 이중화 효과는 따로 검증하지 못했다는 한계까지 평가 문서로 정리
- RDS 삭제 시나리오에서 자동 백업·삭제 보호·최종 스냅샷과 특정 시점 복원 절차(Terraform import 포함)를 도입해 복구 시간을 18분에서 7분으로, 데이터 손실을 "시드 이후 전부"에서 약 3분으로 줄임
- 스팟 노드 회수를 AWS FIS로 재현(IAM을 클러스터·노드 그룹 태그로 제한, CloudWatch 알람 중단 조건). 관리형 노드 그룹 ASG가 그룹 지표를 기본으로 내지 않아 중단 알람이 울리지 않는 문제를 찾아 Terraform으로 해결. 이중화 뒤 회수 시 5xx·유실 0
- Prometheus 알림 규칙을 promtool 단위 테스트로 검증하는 CI를 만들고, 장애 실험에서 얻은 근거(힙 밖 메모리 112Mi에서 기동 실패)로 GitOps CI 값 검사를 추가해 같은 결함 PR을 병합 전에 검출
- OTel Java 에이전트를 init 컨테이너로 주입해 이미지 수정 없이 분산 트레이싱 도입, 조회 p95 증가 2~6%를 실측해 도입 기준(120% 이하) 판단

### 가정이 틀렸던 이야기

각 이야기는 실험 전에 세운 가정, 실제로 본 것(시각과 수치), 그렇게 된 이유, 그 뒤 바꾼 것, 근거 기록 순서로 적는다. 수치는 모두 `records/`의 기록에서 왔다.

#### 1. 메모리를 줄이면 바로 죽을 것이다

- **가정**: core 메모리 한도(원래 요청 1Gi, 한도 2Gi)를 낮추면 OOMKilled가 난다. 계획서의 후보는 1.5Gi, 1.25Gi, 1Gi였다.
- **관찰**: 기준선 부하에서 core 작업 메모리 최대가 약 560Mi라 계획 후보는 쓰지 않고 더 낮췄다. 그래도 640Mi(주입 636초)에서는 OOMKilled가 없었고 작업 메모리 최대는 474Mi였다. 512Mi도 주입 396초 동안 OOMKilled가 없었고(최대 460~507Mi), 그 뒤 vCPU 중단 조건으로 실험이 멈췄다. 448Mi에서야 3회 중 3회 OOMKilled가 났다(첫 증상 알림 240·360·255초).
- **이유**: JVM은 최대 힙을 따로 정하지 않으면 컨테이너 한도의 25%로 잡는다. 한도를 낮추면 힙도 같이 작아져(640Mi에서 160Mi, 448Mi에서 112Mi) GC가 더 자주 돌 뿐 컨테이너 전체 사용량이 한도를 넘지 않는다. 힙 밖 메모리(메타스페이스, 스레드 스택, 코드 캐시)는 한도와 상관없이 일정해서, 한도가 그 크기에 가까워진 448Mi에서야 컨테이너가 한도를 넘었다.
- **함께 본 것**: 640Mi 실험의 채점 유실 35건은 OOMKilled가 아니라 주입·원복 배포의 롤링 재시작 때문이었다. 레플리카가 1개라 평소 배포만으로도 처리 중인 채점이 끊긴다.
- **바꾼 것**: 단계 3에서 `-XX:MaxRAMPercentage=75`로 힙 비율을 고정했다. 단계 5 CI 값 검사에 "Spring 이미지는 힙 비율 필수", "힙 밖 메모리(한도 × (1 - 비율)) 256Mi 이상" 규칙을 넣었다.
- **근거**: `scenarios/s1/README.md`(값 탐색 표), `records/s1-search-*-20261120-*.json`

#### 2. 원인 알림을 켜면 탐지가 빨라질 것이다

- **가정**: 단계 1에서 `PodCrashLooping`(OOMKilled로 한 번이라도 재시작하면 울림)을 켜면 증상 알림보다 먼저 원인을 알린다.
- **관찰**: s1-step1(2026-11-20 16:34)에서 OOMKilled는 16:43:30, 증상 알림 `JudgeJobLost`는 주입 후 360초, `PodCrashLooping`은 405초였다. OOMKilled에서 약 75초 뒤, 증상 알림보다 45초 늦었고, 대응자가 파드 상태를 직접 보고 되돌리기로 한 시점보다도 14초 늦었다.
- **이유**: 규칙 자체에는 대기 시간(`for`)이 없다. 늦어진 것은 수집과 전달 경로다. kube-state-metrics 수집 간격 30초, 규칙 평가 주기, Alertmanager 그룹 대기 30초가 더해진다.
- **함께 본 것**: 가장 빨리 울린 증상 알림 `JudgeJobLost`는 실제 사용자 지표가 아니라 k6 합성 부하의 지표(`k6_judge_lost_total`)다. 부하 테스트가 없는 실제 운영에서는 이 알림이 울리지 않는다. 운영에서 같은 장애를 잡을 지표는 `CoreErrorBudgetBurnFast`인데, S1에서는 재시작이 짧아 한 번도 기준에 닿지 않았다.
- **바꾼 것**: 원인 알림만으로는 탐지가 빨라지지 않는다는 결론을 기록하고, OOMKilled 이벤트 기반 알림을 보완안으로 남겼다. 단계 4(카나리 분석)가 같은 신호(재시작 1회)를 배포 경로 안에서 바로 쓰도록 했다.
- **근거**: `records/s1-step1-notes.md`, `s1-step1-20261120-1634/response.log`

#### 3. 트레이싱을 넣으면 원인이 보일 것이다

- **가정**: 단계 2(Tempo, OTel Java 에이전트)로 장애 요청의 경로를 따라가 원인을 빨리 찾는다.
- **관찰**:
  - 1차(s1-step2-20261123-1531): Tempo 자체가 메모리 한도 2Gi에서 OOMKilled를 반복해 트레이스가 비었다. 대응 중 "core 트레이스가 끊겼다"를 core 문제로 잘못 읽었고, 뒤에 Tempo 문제로 정정했다.
  - 2차(s1-step2-20261123-1559, Tempo 4Gi): 새 버전 core 파드의 스팬은 0개였다. 오류 트레이스는 `/actuator/health` 1건뿐이었다. 원인(메모리 한도)은 파드 상태와 Argo CD 배포 이력으로 찾았다.
  - 장애도 커졌다. 개선 전 핵심 5xx 163/12,011, 유실 6이었는데 단계 2는 938/9,502, 유실 41이었다. 에이전트가 메모리를 더 써서 448Mi 파드가 부하 직후 죽었다.
- **이유**: 에이전트는 스팬을 모았다가 5초마다 보낸다(기본값). OOMKilled는 프로세스를 즉시 끝내므로 아직 보내지 않은 스팬이 사라진다. 메모리로 죽는 장애는 트레이스에 남기 어렵다.
- **바꾼 것**: Tempo 메모리 한도 4Gi. 보고서에 "트레이싱은 요청 안에서 생기는 지연·오류(DB 지연 등)에 맞고, 배포 장애의 원인 파악에는 배포 이력과 파드 상태가 낫다"고 적었다. 오버헤드(조회 p95 102~106%)는 기준 안이었다.
- **근거**: `records/s1-step2-notes.md`, 두 실험의 `response.log`, `loadtest/results/2026-11-23-otel-overhead.md`

#### 4. 노드 그룹을 AZ 두 곳으로 나누면 스팟 회수에 더 강해질 것이다

- **가정**: S2 단계 3(application 노드 그룹 서브넷 a·c, 인스턴스 유형 5개)은 같은 AZ·같은 유형이 한꺼번에 회수되는 위험을 줄인다.
- **관찰**: s2-step3-20261123-1908에서 오히려 `JudgeJobLost`가 180초에 울렸고 핵심 5xx 33/9,861, 채점 유실 38이었다. 단계 1·2에서는 둘 다 0이었다. 대체 노드는 회수 알림 37초 뒤에 떠서 다른 단계(38~43초)와 차이가 없었다.
- **이유**: AZ 변경 자체가 아니라 배치 때문이다. Terraform이 노드 그룹을 교체하면서 core, auth, battle 6개가 처음 준비된 한 노드에 몰렸다. 노드 분산 규칙이 `ScheduleAnyway`라 노드가 늘어난 뒤에도 다시 나누지 않는다. 재시작으로 나눈 뒤 실험했지만, 회수 대상 노드에는 레플리카 1인 judge-api와 Envoy 두 개가 모두 있었다. 회수 한 대 실험으로는 AZ 분산의 이득을 보여 줄 수 없었다.
- **바꾼 것**: 런북 `spot-node-loss.md`에 "복구 뒤 서비스별 파드가 서로 다른 노드에 있는지 보고, 몰렸으면 재시작" 절차를 넣었다. judge-api 레플리카 2, Envoy 분산 강화, descheduler를 다음 개선 후보로 올렸다.
- **근거**: `records/s2-step3-notes.md`, `s2-step3-20261123-1908/s2-pods-on-node.txt`, `watch.log`

#### 5. 실패율이 낮으면 장애가 작은 것이다

- **가정**: 판정 구간의 실패율과 예산 소진량이 장애 크기를 보여 준다.
- **관찰**: s3a-before-20261123-1934(RDS 연결 5분 차단)의 핵심 실패율은 0.83%(69/8,351), 예산 소진 0.06%였다. 그러나 차단 중 Envoy 처리량은 초당 27건에서 1건 미만으로 떨어졌고 그중 약 70%가 5xx였다. 파드 6개가 모두 4분 동안 준비 상태에서 빠졌다. 실제로는 5분 동안 거의 모든 기능이 멈췄다.
- **이유**: 두 가지가 겹쳤다.
  - 부하 모델: k6는 가상 사용자 10명이 응답을 받아야 다음 요청을 보낸다. 요청이 Envoy 경로 제한 15초까지 묶여 요청 수 자체가 줄었고, 분모와 분자가 함께 작아졌다.
  - SLI 사각지대: 엔드포인트가 0개인데 Envoy `upstream_cx_none_healthy`는 0이었다. 요청은 즉시 503이 아니라 15초 시간 초과로 끝나, 클러스터 지표 기반 SLI가 장애를 작게, 늦게 본다.
- **함께 본 것**: 단계 2(Hikari 연결 대기 3초)는 요청을 3초 안에 실패시켰다. 실패율은 16.8%로 오히려 커졌고 `MajorUnavailable`도 울렸다. 사용자 입장에서는 15초 대기보다 즉시 오류가 낫지만, 지표만 보면 나빠진 것처럼 보인다.
- **바꾼 것**: S3a는 "불가 시간"으로 읽도록 비교표에 적었다. downstream 지표 기반 SLI를 다음 개선 후보로 올렸다.
- **근거**: `records/s3a-before-notes.md`, `s3a-summary.md`, `s3a-before-postmortem.md`

#### 6. 실험은 통제된 상황에서만 일어난다

- **가정**: 장애는 실행기가 주입한 것만 일어난다.
- **관찰**: 2026-11-23 20:51:26(UTC 11:51:26) s3a-step2의 회복 관찰 중, AWS가 application 스팟 노드 하나를 실제로 회수했다(ASG 활동: "taken out of service in response to an EC2 Spot Instance interruption notice"). 그 노드에 Prometheus, Alertmanager, Tempo가 있었다. 대체 노드가 뜨고 모니터링이 다시 준비되기까지 약 2분 30초였고, 실행기는 모니터링 장애 중단 조건으로 실험을 멈췄다. 같은 날 19:56:59에는 재조정 권고로 노드 하나가 교체됐다.
- **이유**: 모든 노드가 스팟이고, 모니터링 구성 요소가 레플리카 1로 application 노드에 있다. S2 개선 전 실험 준비 중에도 Prometheus·Alertmanager가 회수 대상 core 노드에 같이 있어 미리 옮겨야 했다. 그때 기록한 위험이 그대로 일어났다.
- **바꾼 것**: 보고서 남은 위험 1순위로 올렸다(모니터링을 system·stateful 노드로, 또는 2개로). 이 실험의 판정 구간이 짧다는 점을 기록에 남겼다.
- **근거**: `records/s3a-summary.md`, ASG 활동 기록, `s2-before-postmortem.md`(실험 전 조치)

#### 7. 개선을 넣으면 나머지는 그대로일 것이다

이 이야기는 한 번에 하나만 바꿔도 다른 곳이 같이 흔들린 사례 셋이다.

- **이중화가 자리를 모자라게 했다**: HPA 최소 2를 넣자 application 노드 3대(최대)의 CPU 요청이 98~99%가 되어 core·battle 두 번째 파드가 Pending이 됐다. 실사용 CPU는 30m 안팎이었다. 노드를 늘리면 Spot vCPU 중단 기준(28)의 여유가 없어져, Spring CPU 요청을 1에서 500m으로 낮추고 HPA 기준을 70%에서 140%로 바꿔 확장 시작점(700m)을 유지했다(PR #63).
- **카나리가 트래픽 없는 정상 배포를 막았다**: 우선순위 클래스 배포(리비전 4)가 부하가 없는 시간에 카나리 분석을 받았다. 오류율 기록 규칙이 요청 0이라 NaN이었고, `NaN < 0.072`는 거짓이라 분석이 실패해 정상 배포가 자동 중단됐다. 질의를 `max(... >= 0) or vector(0)`으로 고쳤다(PR #77). 대가로 트래픽이 없을 때 오류율 조건은 사실상 통과하고, 재시작 조건만 남는다.
- **개선이 실제 실수를 막았다**: S3a 단계 1의 첫 구현은 준비 상태 검사를 `/actuator/health/readiness`로 바꿨는데, 앱 보안 설정이 하위 경로에 401을 돌려 새 파드가 준비되지 못했다(PR #79). core 카나리는 진행 시간 초과(300초)로 자동 중단됐고, auth·battle은 `maxUnavailable: 0`이라 옛 파드가 남아 사용자 영향이 없었다. 실험이 아닌 실제 설정 실수를 S1 단계 3·4가 막은 사례다. 헬스 검사에서 DB만 빼는 방식으로 다시 고쳤다(PR #80).
