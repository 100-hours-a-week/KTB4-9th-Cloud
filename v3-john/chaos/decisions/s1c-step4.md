# 결정 기록: S1' 단계 4 제출 경로를 별도 배포로 분리(구조적 격벽)

## 근거

단계 3(core 풀 10 → 40)은 연쇄를 없앴지만 용량 대응이다. core가 동시에 쥐는 연결은 대략 "초당 제출 수 x 연결 점유 시간"이고, 채점이 멈추면 점유 시간이 최대 30초가 된다(`JUDGE0_MAX_WAIT` 30s, 1초 간격 조회). 실험 부하에서 파드당 수요가 11~13이라 40이면 충분했지만, 제출이 3~4배로 늘면 같은 연쇄가 재발한다.

연쇄의 원인은 "채점을 기다리는 제출"과 "문제 조회·대결"이 같은 core 연결 풀을 나눠 쓰는 데 있다. 백엔드 코드(배포 이미지 기준 `6bb76d7`)에서 Judge0를 부르는 곳은 코드 제출(`/problems/{id}/code-submissions`) 하나뿐이다.

## 값

- core, core-submit 모두 풀 10(단계 3 이전 값). 풀을 키우지 않고도 연쇄가 사라지는지를 보기 위해서다
- core-submit은 HPA 2~3, Rollout 대신 Deployment, 서비스 계정은 core-sa 공유(Pod Identity 연결)
- 백엔드의 예약 작업은 `FOR UPDATE SKIP LOCKED`로 선점해 여러 레플리카에서 안전하다(core는 이미 2~3대로 운영 중)

## 검증 기준(실험 전 고정)

단계 3까지와 같은 주입(부하 RATE 30 중 채점 워커 5분 중단)을 3회 반복해 중앙값으로 판정한다. 비교 기준은 단계 3 이전의 개선 전 결과(풀 10)다.

- 문제 조회 + major-core 5xx가 개선 전 중앙값(6,034)보다 90% 이상 줄어든다
- 영향 경로(오류 기준을 넘은 경로) 수가 개선 전(3)보다 줄어든다
- 문제 조회 쪽 core 연결 대기 최대가 0이다(제출 쪽 core-submit 대기는 그대로 적는다)
- CI 연결 예산 검사 통과
- 평상시 영향: 채점이 정상일 때 제출 p95가 개선 전 기준선(약 2.4초)과 같은 수준이다
