# 결정 기록: S1' 단계 4 연결 구조(최소 유휴 연결 축소)

## 근거

개선 전 실험(s1p-before)과 단계 1~3 측정 뒤 채운다.

채울 항목은 core 풀 값 상향 뒤 RDS 연결 합계가 상한에 근접한 시각과 최대값, 그 상태에서 auth 재시작 때 로그인 경로 오류가 난 기록, 기록 경로다.

설계 단계에서 확인한 사실은 다음과 같다.

- Hikari는 `minimumIdle`을 정하지 않으면 최대 풀과 같게 잡는다. 트래픽이 없어도 파드마다 최대 풀만큼 연결을 쥐고 있다
- 연결 합계의 최대값은 (hpa max + surge) x 최대 풀이고, 실제 점유는 유휴 연결 때문에 최대값에 가깝게 유지된다
- 피해는 공유 자원인 RDS 연결을 다른 서비스가 얻지 못할 때 나타난다. 유휴 연결을 줄이면 같은 최대 풀에서도 평소 점유가 내려가 재시작하는 서비스가 쓸 여유가 생긴다

## 대안 비교

| 항목 | A. 최소 유휴 연결 축소 | B. RDS Proxy | C. RDS 인스턴스 상향 |
|---|---|---|---|
| 효과 | 평소 점유를 파드당 최대 풀에서 2로 줄인다. 최대 연결 합계(상한)는 그대로여서 버스트가 겹치면 상한은 같다. 재시작 시점의 여유를 늘린다 | 앱 연결을 다중화해 DB 쪽 연결 수를 크게 줄인다. 상한 자체를 흡수하므로 효과가 가장 크다(추정) | `max_connections`가 인스턴스 메모리에 비례해 커진다. 상한을 올릴 뿐 낭비 구조는 그대로다 |
| 비용 | 추가 비용 없음 | 프록시는 DB 인스턴스 vCPU당 시간 요금이다. 월 비용 = vCPU 수 x 시간당 단가 x 730시간. db.t4g.medium은 2 vCPU이므로 2 x 단가 x 730이다. 단가는 AWS 공개 가격표(RDS Proxy 요금 페이지) 기준 추정이며 이 기록에서는 조회하지 않았다 | 한 단계 위 인스턴스의 시간 요금 차이만큼 증가한다(추정, AWS RDS 요금 페이지 기준). 이 기록에서는 조회하지 않았다 |
| 운영 부담 | 값 3줄과 CI 규칙 1개 | 프록시, IAM 인증 또는 시크릿 연동, 엔드포인트 교체, 모니터링 추가. 고정(pinning)이 생기면 다중화 효과가 줄어 점검이 필요하다(추정) | 변경 시 재부팅 또는 장애 조치 구간이 생긴다(추정) |
| 위험·부작용 | `minimumIdle`이 작으면 버스트 때 연결을 새로 여는 지연이 조회 지연에 더해진다. 재시작 직후 첫 요청이 느릴 수 있다 | 프록시 경유로 요청마다 지연이 늘 수 있다. 접속 엔드포인트가 바뀌어 롤백 경로가 길다 | 비용이 구조 문제를 덮는다. 이후 풀 상향이 다시 상한에 닿는다 |
| 앱 코드 필요 여부 | 불필요(환경 변수) | 불필요하나 접속 주소 변경 필요 | 불필요 |
| 선택 이유 | 선택. 비용이 없고 원인(유휴 연결 점유)을 직접 줄인다. 값 3줄이라 롤백이 쉽다 | 버림. 효과는 크지만 vCPU 기준 상시 비용과 엔드포인트 변경이 이 실험 범위에 비해 크다. 이 단계에서 최소 안이 기준을 넘지 못하면 다음 후보로 남긴다 | 버림. 상한만 올리고 낭비 구조가 남는다. 비용이 상시 증가한다 |

비용과 운영 부담 수치는 공식 자료로 확인하지 않은 추정이다. 결정적 이유로 다른 안이 우월한 비교 결과는 나오지 않았다.

## 검증 기준

실험 전에 정하고 바꾸지 않는다.

- 같은 주입값 N에서 `s1p step4` 3회 모두 RDS 연결 합계 최대값이 RDS 상한의 80% 아래다
- 3회 모두 auth 재시작 뒤 로그인 경로 `ServiceErrorHigh`가 울리지 않는다
- 조회 p95 증가가 기준선(단계 3 이전 같은 N의 중앙값)의 120% 이하다
- 하나라도 어긋나면 그대로 기록하고 효과 부분 달성 또는 미달로 판정한다

## 결과

단계 실험 뒤 채운다.

측정값(3회, 중앙값과 최소~최대), 판정, 검증 기준을 못 넘은 항목은 그대로 적는다.
