# 결정 기록: S1' 단계 3 영향 범위 카나리

## 근거

개선 전 실험(s1p-before) 측정 뒤 채운다.

채울 항목은 core 풀 값 상향 배포가 카나리 분석(오류율, 재시작)을 통과한 기록과, 그 뒤 다른 서비스(auth) 재시작 때 RDS 연결이 고갈되어 로그인 경로 오류가 난 시각, 기록 경로다.

설계 단계에서 확인한 사실은 다음과 같다.

- 1차의 카나리 분석은 core 오류율과 core 재시작만 본다. core 카나리가 연결을 더 잡아도 core 자신은 정상이라 통과한다
- 피해는 공유 자원인 RDS 연결을 나눠 쓰는 다른 서비스가 재배포될 때 나타난다. 카나리 시점에는 증상이 없다
- 1차에서 트래픽이 없을 때 비율이 NaN이 되어 정상 배포가 중단된 적이 있다(2026-11-23 리비전 4). 새 지표도 데이터가 없을 때 값을 돌려주고 빈 결과를 통과로 보아야 한다

## 대안 비교

| 항목 | A. 카나리에 공유 자원 지표 추가 | B. 배포 직후 합성 점검과 Argo CD 롤백 훅 | C. 수동 승인 단계 |
|---|---|---|---|
| 효과 | 카나리 50% 단계에서 전체 연결 수가 `rdsMax - reserve`를 넘으면 자동 중단한다. 사용자 영향이 생기기 전에 막는다 | 배포 직후 점검 호출이 실패하면 롤백한다. 점검이 연결 여유를 직접 보지 못하면 다른 서비스 재시작 전에는 통과한다 | 사람이 지표를 보고 승인한다. 판단은 정확할 수 있으나 승인 시점이 늦거나 놓치면 효과가 없다 |
| 비용 | 추가 비용 없음 | 점검 잡 실행 자원(추정) | 추가 비용 없음, 사람 시간 소모 |
| 운영 부담 | 차트 값 3개와 지표 규칙. `rdsMax`를 Prometheus 규칙·CI 상수와 맞춰야 한다 | 점검 스크립트와 훅 유지, 점검 항목이 서비스마다 다르다(추정) | 승인 대기로 배포가 지연되고 야간·휴일에 막힌다 |
| 위험·부작용 | 지표 공백이나 NaN 때 오판 위험이 있어 `or vector(0)`와 빈 결과 통과로 처리한다. `reserve` 계산이 어긋나면 정상 배포를 중단한다 | 훅 실패가 롤백 루프를 만들 수 있다. 연결 고갈이 지연 발현이면 놓친다 | 승인자가 습관적으로 승인하면 통제가 되지 않는다 |
| 앱 코드 필요 여부 | 불필요 | 불필요(점검 대상 경로가 있으면) | 불필요 |
| 선택 이유 | 선택. 비용이 없고 1차 구조(분석 단계)에 값만 더한다. 원인 지표를 직접 본다 | 버림. 연결 여유를 직접 보지 못하고 훅 운영 대상이 늘어난다 | 버림. 자동 중단이 되지 않고 사람 의존이다 |

비용과 운영 부담 수치는 공식 자료로 확인하지 않은 추정이다.

## 검증 기준

실험 전에 정하고 바꾸지 않는다.

- `s1p step3` 3회 모두 core 카나리가 `db-connection-headroom` 실패로 자동 중단된다
- 이어지는 auth 재시작 시점에 core가 원래 풀로 돌아가 있고, 로그인 경로 `ServiceErrorHigh`가 울리지 않는다
- 하나라도 어긋나면 그대로 기록하고 효과 부분 달성 또는 미달로 판정한다
- 병합 직후 트래픽이 없는 상태의 무변경 재시작에서는 분석이 통과해야 한다(오탐 확인)

## 결과

단계 실험 뒤 채운다.
