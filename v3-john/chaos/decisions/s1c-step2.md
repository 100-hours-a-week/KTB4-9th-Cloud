# 결정 기록: S1' 단계 2 제출 경로 격벽

## 근거

(개선 전 실험 `s1c-before` 3회 뒤 문제 조회·major-core 5xx, core 대기, 영향 범위 값을 채운다)

설계 단계에서 잰 값:

| 항목 | 값 | 출처 |
|---|---|---|
| 기준선 제출 동시 요청(Envoy 2대 합) | p50 1~3, p95 3~7, 최대 8 | `envoy_cluster_upstream_rq_active`, base-3·base-4 구간 |
| 기준선 제출 동시 요청(Envoy 한 대) | p95 2~5, 최대 6 | 같은 지표 |
| 채점 워커 중단 중 제출 동시 요청(한 대) | 최대 17(15초 표본) | 사전 측정 풀 10 |
| core 풀 합 | 2파드 x 10 = 20(HPA 최대 3파드면 30) | core 값 파일 |
| Envoy 레플리카 | 2(고정, HPA 없음) | `EnvoyProxy prod` |

채점이 멈추면 제출이 core 풀 20을 넘게 요청하고(17 x 2대), 같은 풀을 쓰는 문제 조회·major-core가 연결을 못 얻는다.

## 대안 비교

| 항목 | A. 게이트웨이 회로 차단기(선택) | B. 앱 안 제출 전용 풀 또는 세마포어 | C. 제출 경로 시간 제한 단축 |
|---|---|---|---|
| 효과 | 제출이 동시에 core에 닿는 수를 Envoy 한 대당 8로 묶는다. 넘친 제출은 core에 닿지 않아 연결을 쥐지 않는다. 다른 경로 몫(최소 4)이 남는다 | 제출이 쓰는 연결 수를 앱 안에서 정확히 묶는다. 가장 정확하다 | Envoy가 기다림을 끊어도 앱 스레드는 계속 연결을 쥔다(Envoy 시간 제한은 서버 처리를 취소하지 않는다). 효과 없음 |
| 비용 | 없음 | 개발 시간 | 없음 |
| 운영 부담 | 값 하나. Envoy 레플리카를 바꿀 때 합계 상한이 함께 바뀐다 | 백엔드 팀 변경과 배포 | 값 하나 |
| 위험·부작용 | 평상시 최대 동시 6을 넘는 순간(트래픽 급증)에 정상 제출도 503을 받는다. 상한이 Envoy 대수에 비례 | 앱 변경 위험, 인프라 담당 범위 밖 | 정상 제출(평상시 p95 2.4초)을 끊을 위험 |
| 앱 코드 | 불필요 | 필요 | 불필요 |
| 판단 | 선택. 인프라 쪽에서 즉시 넣을 수 있고 연쇄의 고리를 직접 끊는다 | 근본 해법으로 제안만 한다(보고서에 백엔드 제안으로 적는다) | 버림. 연결 점유를 줄이지 못한다 |

값 8을 고른 이유: 평상시 한 대 최대 6보다 커서 거절이 없어야 하고, 두 대 합(16)이 core 풀 합(20)보다 작아야 다른 경로 몫이 남는다. 7~10 사이에서 두 조건을 모두 만족하는 값 중 여유를 둔 8로 정했다.

## 검증 기준

실험 전에 정하고 바꾸지 않는다.

- 평상시 영향: 기준선 부하 5분에서 제출 경로 넘침(`envoy_cluster_upstream_rq_pending_overflow`) 0
- 3회 중앙값으로 문제 조회·major-core 5xx가 개선 전보다 90% 이상 줄어든다
- 3회 중앙값으로 영향 범위(오류 기준을 넘은 경로 수)가 개선 전보다 줄어든다
- 제출 실패 수는 늘 수 있다(격벽이 제출을 먼저 거절). 늘어난 값을 그대로 적는다
