# 결정 기록: S1' 단계 2 제출 경로 격벽

## 근거

개선 전 실험 `s1c-before` 3회(`records/s1c-before-postmortem.md`): 핵심 SLO 유지율 중앙값 0.590(0.574~0.607), 영향 경로 3개(문제 조회, 제출, major-core, 3회 모두), 핵심 5xx 중앙값 3,103, major 5xx 3,815, core 활성 연결 10/10, 대기 최대 중앙값 97(97~146), DB 연결 최대 60~70, 채점 유실 중앙값 913.

설계 단계에서 잰 값:

| 항목 | 값 | 출처 |
|---|---|---|
| 기준선 제출 동시 요청(Envoy 2대 합) | p50 1~3, p95 3~7, 최대 8 | `envoy_cluster_upstream_rq_active`, base-3·base-4 구간 |

| Envoy 레플리카 | 2(고정, HPA 없음) | `EnvoyProxy prod` |

채점이 멈추면 제출이 core 풀 20을 넘게 요청하고(17 x 2대), 같은 풀을 쓰는 문제 조회·major-core가 연결을 못 얻는다.

## 검증 기준

실험 전에 정하고 바꾸지 않는다.

- 평상시 영향: 기준선 부하 5분에서 제출 경로 넘침(`envoy_cluster_upstream_rq_pending_overflow`) 0
- 3회 중앙값으로 문제 조회·major-core 5xx가 개선 전보다 90% 이상 줄어든다
- 3회 중앙값으로 영향 범위(오류 기준을 넘은 경로 수)가 개선 전보다 줄어든다
- 제출 실패 수는 늘 수 있다(격벽이 제출을 먼저 거절). 늘어난 값을 그대로 적는다

## 결과

### 단계 2(격벽만, 3회 `s1c-step2-20261124-1418/1438/1457`): 효과 없음

| 지표 | 개선 전 중앙값 | 단계 2 회차(1/2/3) |
|---|---|---|
| 핵심 SLO 유지율 | 0.590 | 0.590 / 0.607 / 0.607 |
| 영향 경로 수 | 3 | 3 / 3 / 3 |
| 핵심 5xx | 3,103 | 3,905 / 4,234 / 4,106 |
| major 5xx | 3,815 | 5,275 / 6,036 / 5,697 |
| core 대기 최대 | 97 | 143 / 144 / 125 |
| 격벽 넘침(`upstream_rq_pending_overflow`) | - | 0 / 0 / 0 |

검증 기준(문제 조회·major-core 5xx 90% 감소, 영향 범위 감소)을 못 넘었다. 격벽이 한 번도 작동하지 않았다.

원인(1회차 구간 분석):

- 제출 경로를 지나는 동시 요청은 Envoy 합계 5~15로 상한(한 대당 8)에 닿지 않았다
- 반면 core 연결 점유 시간 최대(`hikaricp_connections_usage_seconds_max`)는 30.4초였다. 제출이 채점 결과를 기다리는 동안 연결을 최대 약 30초 쥔다
- 제출 경로에는 경로 제한 시간이 없어 Envoy 기본값 15초가 적용됐다. 5분 동안 제출 732건 중 99건이 Envoy 시간 초과였다(k6 제출 p95도 15.0초)
- 즉 Envoy가 15초에 요청을 끊어 격벽 슬롯을 비운 뒤에도 core는 15초 더 연결을 쥐었다. 게이트웨이가 보는 동시성(5~15)과 백엔드의 실제 점유가 어긋나 격벽이 의미가 없었다
- 바쁜 Tomcat 스레드는 파드당 130개 이상이었고, 그중 대부분은 연결을 기다리는 문제 조회·major-core 요청이었다(Envoy 동시 요청 문제 조회 최대 97, major-core 175)

교훈: 게이트웨이 격벽은 게이트웨이 제한 시간이 백엔드 자원 점유 시간보다 길 때만 백엔드 자원을 지킨다.

### 단계 2b: 제출 경로 제한 시간 35초 정렬

- 변경: `journey-core-submit` HTTPRoute `timeouts.request: 35s`(백엔드 최대 점유 약 30초 + 여유)
- 기대: 격벽 슬롯이 백엔드 점유와 함께 유지되어 제출이 동시에 쥐는 연결이 Envoy 2대 x 8 = 16 이하로 묶인다(core 풀 합 20)
- 부작용: 채점이 멈췄을 때 제출 사용자가 15초 대신 최대 35초 기다린다. 평상시 제출(p95 약 2.4초)에는 영향이 없다
- 검증 기준은 단계 2와 같다(실험 전 고정): 평상시 넘침 0, 문제 조회·major-core 5xx 중앙값 90% 이상 감소, 영향 경로 수 감소. 넘침 수와 제출 실패 수를 함께 적는다
