# 결정 기록: S1' 단계 3 core 풀 재산정과 연결 예산 검사

## 근거

개선 전 실험 `s1c-before` 3회: core 활성 연결 10/10, 대기 최대 중앙값 97, 영향 경로 3개, 핵심 SLO 유지율 중앙값 0.590(`records/s1c-before-postmortem.md`). 단계 2 결과는 실험 뒤 아래 결과 칸에 함께 적는다.

설계 단계에서 잰 값(`records/s1p-pilot.md`):

| 항목 | 풀 10 | 풀 131 |
|---|---|---|
| 채점 워커 중단 중 core 파드당 연결 최대 | 10(가득, 대기 58~88) | 40~41 |
| DB 연결 합 최대 | 70 | 160 |
| 문제 조회·major-core 5xx | 있음 | 0 |

채점이 5분 멈춰도 core 파드가 실제로 쓴 연결은 41 안쪽이었다. 풀을 그만큼 주면 제출이 연결을 쥐어도 다른 경로 몫이 남는다. 반대로 풀을 무작정 키우면(예: 131) HPA 최대와 배포 중 추가 파드까지 합친 최대 연결이 RDS 상한(303)을 넘을 수 있다.

## 값과 예산

- core 풀 40: 측정 최대 41에 가깝게 잡았다. 41을 넘는 수요는 단계 2 격벽이 제출 쪽에서 묶는다
- 예산 계산(CI 규칙 4): core (HPA 최대 3 + 카나리 추가 1) x 40 = 160, auth (2 + 1) x 10 = 30, battle (3 + 1) x 10 = 40, 합 230 ≤ 242(303 x 0.8) → 통과
- 같은 검사에 풀 131을 넣으면 합 594로 실패한다(로컬 실행 확인). 처음 설계의 "풀을 크게 키우는 PR"은 이 검사가 막는다
- main 필수 검사 지정은 저장소 관리자 설정이라 사용자에게 요청한다. 지정 전에는 "검출"까지다

## 검증 기준

실험 전에 정하고 바꾸지 않는다.

- 3회 중앙값으로 문제 조회·major-core 5xx 0, core 연결 대기 최대 0
- DB 연결 합 최대가 242 이하
- 단계 2 격벽 넘침 수가 단계 2 실험보다 줄거나 같다(풀이 커서 제출이 덜 넘친다)
- 단계 2를 유지할지 결과를 보고 여기에 적는다

판정: 통과. 문제 조회·major-core 5xx 0, core 대기 0, DB 연결 최대 108 ≤ 242(3회 모두). 채점 워커가 멈춰도 피해가 제출 경로 하나에 갇혔다.

- 채점 중단 중 core가 실제로 쓴 연결은 파드당 11~13이었다. 풀 10은 수요를 아주 조금 밑돌았고, 그 작은 차이로 대기가 97~146까지 쌓여 다른 경로가 굶었다. 사전 측정(풀 131)의 41은 cordon 방식 측정 조건 차이로 보이며, 40은 측정 수요의 3배 이상 여유다
- 제출 실패와 채점 유실은 그대로다. 채점 워커가 없으면 피할 수 없는 손실이고, 촉발 자체(워커 1개, 스팟 노드 1대)를 없애는 일은 S2'·백엔드 제안으로 넘긴다
- 핵심 SLO 유지율이 크게 오르지 않은 이유: 핵심 묶음에 제출 경로가 들어 있어 제출 오류(초당 약 3건, 핵심 요청의 약 2.5%)만으로 1분 창 기준 0.5%를 넘는다. 이 연쇄의 개선 효과는 영향 경로 수와 경로별 5xx로 판단한다
- 단계 2·2b 유지: 단계 3 뒤에도 넘침 0이라 격벽은 작동할 일이 없었다. 평상시 영향이 없어 보험으로 유지한다
- main 필수 검사 지정(연결 예산 CI)은 저장소 관리자 설정이라 사용자에게 요청한다
