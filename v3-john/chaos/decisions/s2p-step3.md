# 결정 기록: S2' 단계 3 judge-api 이중화

## 근거

개선 전 실험(s2p-before)과 s2p-step2 실험 뒤 채운다.

채울 항목은 회수 구간 채점 유실 3회 값, 제출 p95 3회 값, 회수 노드에 judge-api가 있었는지 여부, 그 기록 경로다. s2p-step2 뒤에도 유실이 남아야 이 단계가 필요하다.

이미 확인한 1차 증거는 다음과 같다.

- 1차 s2-before에서 채점 유실이 57건이었다. judge-api가 레플리카 1개이고 PDB가 없어 노드를 비우는 순간 마지막 파드가 축출됐다. judge-api 복구에 약 2분 30초가 걸렸고 그동안 core의 제출이 `Judge0 연결 실패`로 유실됐다(`v3-john/chaos/records/s2-before-postmortem.md`)
- 1차 s2-step3에서 채점 유실이 38건이었다. 회수 대상 노드에 judge-api(레플리카 1)가 있었다(`v3-john/chaos/records/s2-step3-notes.md`).

## judge-api 상태 비보유 확인

이중화의 전제는 judge-api 파드가 서로 바꿔 쓸 수 있다는 것이다. 읽기 전용으로 확인한 근거는 다음과 같다.

- 이미지 소스는 Judge0이며 저장소는 `KTB4-9th-Judge`다
- 채점 큐: `config/application.rb`의 `queue_adapter = :resque`와 `config/initializers/resque.rb`가 `REDIS_HOST`, `REDIS_PORT`, `REDIS_PASSWORD`로 Redis를 연결한다. `app/controllers/submissions_controller.rb`의 `IsolateRunner.perform_later`가 이 큐에 작업을 넣는다. 값 파일에서 `REDIS_HOST`는 `judge-redis-queue`다
- 제출 저장: `config/database.yml`이 `POSTGRES_HOST` 등으로 PostgreSQL을 연결한다. 값 파일에서 `POSTGRES_HOST`는 `judge-postgres`다
- 실제 채점은 별도 워커가 Redis 큐에서 가져가 수행한다. API 파드는 접수와 조회만 한다
- 파드 안에 남는 것은 `tmp/pids/server.pid` 같은 임시 파일뿐이다. `scripts/server`는 기동 때 `rails db:create db:migrate db:seed`를 실행하므로 두 파드가 동시에 뜨면 마이그레이션이 겹칠 수 있다. 스키마가 이미 최신이면 변경은 없고, 겹침 여부는 이중화 뒤 첫 기동 로그로 확인한다

이 확인은 소스 읽기이며 클러스터 실측이 아니다. 이중화 뒤 두 파드가 모두 접수를 받고 제출 조회가 어느 파드에서든 같은 결과를 내는지는 실험 전 점검에서 확인한다.

## 대안 비교

| 항목 | A. judge-api 이중화와 PDB(선택) | B. 채점 결과 비동기 조회(앱 코드, 제안) | C. judge-api를 온디맨드 노드에 고정 |
|---|---|---|---|
| 효과 | 한 노드가 사라져도 다른 파드가 접수를 받는다. 회수 구간 채점 유실을 0에 가깝게 줄일 것으로 본다(추정). 두 파드가 같은 노드에 몰리면 효과가 없다 | core가 judge-api를 동기로 기다리지 않고 제출을 먼저 저장한 뒤 결과를 나중에 조회한다. judge-api가 잠시 없어도 제출 자체는 유실되지 않는다. 가장 근본적인 대안이다(추정) | 스팟 회수의 영향을 받지 않아 회수로 인한 유실이 사라진다. 온디맨드 노드 자체 장애와 배포 교체 구간은 그대로다(추정) |
| 비용 | 파드 1개 추가. 요청 CPU 250m, 메모리 512Mi. 노드 추가가 필요 없으면 추가 비용 없음 | 개발 시간. 인프라 비용 없음 | 온디맨드 노드 상시 비용. 스팟보다 시간당 높다(금액은 측정하지 않은 추정) |
| 운영 부담 | 값 설정 3줄. 노드 여유와 쿼터 확인이 필요하다 | 상태 모델과 재시도 정책이 늘어 core 운영이 복잡해진다 | 노드 그룹과 taint, 노드 선택 규칙을 따로 관리한다 |
| 위험·부작용 | 파드가 Pending이면 효과가 없다. 기동 시 마이그레이션 겹침 가능성. HPA 최소와 최대가 모두 2라 부하 증가 시 자동 확장이 없다 | 앱 변경으로 회귀 위험이 크다. 이 역할 범위 밖이다 | 단일 파드면 온디맨드 노드에서도 한 지점 장애다. 용량이 작은 노드 그룹에 몰린다 |
| 앱 코드 필요 여부 | 불필요 | 필요(core, 프런트) | 불필요 |
| 선택 이유 | 선택. 값 설정만으로 비용이 작고 되돌리기 쉬우며 상태 비보유라 안전하다 | 버림. 앱 코드가 필요해 이 역할 범위 밖이다. 후속 제안으로 남긴다 | 버림. 상시 비용이 들고 단일 파드 문제를 못 푼다. 후속 후보로 남긴다 |

비용과 효과는 측정하지 않은 추정이다. 대안 B와 C는 이 단계에서 실측하지 않는다.

## 검증 기준

실험 전에 정하고 바꾸지 않는다.

- 회수 대상 노드에 judge-api 하나를 둔 배치에서 3회 중앙값 채점 유실이 0이다
- 제출 p95 증가가 기준선 3회 중앙값의 120% 이하다
- judge-api 파드 둘이 서로 다른 노드에 놓인다. 같은 노드면 그 회차는 배치 재현 실패로 기록하고 판정에서 뺀다
- 한 항목이라도 못 넘으면 효과 없음으로 판정하고 그대로 기록한다

## 쿼터와 노드 여유

단계 3 실험 전에 확인해 채운다(Pending이면 원인과 조치를 함께 적는다).

## 결과

단계 실험 뒤 채운다.
