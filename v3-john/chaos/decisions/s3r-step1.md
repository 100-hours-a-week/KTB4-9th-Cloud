# 결정 기록: 상태 저장 노드 교체 장애 대응(s3r 단계 1)

## 근거

대응 전 재현(계획 교체, 부하 RATE 30):

| 회차 | DB·큐 끊김(인프라) | 핵심 기능 회복(서비스) | 제출 실패 | 사람 개입 |
|---|---|---|---|---|
| 최초 발견(스팟 회수, 19:44) | 약 45초 | 약 47분(수동 재시작 20:31) | 623건 이상 | 필요 |
| repro-1(21:15) | 49초 | 165초 | 165건 | 불필요 |
| repro-2(21:40) | 50초 | 150초 | 155건 | 불필요 |
| repro-3 | 62초 | 150초 | 126건 | 불필요 |

제출 실패는 교체 후 11분 동안의 Envoy 제출 경로 503 증가량이다(보고서 5.1과 같은 기준). 처음 기록한 153/158/125건과 달라 보고서와 같은 기준으로 통일했다.

원인(로그 근거, Loki): 교체 순간 Redis 연결이 끊기면 채점 워커의 채점 프로세스가 `Redis::CannotConnectError`로 죽고(`rake aborted`), 관리 스크립트가 다시 띄운다. 그동안 대기열이 쌓이고, 워커가 1대(KEDA 최소·최대 1)라 따라잡는 데 2분 가까이 더 걸린다. 최초 발견 때는 다시 뜬 뒤 처리 속도가 평소의 약 70%(분당 약 150건 대 200건)에 머물러 대기열을 끝내 따라잡지 못했다. 컨테이너는 Running이라 쿠버네티스는 아무것도 하지 않았다.

## 대안 비교

| 항목 | A. 대응 장치 묶음(선택) | B. Redis·Postgres 이중화(Sentinel·복제) | C. 채점 대기열을 관리형(ElastiCache)으로 |
|---|---|---|---|
| 내용 | 원인 이름 알림(`JudgePathDegraded`), 채점 워커 상시 2대(KEDA 2~3, 채점 노드 2~3), 처리 정지 감지 생존 검사(자동 재시작), 교체 런북 | 대기열·DB 끊김 자체를 없앤다 | 노드 교체와 무관해진다(관리형 장애 조치는 남음) |
| 효과(예상) | 탐지 시간 단축, 회복 시간 단축(대기열을 2대가 처리), 장기 장애를 자동 재시작으로 차단 | 끊김 50초 → 수 초 | 끊김을 노드 교체와 분리 |
| 비용 | 채점 노드 스팟 1대(c5.xlarge 스팟 시간당 약 0.07달러, 추정) | 노드·운영 부담 큼 | cache.t4g.micro 시간당 약 0.02달러(추정) + 이전 작업 |
| 운영 부담 | 낮음(값 파일, Terraform 한 줄, 알림 규칙) | 높음(장애 조치 운영) | 중간(Terraform, 엔드포인트·Secret 변경) |
| 위험 | 생존 검사 오판으로 불필요한 재시작(90초 지속 조건과 Redis 장애 시 통과로 완화) | 설정 오류 시 데이터 불일치 | 이전 중 장애 |
| 앱 코드 | 불필요 | 불필요(클라이언트 설정 변경 필요할 수 있음) | 불필요 |
| 판단 | 선택. 이번 장애의 고리(탐지 지연, 따라잡기 지연, 고장 무시)를 오늘 끊는다 | 후속 과제. 범위가 크다 | 후속 과제로 비용 비교만 남긴다 |

## 검증 기준(실험 전 고정)

같은 계획 교체를 3회 반복해 중앙값으로 판정한다.

- 핵심 기능 회복 시간(`recovery_seconds_core`)이 대응 전 중앙값의 50% 이하
- 제출 실패 건수가 대응 전 중앙값의 50% 이하
- `JudgePathDegraded`가 교체 후 2분 안에 울린다(탐지 시간 기록)
- 사람 개입 0회
- 평상시(교체 없는 구간) 불필요한 채점 워커 재시작 0회

## 결과

### 계획 교체(s3r) 3회: 기준 일부 미달

| 기준 | 대응 전 중앙값 | 대응 후(1/2/3) | 판정 |
|---|---|---|---|
| 핵심 기능 회복 시간 50% 이하 | 150초 | 150초 안팎(변화 없음) | 미달 |
| 제출 실패 50% 이하 | 155건 | 172 / 108 / 178건 | 미달 |
| `JudgePathDegraded` 2분 안 | - | 120 / 105 / 120초 | 통과 |
| 사람 개입 0회 | 0 | 0 | 통과 |
| 평상시 불필요한 재시작 0회 | - | 0 | 통과 |

- 정정: "회복 150초"는 1분 창 오류율과 1분 유지 조건이 만든 측정 지연이었다. 15초 단위로 다시 재면 실제 실패 구간은 DB·큐 끊김(50~62초)과 같은 약 1분이다. 이 1분은 단일 레플리카 DB·큐가 옮겨지는 동안의 손실이라 이번 대응으로 줄지 않는다. 기준 두 개의 미달은 이 때문이며 대안 B·C(이중화, 관리형)가 다룰 영역이다
- 계획 교체 3회 모두 장기 장애가 다시 나지 않아, 대응의 핵심 목표(장기 장애 차단)는 아래 채점 워커 정지 실험으로 검증했다

### 채점 워커 정지(s3w): 장기 장애 차단 검증

장기 장애 상태(살아 있지만 일을 못 하는 워커)를 SIGSTOP으로 600초 주입했다. 600초 뒤 재개가 사람 개입에 해당한다. 각 3회.

| 구성 | 회복까지 | 제출 실패(503) | 사람 개입 |
|---|---|---|---|
| 원래 구성(KEDA 1/1, 생존 검사 없음) | 회복 안 됨(재개 뒤 645/660/660초) | 1,816 / 1,830 / 1,850 | 필요 |
| 자동 확장만(KEDA 2~3, 생존 검사 없음) | (90) / 285 / 285초 | 171 / 761 / 787 | 불필요 |
| 대응 후(KEDA 2~3 + 생존 검사) | 180 / 180 / 180초 | 432 / 388 / 416 | 불필요 |

- 원래 구성 대비 회복 "사람 개입 전까지 지속" → 3분 자동 회복, 제출 실패 중앙값 -77%
- 자동 확장만으로도 새 워커가 일을 대신해 회복했다. 생존 검사는 멈춘 워커 자체를 고쳐 여유 대수와 무관하게 동작하고, 회복을 105초 앞당겼다
- 자동 확장만 1회차(90초)는 세 번째 워커가 주입 직전에 이미 뜨는 중이라 제외했다
- 판정: 장기 장애 차단 목표 통과. 평상시 1분 중단은 남은 위험으로 넘긴다
- 한계: 생존 검사는 처리가 완전히 멈춘 워커만 잡는다. 실제 47분 장애처럼 처리가 느려진(약 70%) 상태나 두 프로세스 중 하나만 멈춘 상태는 자동 확장과 `JudgePathDegraded`가 맡는다. 채점 Postgres 불통은 예외 처리하지 않아 재시작 반복이 가능하다(보고서 5.2)
