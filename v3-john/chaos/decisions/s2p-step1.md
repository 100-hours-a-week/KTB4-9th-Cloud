# 결정 기록: S2' 단계 1 종료 정리

## 근거

개선 전 실험 3회(`records/s2a-before-postmortem.md`, 회차 s2-r2-before-20261124-1804 / 1832 / 1917): 회수 구간 제출 5xx 24 / 측정 불가 / 38, 문제 조회 5xx 2 / - / 0, Envoy 처리 중 끊긴 연결 4 / - / 1, k6 요청 실패율 0.167% / 0.175% / 0.173%. 1832 회차는 Prometheus가 26분 동안 뜨지 못해 서버 측 지표가 없다.

관찰: 관리형 노드 그룹이 회수 알림 약 80초 뒤 노드를 cordon·drain한다(1917 회차 19:21:13 알림 → 19:22:33 cordon). 파드는 정상 종료 경로(SIGTERM)를 밟지만 앱에 정상 종료 설정이 없어 진행 중 요청이 끊긴다.

2026-11-24 진행 결정: 시간 제약으로 단계 1(종료 정리)과 단계 2(게이트웨이 재시도)를 한 단계로 묶어 함께 적용하고 3회 잰다. 판정은 단계 1의 기준(5xx와 k6 실패 20% 이하)으로 하고, 재시도 동작 여부는 단계 2의 기준(`upstream_rq_retry` 증가)으로 따로 적는다.

대안으로 Node Termination Handler(회수 알림 즉시 drain)도 검토했다. 관리형 노드 그룹이 이미 알림 +80초에 비우므로 얻는 것은 비우기 시작을 80초 당기는 것뿐이라 넣지 않았다(브랜치 `feat/v3/john-r2-nth`).

이미 확인한 1차 증거는 다음과 같다.

- 1차 실험 s2-step3의 회수 구간에서 핵심 5xx가 33/9,861건이었다(`v3-john/chaos/records/s2-step3-notes.md`). 회수 노드에 judge-api와 Envoy 두 개가 모두 있었고, Envoy가 사라진 동안 실패한 요청은 Envoy 지표에 잡히지 않아 실제 값은 더 클 수 있다
- 파드가 종료될 때 엔드포인트 제거와 SIGTERM이 거의 동시에 일어나 아직 제거가 전파되지 않은 연결로 요청이 들어갈 수 있다. 앱이 진행 중 요청을 마치지 않고 끝나면 그 요청도 5xx가 된다
- 현재 Spring 3개 서비스는 종료 설정이 기본값이라 즉시 종료한다

## 대안 비교

|---|---|---|---|
| 효과 | 엔드포인트 제거가 전파된 뒤 SIGTERM을 받고, 진행 중 요청을 마친 뒤 종료한다. 종료로 인한 연결 거부와 중단을 원인에서 줄인다. 노드 회수로 노드가 통째로 사라지는 경우는 막지 못한다 | 죽은 업스트림을 수 초 안에 제외한다. 종료 파드와 사라진 노드 모두에 효과가 있다. 정상 종료 중 진행 요청 보호는 못 한다 | 실패한 요청을 다시 보내 사용자 오류를 줄인다. 원인은 그대로이고 재시도가 쓰는 시간과 부하가 늘어난다. 멱등하지 않은 요청은 재시도가 위험하다 |
