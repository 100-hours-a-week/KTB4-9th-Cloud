# 결정 기록: S1' 단계 2 연결 예산 검사

## 근거

개선 전 실험(s1p-before) 측정 뒤 채운다.

채울 항목은 개선 전 실험에서 core 풀 값을 올린 PR이 CI를 통과해 병합된 기록과, 그 뒤 RDS 연결 수가 예산을 넘은 시각, 기록 경로다.

설계 단계에서 확인한 사실은 다음과 같다.

- 값 파일의 `SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE`는 서비스별 값이라 리뷰어가 RDS 전체 연결 한도와 비교하기 어렵다. 최대 연결 수는 (hpa 최댓값 + 배포 중 추가 파드) x 풀 크기의 합이며 롤아웃 방식에 따라 추가 파드 수가 달라진다
- 기존 CI는 메모리 설정만 검사한다. 연결 수는 사람이 계산해야 하고, 단계 1의 알림은 문제가 난 뒤에야 울린다

## 대안 비교

| 항목 | A. CI 값 검사 | B. 클러스터 입장 정책(Kyverno 등) | C. 검사 없이 RDS Proxy로 상한 흡수 |
|---|---|---|---|
| 효과 | 풀 값을 올리는 PR이 병합 전에 "연결 예산" 사유로 실패한다. 병합 전 차단이라 장애 자체를 막는다 | 클러스터에 적용되는 시점에 거부한다. 병합 뒤에도 Argo CD 동기화가 실패하므로 우회 병합도 막는다 | 앱이 만드는 연결 수와 무관하게 RDS 쪽 연결은 Proxy가 모은다. 풀 값 실수 자체는 막지 못하고 증상만 흡수한다 |
| 비용 | 추가 비용 없음 | 추가 비용 없음(컨트롤러 파드 자원은 소모, 추정) | Proxy 요금이 vCPU당 시간 단위로 붙는다(추정) |
| 운영 부담 | 스크립트 1개와 테스트. 한도 상수를 RDS 실측값과 맞춰야 한다 | 컨트롤러 설치와 정책 업그레이드를 관리한다. 서비스 간 합계를 정책 하나로 계산하기 어렵다(추정) | Proxy 설정, 인증, 고정 세션 확인이 필요하다 |
| 위험·부작용 | main 필수 검사가 아니면 우회 병합이 가능하다. 한도 상수가 어긋나면 오판한다 | 정책 오류가 모든 배포를 막을 수 있다. 입장 시점은 파드 단위라 전체 합계 검사에 부적합하다 | 풀 고갈 지연이 Proxy 대기로 옮겨질 뿐이다. 단계 4의 연결 구조 개선과 겹친다 |
| 앱 코드 필요 여부 | 불필요 | 불필요 | 엔드포인트 변경만 필요하며 코드는 불필요(추정) |
| 선택 이유 | 선택. 비용이 없고 병합 전에 막으며 GitOps 저장소 값만으로 계산된다 | 버림. 서비스 간 합계를 계산하기 어렵고 운영 대상이 늘어난다 | 버림. 원인을 없애지 못하고 비용이 든다. 단계 4에서 별도 대안으로 비교한다 |

비용과 운영 부담 수치는 공식 자료로 확인하지 않은 추정이다.

## 검증 기준

실험 전에 정하고 바꾸지 않는다.

- S1' 주입 PR이 GitOps CI에서 "연결 예산" 사유로 실패한다
- main 필수 검사가 지정되면 병합이 거부된다
- 필수 검사가 지정되지 않아 우회 병합이 가능하면 CI 실패 기록은 남기되 효과 부분 달성으로 판정한다. 둘 중 하나라도 어긋나면 그대로 기록한다
