# 결정 기록: S1' 단계 1 연결 알림

## 근거

개선 전 실험(s1p-before) 측정 뒤 채운다.

채울 항목은 개선 전 실험의 탐지 시간 3회 값, 원인 서비스를 맞힐 때까지 걸린 시간 3회 값, 그 기록 경로다.

설계 단계에서 확인한 사실은 다음과 같다.

- 사용자가 먼저 겪는 증상은 auth 로그인 실패다. 그러나 원인은 core의 Hikari 풀 값을 올린 PR이 RDS 연결을 더 쥐게 만든 것이다. 증상이 나는 서비스와 원인 서비스가 다르다
- 1차 실험의 S1(잘못된 배포)에서 증상 알림만으로는 원인 서비스를 정하기 어려웠다. 원인은 파드 상태와 배포 이력을 사람이 뒤져서 찾았다. 연결 수 합계와 서비스별 분해가 알림에 없으면 같은 탐색을 반복한다
- 앱 전체 연결 수는 이미 `cosmos:db_connections:sum`으로 모으고 있다. 지표 수집 비용 없이 알림 규칙과 경로만 추가하면 된다

## 대안 비교

| 항목 | A. Hikari 지표 합(Prometheus) | B. CloudWatch `DatabaseConnections` 알람 | C. RDS Performance Insights |
|---|---|---|---|
| 효과 | 앱 연결 합계가 예산 80%를 넘으면 1분 안에 알림. `by (app)`으로 원인 서비스까지 분해 가능. 풀 대기 시간 초과도 직접 잡는다 | RDS가 보는 전체 연결 수를 잡는다. 앱이 아닌 클라이언트의 연결도 포함. 서비스별 분해는 불가 | 대기 이벤트와 세션 단위 부하를 본다. 연결 수 임계 알림 용도가 아니라 사후 분석 도구 |
| 비용 | 추가 비용 없음(이미 수집 중인 지표) | 지표는 무료, 알람 1개 월 약 0.1달러(추정) | 기본 7일 보존은 무료, 장기 보존은 유료(추정) |
| 운영 부담 | 규칙 2개와 경로 1개. 코드 검사 스크립트가 있다 | Terraform 알람과 SNS 또는 Discord 연동을 따로 관리. Alertmanager와 경로가 이원화된다 | 콘솔에서 사람이 조회해야 한다. 자동 알림 경로가 없다 |
| 위험·부작용 | 분모 300은 RDS 실측 전의 자리 표시 값이므로 실측 값 반영 전에는 판정이 어긋날 수 있다. Prometheus가 죽으면 알림도 멈춘다 | 수집 주기가 1분이고 지연이 있다. 서비스 구분이 없어 원인 서비스 판단은 여전히 사람 몫이다 | 없음. 단 알림이 아니므로 탐지 시간을 줄이지 못한다 |
| 앱 코드 필요 여부 | 불필요(Hikari 지표는 이미 노출 중) | 불필요 | 불필요 |
| 선택 이유 | 선택. 탐지와 원인 서비스 특정을 한 번에 줄이고 추가 비용이 없다 | 버림. 서비스별 분해가 없어 이 단계의 목표(원인 서비스 특정)를 못 채운다. 전체 합 보조 신호로는 쓸 수 있어 런북 확인 절차에만 넣는다 | 버림. 알림이 아니라 분석 도구다. 사후 원인 확인용으로 런북에 언급하지 않는다 |

비용 수치는 공식 가격표로 확인하지 않은 값이라 모두 추정이다.

## 검증 기준

실험 전에 정하고 바꾸지 않는다.

- 3회 중앙값 기준 `RdsConnectionBudgetHigh` 또는 `DbConnectionAcquireFailed`가 `CoreBurnFastAll`과 `ServiceErrorHigh`보다 먼저 울린다
- 대응 기록에서 원인 서비스(core 풀)를 맞힐 때까지 걸린 시간의 3회 중앙값이 개선 전 중앙값보다 짧다
- 두 조건 중 하나라도 못 넘으면 효과 없음으로 판정하고 그대로 기록한다

## 결과

단계 실험 뒤 채운다.
