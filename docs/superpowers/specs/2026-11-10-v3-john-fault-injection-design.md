# v3-john 장애 주입과 장애 대응 설계

작성일: 2026-11-10 · 수정일: 2026-11-11 · 대상: `v3-john` 훈련 클러스터 · 기간: 6주

## 1. 목적

운영에서 터질 약점을 장애 주입으로 먼저 찾고, 고친 뒤 같은 실험으로 개선을 수치로 증명한다. 모든 도구 도입은 "실험에서 드러난 문제 → 대안 비교 → 선택 → 같은 실험으로 재측정" 순서를 따른다.

장애 주입만 하지 않고, 실제 기업이 운영하는 장애 대응 체계(심각도 등급, 역할, 대응 순서, 포스트모템, 에러 예산 정책)를 이 환경에 맞게 만들어 모든 실험에 똑같이 적용한다. 체계의 기준과 숫자에는 출처나 SLO에서 계산한 근거를 붙인다(15장). 결과물은 실험 기록, 포스트모템, 전후 비교 수치, 운영 도구다.

## 2. 제약

- v3-john은 작업할 때만 `up.sh`로 띄우고 `down.sh`로 내린다. 모든 도구와 실험은 `up.sh` 한 번으로 재현되어야 하고, 실험 결과와 장애 기록은 S3와 문서로 남긴다.
- 수정은 인프라, 설정, 운영 도구만 한다(Helm 값, 환경 변수, 쿠버네티스 리소스, Istio 정책, Discord 장애 봇, Cloud 저장소 워크플로). 예외는 Judge(Rails)의 OTel gem 추가 하나다. 앱 코드 수정이 필요한 문제는 개선 제안으로만 기록한다.
- Spot vCPU 한도는 32개이고 한도 증가는 요청하지 않는다. 현재 노드는 system 1대(2 vCPU), stateful 1대(2), judge 1대(4), application 2대(8)로 16 vCPU다. 개선 후 최대치는 application 3대, judge 3대로 28 vCPU다.
- v3-john은 실제 Gemini API를 호출하지 않는다. ai-llm은 환경 변수 `GOOGLE_GEMINI_BASE_URL`로 클러스터 안의 가짜 Gemini 서버를 본다. Gemini SDK(`google-genai`)가 이 변수를 기본 접속 주소로 쓰므로 앱 코드는 바꾸지 않는다.
- 승격 파이프라인(`v3-promote`)이 `v3-john` 값 파일을 자동으로 고치므로, 실험용 변경은 값 파일의 `image`, `sourceRevision` 줄을 건드리지 않는다.
- 대응자는 한 명이다. 기업에서 여러 사람이 나눠 맡는 역할을 한 사람이 체크리스트로 수행하고, 이 한계를 보고서에 적는다.

## 3. 현재 구조에서 확인한 사실

- 동기 HTTP 호출: Spring(core, auth, battle) → `ai-llm-service`, `judge-api-service` / AI(ai-llm, ai-make-problem, ai-problem-batch) → `core-service`, `judge-api-service`. core와 AI가 서로 호출한다.
- 비동기: judge-api → `judge-redis-queue` → judge-worker(KEDA 확장), judge-postgres.
- 언어: Java(Spring), Python(FastAPI), Ruby(Rails).
- 모든 앱 Deployment는 HPA 최소 1개다. 차트에 PodDisruptionBudget이 없다. application 노드 그룹은 min=max=2라 여유 노드가 없다.
- 채점 용량은 고정이다. KEDA ScaledObject가 `minReplicaCount: 1`, `maxReplicaCount: 1`이고, judge 노드 그룹은 min=max=1(4 vCPU)이며, worker는 CPU 2개를 요청하고 `COUNT: 2`로 동시에 2건만 채점한다.
- 진입점: EnvoyProxy가 `replicas: 1`이다. 이 파드 하나가 죽으면 모든 외부 요청이 끊긴다.
- DNS: CoreDNS는 EKS 애드온으로 2개가 뜨지만 system 노드가 1대라 같은 노드에 있다.
- 데이터 저장소:
  - RDS MySQL은 단일 AZ이고 `backup_retention_period = 0`, `skip_final_snapshot = true`다. 특정 시점 복원을 할 수 없다.
  - judge-redis는 `--appendonly yes`, 5Gi 볼륨 1개다.
  - judge-postgres, ai-postgres는 30Gi 볼륨 1개씩이고 클러스터 안에 백업이 없다.
  - 세 저장소 모두 v3-john 안에서 되살릴 수단이 시드 데이터뿐이다.
- 배포: prod ApplicationSet은 auth, core, battle, ai-llm, ai-make-problem, ai-problem-batch를 자동 동기화하고, judge-api, judge-worker는 운영자가 Sync한다. `selfHeal`은 꺼져 있다. 배포된 환경은 `prod` 하나다.
- 관측: Prometheus, Alertmanager(Discord 웹훅), Loki, Alloy, Grafana가 있다. 트레이스와 SLO 알림은 없다. 배포 이벤트가 대시보드에 표시되지 않는다.

## 4. 접근 방식

가설 기반 2단계 비교를 택한다. Istio를 먼저 설치하는 방식은 도입 전 수치가 없어 개선을 증명할 수 없고, AWS FIS만 쓰는 방식은 서비스 구간 장애 표현력이 약해 기각했다.

| 단계 | 내용 | 다음 단계로 가는 조건 |
|---|---|---|
| 0. 기준선 | SLO, k6 사용자 시나리오, RED 대시보드, SLO 알림, 실험 기록 양식 | 기준선 수치 3회 측정 완료 |
| 0. 대응 체계 | 심각도 매트릭스, 역할 체크리스트, Discord 장애 봇, 포스트모템 양식 | 시험 실험 하나가 알림 → 봇 스레드 → 포스트모템 초안까지 이어짐 |
| 1. 현재 구조 실험 | E1~E13 실행, 대응, 포스트모템 | 13개 기록 완료 |
| 1. 개선 | 9장의 설정 개선, 자동 롤백, 속도 제한, 에러 예산 정책. 해당 실험 재측정 | 개선마다 전후 비교 기록 |
| 2a. 트레이스 | OTel + Tempo 도입 후 E5 재실행 | E5 원인 파악 시간 10분 초과 |
| 2b. Istio | Istio 도입 후 E4, E5, E8 재실행 | E4 또는 E8에서 핵심 기능 가용성이나 조회 지연 목표 위반 |

2a, 2b는 조건을 넘지 못하면 도입하지 않고 "검토 후 미도입" 결과로 기록한다.

## 6. SLO

v3-john은 작업할 때만 켜고 트래픽은 k6가 만든다. 따라서 목표와 에러 예산은 "운영이라면 이렇게 둔다"는 가정이고, 실험의 합격 여부는 실험 구간 안의 수치로 판정한다. 에러 예산 기간은 에러 예산 정책(9.4)과 같은 **최근 4주**로 통일한다.

### 6.1 기능 묶음과 목표

가용성은 `/api` 전체가 아니라 기능 묶음별로 나눈다. 묶음은 Envoy Gateway 라우트 경로로 구분하고 `journey` 라벨로 기록한다. 하나로 합치면 AI 실패가 섞여 "AI만 실패하고 핵심 기능은 멀쩡하다"는 가설(E4, E8)을 판정할 수 없다.

| 묶음 | 기능 (BE 컨트롤러) | 이 묶음인 이유 |
|---|---|---|
| 핵심 | 로그인(`Auth`), 문제 조회(`Problem`, `DailyProblem`), 코드 제출과 채점(`CodeSubmission`) | 서비스의 본래 가치인 "문제를 풀고 채점받기"다. 이게 안 되면 서비스가 없는 것과 같다 |
| 주요 | 배틀(`DailyBattle`), 랭킹(`Ranking`), 알림(`Sse`, `Notification`), 활동 기록(`ActivityRecord`) | 핵심 흐름이 살아 있으면 잠시 늦거나 실패해도 나중에 따라잡을 수 있다 |
| 부가 | AI 힌트(`Hint`), 풀이 평가(`ApproachSubmission`, `SolutionEvaluation`), 문제 생성 배치 | 외부 LLM에 의존하고, 없어도 문제 풀이는 할 수 있다 |

| SLO | 지표 | 목표 | 판정에 쓰는 실험 |
|---|---|---|---|
| 핵심 기능 가용성 | 핵심 묶음 요청 중 5xx가 아닌 비율 | 99.5% | E1, E3, E4, E5, E6, E8, E9, E11, E12 |
| 주요 기능 가용성 | 주요 묶음 요청 중 5xx가 아닌 비율 | 99% | E1, E3, E12 |
| AI 기능 가용성 | 부가 묶음 요청 중 5xx가 아닌 비율 | 95% | E4, E8, E9 |
| 조회 지연 | 로그인, 문제 조회 p95 | 기준선 p95의 2배 이하 | E4, E5 |
| 제출 지연 | `POST /api/submissions` p95 | 1초 이하 | E5, E7 |
| 채점 처리 | 제출부터 결과 조회 성공까지 p95 (k6 측정) | 30초 이하 | E2, E5, E7, E10, E13 |
| 채점 완료율 | k6가 보낸 제출(속도 제한으로 거절된 것 제외) 중 결과를 받은 비율 | 100% | E2, E7, E13 |

- 주요 기능 99%는 핵심(99.5%)보다 낮고 부가(95%)보다 높다. 실패해도 나중에 회복할 수 있어 핵심보다 낮추고, 외부 의존 없이 우리 서비스 안에서 처리하므로 부가보다 높인다. 이 값은 서비스 구조에서 추론한 값이다.
- AI 기능은 외부 LLM에 의존하므로 목표를 낮게 둔다. 대신 AI 실패가 핵심 기능으로 번지면 안 된다.
- 지연 목표는 기준선 3회를 잰 뒤 확정한다. 조회 지연은 기준선 p95의 2배로 정하고, 제출 지연 1초와 채점 처리 30초는 기준선 p95가 이를 넘으면 기준선 p95의 1.5배로 바꾸고 이유를 기록에 남긴다.
- 채점 완료율은 제출 후 5분 안에 결과를 받지 못하면 유실로 센다.
- 속도 제한(9.3)이 돌려주는 429는 5xx가 아니므로 가용성을 깎지 않는다. 대신 거절률을 따로 잰다.

### 6.2 에러 예산과 알림

- **에러 예산**: 목표가 99.5%이면 요청의 0.5%까지는 실패해도 된다. 4주는 40,320분이므로 핵심 기능이 완전히 멈춰도 되는 시간은 4주에 약 200분이다.
- **소진 속도**: 지금 에러 비율이 허용 비율의 몇 배인지다. 1배면 4주에 예산을 딱 다 쓰고, 14.4배면 약 2일 만에 다 쓴다.
- **예산 소진량**: 장애 한 건이 4주 예산 중 몇 %를 썼는지다. `소진량 = (실패 비율 × 지속 시간) ÷ 4주 허용 실패 시간`으로 계산한다.

| 장애 예 (핵심 기능) | 계산 | 소진량 |
|---|---|---|
| 30분 동안 완전히 멈춤 | 30분 × 100% ÷ 200분 | 15% |
| 30분 동안 10% 실패 | 30분 × 10% ÷ 200분 | 1.5% |
| 1시간 동안 7.2% 실패 | 60분 × 7.2% ÷ 200분 | 약 2% |

알림은 탐지 시간을 재고 심각도를 제안하는 용도다. 각 알림의 `severity` 라벨은 7.3 매트릭스에서 가져온다.

| 알림 | 조건 | 같은 뜻의 에러 비율 | 제안 등급 |
|---|---|---|---|
| `CoreUnavailable` | 최근 5분 핵심 기능 성공 비율 50% 미만 | 5분 동안 50% 넘게 실패 | SEV1 |
| `CoreErrorBudgetBurnFast` | 최근 5분과 최근 1시간 모두 14.4배 초과 | 5분 동안 7.2% 넘게 실패 | SEV2 |
| `CoreErrorBudgetBurnPage` | 최근 1시간 14.4배 초과 | 1시간 동안 7.2% 넘게 실패 | SEV2 |
| `CoreErrorBudgetBurnTicket` | 최근 6시간 6배 초과 | 6시간 동안 3% 넘게 실패 | SEV3 |
| `MajorUnavailable` | 최근 5분 주요 기능 성공 비율 50% 미만 | 5분 동안 50% 넘게 실패 | SEV2 |
| `MajorErrorBudgetBurnFast` | 최근 5분과 최근 1시간 모두 14.4배 초과 | 5분 동안 14.4% 넘게 실패 | SEV3 |
| `AiErrorRateHigh` | 최근 5분 AI 기능 에러 비율 5% 초과 | 같음 | SEV3 |
| `SubmissionLatencyHigh` | 제출 p95가 목표 초과 상태로 5분 지속 | - | SEV2 |
| `JudgeTurnaroundHigh` | 채점 처리 p95가 목표 초과 상태로 5분 지속 | - | SEV2 |
| `ReadLatencyHigh` | 조회 p95가 목표 초과 상태로 5분 지속 | - | SEV2 |
| `JudgeJobLost` | k6 유실 카운터 증가 | - | SEV1 |
| 관측 경로 장애 | 봇이 Alertmanager `Watchdog` 알림을 5분 동안 받지 못함 | - | SEV2 |

에러 비율 하나로 알림을 걸면 잠깐 튄 오류에도 울리고, 조금씩 오래 새는 오류는 놓친다. 소진 속도와 시간 창을 함께 쓰면 큰 장애는 짧은 창으로, 천천히 새는 장애는 긴 창으로 구분해 잡는다. 1시간과 6시간 알림은 실험에는 거의 쓰이지 않지만 운영에 그대로 옮길 구성으로 남긴다.

Prometheus가 멈추면 Prometheus 스스로는 알림을 보낼 수 없다. 그래서 항상 울리는 `Watchdog` 알림을 봇이 받고, 끊기면 봇이 직접 장애를 연다.

### 6.3 실험 판정

- 판정 구간은 주입 시작부터 회복 구간 끝까지다. 이 구간의 SLO 지표를 6.1 목표와 비교해 가설 성립 여부를 적는다.
- 트래픽이 적으면 실패 몇 건에 비율이 크게 흔들린다. 판정 구간의 핵심 기능 요청이 1,000건 미만이면 "판정 불가"로 기록하고 부하를 늘려 다시 한다.
- 복구 시간은 주입 시작부터 해당 SLO 지표가 목표 안으로 돌아와 1분 동안 유지된 시점까지다.

## 7. 장애 대응 체계

장애를 언제 선언하고, 어떤 순서로 대응하고, 끝난 뒤 무엇을 남기는지를 정한다. E1~E13 모든 실험에 똑같이 적용해 대응 기록을 쌓는다.

### 7.1 설계 원칙

| 원칙 | 출처 |
|---|---|
| 사용자 영향과 서비스 영향 중 하나라도 기준을 넘으면 그 등급으로 정한다 | GitLab 심각도 기준: "If either the Customer Impact OR the GitLab Impact criteria is met" |
| 등급 정의는 사람의 느낌이 아니라 지표로 쓴다 | PagerDuty: 영향받은 사용자 비율 같은 지표로 등급을 정의하라고 권한다 |
| 애매하면 높은 등급으로 정하고, 장애 중에는 등급을 두고 논쟁하지 않는다 | PagerDuty: "Always Assume The Worst". 논쟁은 포스트모템에서 한다 |
| 등급은 장애 중 가장 컸던 영향으로 남기고, 완화된 뒤에도 낮추지 않는다 | GitLab: "reflects the maximum impact the incident had" |

### 7.2 영향 정도

기능 묶음(6.1)마다 영향 정도를 아래 기준으로 판단한다.

| 정도 | 지표 기준 | 근거 |
|---|---|---|
| 전면 불가 | 해당 묶음의 성공 비율이 5분 동안 50% 미만 | PagerDuty SEV-2 예시 "most or all users". 실제 사용자 수를 셀 수 없어 "대부분"을 요청의 절반 넘게 실패하는 것으로 해석했다 |
| 빠른 소진 | 소진 속도 14.4배 초과 (5분, 1시간 모두) | Google SRE 워크북: 1시간에 예산 2% 소진, 즉시 호출 기준 |
| 느린 소진 | 소진 속도 6배 초과 (6시간) | Google SRE 워크북: 6시간에 예산 5% 소진. 워크북은 소진 속도에 따라 대응 우선순위를 달리하라고 해서 한 단계 낮췄다 |
| 지연 | 제출 지연, 채점 처리, 조회 지연 목표 위반이 5분 지속 | 6.1 목표 |

### 7.3 심각도 매트릭스

| 등급 | 조건 (하나라도 해당하면) | 근거 |
|---|---|---|
| SEV1 | ① 핵심 기능 전면 불가 ② 채점 결과 유실이나 잘못된 채점 ③ 사용자 데이터 손상이나 손실 | ① GitLab S1 "Customer-facing service is down" ②③ GitLab S1 "Customer data loss". 데이터 문제는 영향 범위와 관계없이 SEV1이다 |
| SEV2 | ① 핵심 기능 빠른 소진 ② 핵심 기능 지연 목표 위반 ③ 주요 기능 전면 불가 ④ 모니터링이나 알림 경로 장애 | ①② GitLab S2 "Core functionality is significantly impacted" ③ GitLab S2 "unavailable for some customers" ④ PagerDuty SEV-2 "Monitoring for major incident conditions is impaired". 장애를 볼 수 없는 상태 자체가 장애다 |
| SEV3 | ① 핵심 기능 느린 소진 ② 주요 기능 빠른 소진 ③ 부가 기능 전면 불가나 `AiErrorRateHigh` ④ 이중화 상실: 한 번만 더 실패하면 장애가 나는 상태 | ①② 7.2 기준 ③ GitLab S3 "Moderate impact", PagerDuty SEV-3 "Partial loss of functionality" ④ PagerDuty SEV-3 "one more node failure would cause an outage" |
| SEV4 | 사용자 영향이 없는 이상: 파드 한 개 재시작 반복, 배치 지연 | PagerDuty SEV-4 "not affecting customer ability to use the product", GitLab S4 |

실험별 예상 등급은 8.2 표에 적는다. "개선으로 등급이 내려갔다"를 전후 비교 지표 하나로 쓴다. 예를 들어 E1은 지금 최소 1개라 SEV1이 예상되고, 개선 후 목표는 SEV3(이중화 상실)이다.

### 7.4 등급별 대응 규칙

| 항목 | SEV1 | SEV2 | SEV3 | SEV4 | 근거 |
|---|---|---|---|---|---|
| 대응 형태 | 주요 장애 대응 | 주요 장애 대응 | 담당자 즉시 대응 | 기록 후 처리 | PagerDuty: SEV-1, 2는 major incident response, SEV-3은 high-urgency page |
| 역할 | 지휘, 기록, 전파 | 지휘, 기록, 전파 | 지휘가 겸임 | 겸임 | GitLab: Communications Lead는 S1/S2, 낮은 등급은 한 사람이 여러 역할 |
| 탐지 목표 | 5분 | 5분 | - | - | 알림 짧은 창이 5분이다. Google SRE 워크북의 "짧은 창은 긴 창의 1/12" 규칙 |
| 등급 확정 | 선언 후 15분 안 | 15분 안 | 15분 안 | - | Monzo: 15분 안에 등급을 정하도록 반복 알림 |
| 첫 공지 | 선언 즉시, 확인된 최소 정보만 | 즉시 | - | - | 우아한형제들: 감지 즉시 공지, 처음에는 최소 정보 |
| 이후 공지 | 매 공지에 다음 공지 시각을 적음 | 같음 | - | - | GitLab은 고정 주기를 두지 않는다. 그래서 다음 시각을 약속하는 방식을 택했다 |
| 완화 목표 | 30분 | 30분 | 다음 작업 세션 | - | GitLab 지표 "30분 안 완화 비율". 아래 예산 계산 |
| 포스트모템 | 필수 | 필수 | 선택 | 없음 | GitLab: "All S1 and S2 incidents require a review". Atlassian: Sev 1, 2 필수 |
| 조치 항목 기한 | 4주 | 8주 | - | - | Atlassian: 우선 조치에 4주 또는 8주 기한 |
| 단기 조치 | 1~2일 | 1~2일 | - | - | 우아한형제들: 단기 재발 방지책은 하루 이틀 안에 마무리 |

완화 목표 30분과 에러 예산의 관계(6.2 4주 기준):

- SEV1 전면 불가 30분은 예산의 15%를 쓴다. 40분을 넘기면 20%를 넘어, 에러 예산 정책(9.4)의 "큰 장애 한 건" 기준에 걸린다.
- SEV2 빠른 소진(7.2%) 30분은 약 1%를 쓴다.
- 완화 목표 30분은 SEV1 한 건이 정책의 20% 기준 안에 들어오도록 맞춘 값이다.

### 7.5 역할

- 기업은 지휘, 기록, 전파를 다른 사람이 맡는다(PagerDuty Incident Commander, Scribe, Liaison / GitLab Incident Lead, Communications Lead). GitLab은 등급이 높을수록 사람을 나누라고 한다.
- 이 환경은 대응자가 한 명이라 SEV1, 2에서도 한 사람이 체크리스트 세 장을 순서대로 수행한다. 체크리스트는 `v3-john/chaos/incident/roles.md`에 둔다.
  - 지휘: 등급 확정, 완화 방법 결정, 종료 선언
  - 기록: 판단과 조치를 봇 스레드에 실시간으로 남긴다
  - 전파: 상태, 영향, 다음 조치, 다음 공지 시각을 올린다

### 7.6 대응 순서

1. 탐지: 알림을 받는다.
2. 선언: 봇 스레드에서 등급을 확정한다.
3. 완화: 원인을 찾기 전에 피해부터 멈춘다. 우아한형제들 "서비스 정상화는 원인 파악보다 우선", PagerDuty의 안정화 우선 원칙을 따른다.
   - 먼저 최근 24시간 변경(Argo CD 배포, 승격 PR, 실행 중인 실험)을 확인한다. 우아한형제들 롤백 판단 기준과 같다.
   - 기본 조치 목록에서 고른다: 롤백, 재시작, 확장, 격리, 속도 제한. PagerDuty가 드는 대표 조치(롤백, 롤링 재시작, 스로틀링)를 이 환경에 맞췄다.
4. 복구 확인: SLO 지표가 목표 안으로 돌아와 1분 유지되는지 본다(6.3).
5. 종료: 지휘 체크리스트로 종료를 선언한다.
6. 포스트모템: SEV1, 2는 필수다(7.8).
7. 조치 항목: GitHub Issue로 등록하고 7.4 기한을 단다.

### 7.7 Discord 장애 봇

| 기능 | 동작 | 근거 |
|---|---|---|
| 스레드 개설 | Alertmanager 웹훅을 받으면 `INC-<날짜>-<번호>` 스레드를 연다. 알림 내용, Grafana 패널 링크, 제안 등급을 올린다 | 카카오페이증권 핑크와드: 자동 스레드 개설 |

- 핑크와드 공개 사례는 장애 처리 시간 67%, 보고서 작성 시간 80% 단축을 보고했다.
- 등급 제안 로직은 7.3 매트릭스를 그대로 코드로 옮긴다. 매트릭스가 문서로만 남지 않고 단위 테스트로 검증된다.
- Python으로 만들고 `monitoring` 네임스페이스에 Deployment로 띄운다. Discord 봇 토큰은 Secrets Manager에 둔다. Alertmanager 알림용 웹훅(`cosmos/monitoring/discord-webhook`)과는 별개다.
- 클러스터가 꺼지면 상태가 사라지므로 장애 기록은 S3에 남긴다.
- 봇 기록 시각과 실행기의 주입 시각을 합쳐 탐지, 선언, 완화 시간을 자동으로 계산한다(10.1).
- GitHub에 PR이나 이슈를 자동으로 만드는 기능은 넣지 않는다. 초안 커밋과 조치 이슈 등록은 사람이 한다.

### 7.9 해석과 추론으로 정한 값

- 전면 불가 50%: PagerDuty의 "대부분의 사용자"를 요청 비율로 바꾼 해석이다.
- 주요 기능 99%: 서비스 구조에서 추론한 값이다.
- 두 값은 실험 결과를 보고 바꿀 수 있고, 바꾸면 이유를 기록한다.

## 8. 실험 범위와 안전 장치

### 8.1 의존성 표

실험은 서비스가 기대는 의존성 표에서 뽑는다. Shopify는 의존성과 장애 시나리오를 사용자 경험과 대조한 표를 훈련의 근거로 쓰고, 우아한형제들은 외부 의존성마다 담당자, 알림 채널, 최악의 장애 등급, 대응책을 기록한다.

선택 규칙:

- 핵심 기능 경로에 있는 의존성은 전부 실험 하나 이상으로 덮는다.
- 주요, 부가 기능은 대표 의존성 하나씩만 덮는다.
- 실험하지 않는 의존성은 이유를 적는다.

| 의존성 | 쓰는 묶음 | 현재 상태 | 실패 시 예상 등급 | 실험 |
|---|---|---|---|---|
| Envoy 프록시 | 전부 | `replicas: 1` | SEV1 | E12 |
| CoreDNS | 전부 | system 노드 1대에 몰림 | SEV1 | E12 |
| core 파드 | 핵심 | HPA 최소 1 | SEV1 | E1 |
| RDS MySQL | 핵심 | 단일 AZ, 자동 백업 보존 0일 | SEV1 | E6, E11 |
| judge-redis 대기열 | 핵심 | AOF, 5Gi 볼륨 1개 | 유실 시 SEV1 | E13 |
| judge-worker | 핵심 | KEDA 최대 1 | 유실 시 SEV1 | E2, E7 |
| judge-postgres | 핵심 | 30Gi 볼륨 1개, 백업 없음 | SEV1 | E5, E10 |
| Spot 노드 | 전부 | application 노드 min=max=2 | SEV1~3 | E3 |
| core → ai-llm | 부가 | 동기 호출 | SEV3, 번지면 SEV2 | E4 |
| ai-llm → Gemini | 부가 | 가짜 서버로 대체 | SEV3 | E8 |
| 설정 배포 (GitOps) | 전부 | 자동 롤백 없음 | SEV1~3 | E9 |
| ai-postgres | 부가 | 볼륨 1개 | SEV3 | 미실험: judge-postgres와 복구 경로가 같아 E10 결과로 대신한다 |
| ECR, Secrets Manager | 파드 시작 시점 | AWS 관리형 | 재시작 중에만 영향 | 미실험: 주입 수단이 없고 영향이 파드 재시작 순간에 한정된다. E1, E3에서 함께 관찰한다 |
| 관측 경로 (Prometheus, Alertmanager) | 대응 수단 | 1개씩 | SEV2 | 미실험: 실험을 측정하는 수단이라 망가뜨리지 않고 중단 조건(8.3)으로 보호한다 |

표를 만들면서 드러난 약점:

- 진입점(Envoy 1개)과 DNS(노드 1대)가 단일 장애점이다.
- 데이터 저장소 세 곳 모두 되살릴 수단이 시드 데이터뿐이라, 데이터 손실 범위가 "시드 이후 전부"다.

### 8.2 실험 목록

실험별 보충:

- E4는 judge-api 구간에도 같은 방식으로 반복할 수 있으나 범위에서 제외한다.
- E7은 Chaos 리소스 없이 k6 부하 형태만 바꾼다. Spot 용량이 부족해 노드가 늘지 않는 경우도 결과로 기록한다.
- E8은 비용을 막기 위해 실제 Gemini 대신 WireMock으로 만든 가짜 Gemini 서버에 지연을 넣는다. 가짜 서버는 `generateContent`와 임베딩 요청에 고정된 정상 응답을 돌려주므로 기준선에서도 AI 기능이 성공한다. 실제 외부 호출과 다른 점(HTTPS가 아닌 HTTP, 응답 내용 고정)은 결과 해석에 함께 적는다. 실행기는 시작 전에 ai-llm 파드의 `GOOGLE_GEMINI_BASE_URL`이 가짜 서버를 가리키는지 확인하고, 아니면 실험을 시작하지 않는다.
- E9는 실제 운영과 같은 경로로 진행한다. `v3-john` 값 파일을 바꾸는 PR을 병합하면 Argo CD가 core를 자동 동기화한다. 복구는 되돌림 PR로 한다. 커밋 메시지는 `chaos(E9):`로 시작해 이력에서 실험임을 구분한다. 자동 롤백(9.2) 도입 후 다시 돌려 수동 복구와 비교한다.
- E10, E11, E13은 E2와 달리 데이터 저장소 자체를 건드린다. 근거는 AWS Well-Architected REL13-BP03 "복구 경로를 정기적으로 시험해 RTO, RPO 충족을 확인하라"다.
- E10, E11의 복구 목표 시간과 허용 데이터 손실 범위는 미리 정하지 않는다. 현재 값을 먼저 재고, 그 값으로 개선 후 목표를 정한다. REL13-BP01 "복구 목표를 정의하라"의 순서를 따르되 근거 없는 숫자를 먼저 두지 않기 위해서다.
- E11은 RDS를 삭제하므로 실행 전에 수동 스냅샷을 만들고, 복원 확인 전에는 스냅샷을 지우지 않는다.

### 8.3 안전 장치

Netflix는 실험 영향이 커지면 자동으로 중단해 실제 사용자를 보호한다. 이 환경에는 실제 사용자가 없어 그 목적은 해당하지 않고, 대신 아래를 막는다.

| 중단 조건 | 막으려는 것 | 근거 |
|---|---|---|
| 관측 경로(Prometheus, Alertmanager)가 응답하지 않으면 즉시 중단 | 측정할 수 없는 실험 | 7.3 SEV2 ④와 같은 이유 |
| Spot vCPU 합계가 28을 넘으면 중단 (E7) | 비용 폭주와 한도 32 도달 | 2장 제약 |
| 실험 시간이 최대 10분을 넘으면 중단 | 끝나지 않는 장애 | Chaos Mesh `duration`으로 자동 종료 |
| FIS 실험(E3)에 CloudWatch 알람 중단 조건 연결 | 노드를 지나치게 회수하는 것 | AWS FIS 문서: 정상 상태를 정의하고 CloudWatch 알람으로 실험을 멈춘다 |

실행 규칙:

- 주입 전 정상 상태 확인: 2분 동안 SLO를 만족하지 못하면 주입하지 않는다. 이미 아픈 상태에서 장애를 넣으면 원인을 구분할 수 없다. 근거는 AWS FIS "first define the steady state", Netflix의 대조군 비교다.
- 한 번에 실험 하나만 한다. Netflix는 동시 실험을 제한하고 페일오버 중에는 실험하지 않는다.
- 실행기는 중단 시그널을 받으면 모든 Chaos 리소스를 지운다.

## 9. 개선

실험으로 약점이 확인된 것만 고치고, 같은 실험으로 다시 잰다. 가설대로 버틴 항목은 고치지 않고 버틴 근거를 기록한다.

### 9.1 실험별 설정 개선

| 약점 (실험) | 개선 | 근거 |
|---|---|---|
| 최소 1개라 재시작 동안 전면 불가 (E1, E3) | core, auth, battle, judge-api HPA 최소 2, PDB `minAvailable: 1`, 노드와 AZ 분산, application 노드 최대 3대 | PagerDuty SEV-3 "one more node failure would cause an outage" |
| 채점 용량 고정 (E7) | KEDA 최대 3, judge 노드 최대 3대 | worker가 CPU 2개를 요청해 judge 노드 한 대(4 vCPU)에 하나씩만 들어간다 |
| 진입점 단일 장애점 (E12) | Envoy `replicas: 2`, 노드 분산 | 8.1 의존성 표 |
| DNS가 노드 한 대에 몰림 (E12) | CoreDNS가 application 노드에도 뜰 수 있게 배치 규칙 변경, 노드 분산 | system 노드를 늘리면 vCPU 합계가 30이 된다. 배치 규칙만 바꾸면 비용이 없다 |
| judge-postgres 복구 수단 없음 (E10) | judge-postgres, ai-postgres `pg_dump` → S3 CronJob. 주기는 E10에서 정한 허용 손실 범위로 결정 | REL13-BP01 복구 목표 정의 |
| RDS 특정 시점 복원 불가 (E11) | `backup_retention_period = 1` | 자동 백업을 켜야 특정 시점 복원이 된다. 1일은 비용이 가장 적은 값이다 |
| 대기열 유실 (E13, 유실 확인 시에만) | `appendfsync always` 검토 | 매번 디스크에 쓰면 성능이 떨어진다. 유실 건수와 성능 저하를 함께 재서 판단한다 |
| 배포 이벤트가 안 보임 (E9) | Argo CD 배포 알림을 Grafana 주석으로 표시 | 우아한형제들: 장애 전 24시간 변경 확인 |
| 연쇄 장애 (E4, E8) | 2b Istio 조건부 도입. 앱 타임아웃은 개선 제안으로 기록 | 4장 |

vCPU 최대치: system 2 + stateful 2 + judge 12 + application 12 = 28. 한도 32 안이다.

### 9.2 자동 롤백 (Argo Rollouts 카나리 배포)

E9는 사람이 발견하고 되돌려야 해서 복구 시간이 길다. 우아한형제들 채용 공고는 블루그린, 카나리 배포로 장애 영향을 줄이는 경험을 요구하고, 카카오페이증권은 롤백 버튼을 운영 도구에 둔다.

| 항목 | 설정 | 근거 |
|---|---|---|
| 대상 | core, auth, battle (같은 차트) | E9 대상이 core다 |
| 단계 | 50% → 분석 5분 → 100% | 레플리카가 2개라 트래픽 분배기 없이 나눌 수 있는 최소 단위가 50%다. Argo Rollouts는 트래픽 분배기가 없으면 레플리카 수로 비율을 맞춘다 |
| 분석 지표 | `slo:core_errors:ratio_rate5m > 0.072` 또는 `slo:ai_errors:ratio_rate5m > 0.05`이면 실패 | 7.3과 같은 선이다. 7.2%는 소진 속도 14.4배, 5%는 AI SLO다 |
| 실패 시 | 롤아웃을 중단하고 안정 버전으로 돌아간다 | Argo Rollouts 문서 |

한계: 지표가 버전별이 아니라 서비스 전체 기준이다. 카나리가 크게 망가져야 확실히 잡히고 작은 회귀는 놓칠 수 있다. 이 한계를 보고서에 적는다.

재측정: E9를 다시 돌려 수동 되돌림 복구 시간과 자동 중단 복구 시간을 비교한다.

### 9.3 속도 제한

채점 용량을 늘려도 한도가 있다. 그걸 넘는 폭주(E7)에서는 일부를 거절하는 편이 전체가 느려지는 것보다 낫다. Slack은 2022년 장애에서 스로틀링으로 부하를 막고 한도를 조금씩 올렸고, PagerDuty도 대표 완화 조치로 스로틀링을 든다.

| 항목 | 설정 | 근거 |
|---|---|---|
| 방식 | Envoy Gateway `BackendTrafficPolicy` 로컬 속도 제한, `POST /api/submissions` 경로만 | Envoy Gateway 문서. Redis 없이 프록시마다 메모리에서 센다 |
| 한도 | E7 재실험에서 잰 채점 처리량을 넘지 않게 정한다 | 숫자를 미리 정하지 않는다 |
| 프록시 2개일 때 | 한도가 프록시마다 적용되어 전체 한도가 2배가 된다. 계산에 반영한다 | 문서: 프록시 인스턴스 하나 기준 |
| 거절 응답 | 429 | 문서 |

재측정: E7을 속도 제한 전후로 비교한다. 채점 처리 p95, 채점 완료율, 거절률을 본다.

### 9.4 에러 예산 정책

Google SRE 워크북의 예시 에러 예산 정책을 이 환경에 맞췄다.

| 정책 | 내용 | 원문 근거 |
|---|---|---|
| 기간 | 최근 4주 | "preceding four-week window" |
| 예산 초과 시 | P0 버그와 보안 수정을 빼고 승격을 멈춘다 | "halt all changes and releases other than P0 issues or security fixes" |
| 큰 장애 한 건 | 4주 예산의 20%를 넘게 쓴 장애는 포스트모템에 P0 조치 항목을 최소 하나 넣는다 | "more than 20% of error budget over four weeks" |
| 예외 | 부하 테스트처럼 계획된 트래픽이 쓴 예산은 정책에서 뺀다 | "out-of-scope traffic (such as load tests...)" |

집행 방법:

- 장애마다 예산 소진량을 `v3-john/chaos/error-budget-ledger.md`에 기록한다.
- 4주 합계가 100%를 넘으면 Cloud 저장소에 `deploy-freeze` 라벨 이슈를 연다.
- `v3-promote`가 이 이슈를 확인하고, 열려 있으면 승격 PR의 필수 검사를 실패시킨다. GitLab 장애 필드 "Blocks Deployments"와 같은 장치다.
- P0, 보안 수정은 PR에 `freeze-exception` 라벨을 달면 통과한다.

한계: 이 환경의 장애는 전부 계획된 실험이라 원문 예외 조항대로라면 정책이 자연스럽게 발동하지 않는다. 그래서 집행 장치는 단위 테스트와, 장부에 가상 항목을 넣어 승격이 막히는지 확인하는 시연 한 번으로 검증한다. 실험이 쓴 예산은 "훈련 소진"으로 따로 기록하고, 운영이었다면 정책이 발동했을지 보고서에 계산한다.
