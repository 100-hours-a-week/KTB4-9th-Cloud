# v3-john 장애 주입과 장애 대응 설계

작성일: 2026-11-11 · 대상: `v3-john` 훈련 클러스터 · 기간: 7일

## 1. 목적

자주 일어나거나 일어나면 치명적인 장애 세 가지를 직접 일으키고, 장애 대응 체계에 따라 대응한다. 장애 하나가 어디까지 번지는지 밝혀내고, 여러 계층에서 개선한 뒤 같은 장애로 다시 재서 개선마다 효과를 수치로 증명한다.

결과물은 시나리오별 실험 기록, 포스트모템, 개선 단계별 전후 비교 수치, 런북, 최종 보고서다.

## 2. 시나리오 선정

| ID | 시나리오 | 고른 이유 | 답하는 질문 |
|---|---|---|---|
| S1 | 잘못된 배포로 core 파드가 죽고 연쇄 장애로 번짐 | 업계에서 가장 자주 일어난다. Google SRE는 운영 장애의 약 70%가 변경에서 생긴다고 본다 | 우리가 일으킨 장애를 빨리 잡고 되돌릴 수 있나 |
| S2 | application 스팟 노드 회수 | 이 환경에서 가장 자주 일어난다. 모든 노드가 스팟이다 | 인프라가 사라져도 서비스가 버티나 |
| S3 | RDS 장애: 연결 차단, 이어서 삭제와 복원 | 일어나면 가장 치명적이다. core, auth, battle이 단일 AZ RDS 하나를 쓰고 백업이 없다 | 데이터 계층이 죽으면 얼마나 번지고, 얼마나 잃고, 얼마나 걸려 복구하나 |

"가장 자주 일어나는 것 둘, 가장 치명적인 것 하나"를 기준으로 골랐다. 세 시나리오는 원인이 겹치지 않는다. S1은 사람이 만든 변경, S2는 컴퓨팅 인프라 소실, S3은 데이터 계층 소실이다.

검토 후 제외한 후보:

- 외부 AI 의존성 지연: core가 AI 호출을 비동기로 처리해 핵심 기능으로 번질 가능성이 낮다. 1일차 사전 확인에서 실제로 비동기인지 확인한다.
- 단순 파드 강제 종료: 쿠버네티스가 스스로 복구해 사람이 대응할 거리가 적다. 실제 운영에서 파드가 죽는 주원인은 배포이므로 S1에 포함한다.
- Envoy 프록시 단일 장애점: `replicas: 2` 한 줄로 해결되어 대응과 개선 거리가 적다. 실험 없이 1일차에 바로 고친다(11장).

## 3. 제약

- v3-john은 작업할 때만 `up.sh`로 띄우고 `down.sh`로 내린다. 모든 도구와 실험은 `up.sh` 한 번으로 재현되어야 하고, 실험 결과는 S3와 문서로 남긴다.
- 수정은 인프라, 설정, 운영 도구만 한다(Terraform, Helm 값, 환경 변수, 쿠버네티스 리소스, Cloud 저장소 워크플로). 앱 코드 수정이 필요한 문제는 개선 제안으로만 기록한다.
- Spot vCPU 한도는 32개이고 한도 증가는 요청하지 않는다.
- v3-john은 실제 Gemini API를 호출하지 않는다. ai-llm은 `GOOGLE_GEMINI_BASE_URL`로 클러스터 안의 가짜 Gemini 서버를 본다.
- 승격 파이프라인(`v3-promote`)이 `v3-john` 값 파일의 `image`, `sourceRevision` 줄을 고치므로 실험용 변경은 이 줄을 건드리지 않는다.
- 대응자는 한 명이다. 기업에서 여러 사람이 나눠 맡는 역할을 한 사람이 체크리스트로 수행하고, 이 한계를 보고서에 적는다.

## 4. 현재 구조에서 확인한 사실

시나리오와 직접 관련된 사실만 적는다.

**core**

- 값 파일은 `v3-john/gitops/environments/prod/core.yaml`이다.
- HPA는 최소 1, 최대 3이고 CPU 70%를 기준으로 확장한다.
- 자원은 요청 CPU 1, 메모리 1Gi이고 제한은 CPU 2, 메모리 2Gi다. JVM 힙 설정이 없어 기본값이면 힙은 메모리 제한의 25%다.
- 검사:
  - 기동 검사는 TCP 8080을 최대 180초(5초 × 36회) 기다린다.
  - 준비 상태 검사는 `/actuator/health`(9091)를 본다. Spring 기본 설정이면 이 검사에 DB 상태가 포함된다.
  - 생존 검사는 TCP 8080이다.
- Hikari 커넥션 풀은 최대 10개다.
- 차트에 PodDisruptionBudget이 없다.

**core를 호출하는 쪽**

- ai-llm, ai-make-problem, ai-problem-batch, ai-migrate가 `BACKEND_URL: http://core-service/api`로 core를 호출한다.
- Judge는 채점이 끝나면 `callback_url`로 결과를 보내는 기능이 있다(`app/jobs/isolate_job.rb`). 5초 제한으로 3번 시도하고, 실패하면 예외를 삼키고 기록을 남기지 않는다. core가 이 기능을 쓰는지는 1일차에 확인한다.

**노드** (`v3-john/modules/eks`)

- 모든 노드 그룹이 스팟이고, 서브넷 `a` 하나에만 있다. 단일 AZ다.
- application 노드 그룹은 `t3.xlarge`, `t3a.xlarge`, `m5.xlarge`이고 min=max=2다. 여유 노드가 없다.
- stateful 노드 그룹(judge-redis, judge-postgres, ai-postgres)은 1대다.
- 현재 vCPU 합계는 system 2, stateful 2, judge 4, application 8로 16이다.

**RDS** (`v3-john/modules/data/main.tf`)

- `db.t4g.medium`, `multi_az = false`
- `backup_retention_period = 0`: 특정 시점 복원을 할 수 없다.
- `deletion_protection = false`, `skip_final_snapshot = true`: 지우면 스냅샷 없이 사라진다.
- 접속 정보는 Secrets Manager `cosmos/john/spring-config`(`DB_URL`)와 `cosmos/john/main-db`에 있다.

**배포와 관측**

- prod ApplicationSet은 auth, core, battle과 AI 앱을 자동 동기화한다. `selfHeal`은 꺼져 있다.
- EnvoyProxy는 `replicas: 1`이다.
- Prometheus, Alertmanager(Discord 웹훅), Loki, Alloy, Grafana가 있다. 배포 이벤트가 대시보드에 표시되지 않는다.

## 6. SLO와 알림

v3-john은 작업할 때만 켜고 트래픽은 k6가 만든다. 목표와 에러 예산은 "운영이라면 이렇게 둔다"는 가정이고, 실험의 합격 여부는 실험 구간 안의 수치로 판정한다.

### 6.1 기능 묶음과 목표

가용성은 기능 묶음별로 나눈다. 묶음은 Envoy Gateway 라우트 경로로 구분하고 `journey` 라벨로 기록한다.

| 묶음 | 기능 (BE 컨트롤러) | 이유 |
|---|---|---|
| 핵심 | 로그인(`Auth`), 문제 조회(`Problem`, `DailyProblem`), 코드 제출과 채점(`CodeSubmission`) | 서비스의 본래 가치인 "문제를 풀고 채점받기"다 |
| 주요 | 배틀(`DailyBattle`), 랭킹(`Ranking`), 알림(`Sse`, `Notification`), 활동 기록(`ActivityRecord`) | 잠시 실패해도 나중에 따라잡을 수 있다 |
| 부가 | AI 힌트(`Hint`), 풀이 평가(`ApproachSubmission`, `SolutionEvaluation`) | 외부 LLM에 의존하고, 없어도 문제 풀이는 된다 |

| SLO | 지표 | 목표 |
|---|---|---|
| 핵심 기능 가용성 | 핵심 묶음 요청 중 5xx가 아닌 비율 | 99.5% |
| 주요 기능 가용성 | 주요 묶음 요청 중 5xx가 아닌 비율 | 99% |
| AI 기능 가용성 | 부가 묶음 요청 중 5xx가 아닌 비율 | 95% |
| 조회 지연 | 로그인, 문제 조회 p95 | 기준선 p95의 2배 이하 |
| 채점 처리 | 제출부터 결과 조회 성공까지 p95 (k6 측정) | 30초 이하 |
| 채점 완료율 | k6가 보낸 제출 중 5분 안에 결과를 받은 비율 | 100% |

- 주요 기능 99%는 핵심보다 낮고 부가보다 높게 서비스 구조에서 추론한 값이다.
- 지연 목표는 기준선 3회를 잰 뒤 확정한다. 채점 처리 30초는 기준선 p95가 이를 넘으면 기준선의 1.5배로 바꾸고 이유를 남긴다.

### 6.2 에러 예산

- 에러 예산 기간은 최근 4주다. 핵심 기능 99.5%면 4주(40,320분) 중 완전히 멈춰도 되는 시간이 약 200분이다.
- 소진 속도는 지금 에러 비율이 허용 비율(0.5%)의 몇 배인지다. 14.4배면 약 2일 만에 예산을 다 쓴다.
- 예산 소진량은 장애 한 건이 4주 예산 중 몇 %를 썼는지다. `소진량 = (실패 비율 × 지속 시간) ÷ 4주 허용 실패 시간`. 예를 들어 핵심 기능이 30분 동안 완전히 멈추면 15%다.

### 6.3 알림

알림을 두 종류로 나눈다. Google SRE는 원인이 아니라 사용자가 겪는 증상으로 호출하라고 한다. 증상 알림이 장애를 열고, 원인 알림은 진단을 돕는다.

증상 알림 (장애 선언의 근거, `severity` 라벨에 제안 등급):

| 알림 | 조건 | 제안 등급 |
|---|---|---|
| `CoreUnavailable` | 최근 5분 핵심 기능 성공 비율 50% 미만 | SEV1 |
| `CoreErrorBudgetBurnFast` | 최근 5분과 1시간 모두 소진 속도 14.4배 초과(5분 동안 7.2% 넘게 실패) | SEV2 |
| `MajorUnavailable` | 최근 5분 주요 기능 성공 비율 50% 미만 | SEV2 |
| `ReadLatencyHigh` | 조회 p95 목표 초과가 5분 지속 | SEV2 |
| `JudgeTurnaroundHigh` | 채점 처리 p95 목표 초과가 5분 지속 | SEV2 |
| `JudgeJobLost` | k6 유실 카운터 증가 | SEV1 |
| `AiErrorRateHigh` | 최근 5분 AI 기능 에러 비율 5% 초과 | SEV3 |

원인 알림 (진단용, 등급 없음):

| 알림 | 조건 | 주로 쓰는 시나리오 |
|---|---|---|
| `PodCrashLooping` | 컨테이너 재시작이 10분에 3회 이상, 또는 OOMKilled | S1 |
| `PodsPending` | `prod` 파드가 2분 넘게 Pending | S1, S2 |
| `NodeNotReady` | 노드가 1분 넘게 NotReady | S2 |
| `DbConnectionPoolExhausted` | Hikari 대기 커넥션이 1분 넘게 0보다 큼 | S1, S3 |
| `DeploymentReplicasUnavailable` | Deployment 가용 레플리카가 원하는 수보다 적은 상태가 2분 지속 | 전부 |

관측 경로 장애는 Alertmanager `Watchdog` 알림이 Discord에 계속 오는지로 확인한다. 실험 실행기는 Prometheus가 응답하지 않으면 실험을 중단한다(8.2).

### 6.4 실험 판정

- 판정 구간은 주입 시작부터 회복 구간 끝까지다. 이 구간의 SLO 지표를 목표와 비교해 가설 성립 여부를 적는다.
- 판정 구간의 핵심 기능 요청이 1,000건 미만이면 "판정 불가"로 기록하고 부하를 늘려 다시 한다.
- 복구 시간은 주입 시작부터 해당 SLO 지표가 목표 안으로 돌아와 1분 동안 유지된 시점까지다.

## 7. 장애 대응 체계

### 7.1 원칙

| 원칙 | 출처 |
|---|---|
| 사용자 영향과 서비스 영향 중 하나라도 기준을 넘으면 그 등급으로 정한다 | GitLab: "If either the Customer Impact OR the GitLab Impact criteria is met" |
| 등급은 느낌이 아니라 지표로 정의한다 | PagerDuty |
| 애매하면 높은 등급으로 정하고, 등급 논쟁은 포스트모템에서 한다 | PagerDuty: "Always Assume The Worst" |
| 등급은 장애 중 가장 컸던 영향으로 남기고 낮추지 않는다 | GitLab: "reflects the maximum impact the incident had" |
| 원인을 찾기 전에 피해부터 멈춘다 | 우아한형제들: "서비스 정상화는 원인 파악보다 우선". PagerDuty 안정화 우선 |

### 7.2 심각도 매트릭스

| 등급 | 조건 (하나라도 해당하면) | 근거 |
|---|---|---|
| SEV1 | ① 핵심 기능 전면 불가(성공 비율 5분 동안 50% 미만) ② 채점 결과 유실이나 잘못된 채점 ③ 사용자 데이터 손실이나 손상 | ① GitLab S1 "Customer-facing service is down" ②③ GitLab S1 "Customer data loss" |
| SEV2 | ① 핵심 기능 빠른 소진(14.4배) ② 핵심 기능 지연 목표 위반 ③ 주요 기능 전면 불가 ④ 모니터링이나 알림 경로 장애 | ①② GitLab S2 "Core functionality is significantly impacted" ③ GitLab S2 ④ PagerDuty SEV-2 "Monitoring for major incident conditions is impaired" |
| SEV3 | ① 주요 기능 빠른 소진 ② 부가 기능 장애 ③ 이중화 상실: 사용자 영향은 없지만 한 번만 더 실패하면 장애가 나는 상태 | ①② GitLab S3 "Moderate impact" ③ PagerDuty SEV-3 "one more node failure would cause an outage" |

- 전면 불가 50%는 PagerDuty의 "most or all users"를 요청 비율로 바꾼 해석이다.
- 시나리오마다 개선 전과 후의 등급을 비교한다. 예를 들어 S2는 개선 전 SEV1, 개선 후 SEV3(이중화 상실)을 목표로 한다.

### 7.3 등급별 대응 규칙

| 항목 | SEV1 | SEV2 | SEV3 | 근거 |
|---|---|---|---|---|
| 탐지 목표 | 5분 | 5분 | - | 알림 짧은 창 5분. Google SRE 워크북 "짧은 창은 긴 창의 1/12" |
| 등급 확정 | 선언 후 15분 안 | 15분 안 | 15분 안 | Monzo: 15분 안에 등급을 정하도록 반복 알림 |
| 첫 공지 | 즉시, 확인된 최소 정보만 | 즉시 | - | 우아한형제들: 감지 즉시 공지 |
| 이후 공지 | 매 공지에 다음 공지 시각을 적음 | 같음 | - | GitLab은 고정 주기를 두지 않는다 |
| 완화 목표 | 30분 | 30분 | 다음 작업 세션 | GitLab 지표 "30분 안 완화 비율". SEV1 30분은 4주 예산의 15%로, 40분(20%)을 넘지 않게 맞춘 값이다 |
| 포스트모템 | 필수 | 필수 | 선택 | GitLab: "All S1 and S2 incidents require a review". Atlassian: Sev 1, 2 필수 |
| 조치 항목 기한 | 4주 | 8주 | - | Atlassian: 우선 조치 4주, 8주 |

### 7.4 역할

기업은 지휘, 기록, 전파를 다른 사람이 맡는다(PagerDuty Incident Commander, Scribe, Liaison). 이 환경은 한 사람이 체크리스트 세 장을 순서대로 수행한다. 체크리스트는 `v3-john/chaos/incident/roles.md`에 둔다.

- 지휘: 등급 확정, 완화 방법 결정, 종료 선언
- 기록: 시각과 판단, 조치를 장애 스레드에 바로 남긴다
- 전파: 상태, 영향, 다음 조치, 다음 공지 시각을 올린다

### 7.5 대응 순서

1. 탐지: 증상 알림을 받는다.
2. 선언: Discord에 `INC-<날짜>-<번호>` 스레드를 열고 등급을 확정한다.
3. 완화:
   - 최근 24시간 변경(Argo CD 배포, 승격 PR)부터 확인한다. 우아한형제들 롤백 판단 기준과 같다.
   - 기본 조치 목록에서 고른다: 롤백, 재시작, 확장, 격리, 재배치.
4. 복구 확인: SLO가 목표 안으로 돌아와 1분 유지되는지 본다.
5. 종료 선언
6. 포스트모템과 조치 이슈 등록

장애 스레드는 Discord에 사람이 직접 연다. Alertmanager 알림은 기존 웹훅 채널로 온다. 봇 자동화는 범위 밖이다(12장).

### 7.6 포스트모템 양식

비난 없는 형식으로 쓰고 양식은 `v3-john/chaos/incident/postmortem-template.md`에 둔다.

## 8. 실험 진행 방식

### 8.1 시나리오 한 개의 진행

1. 정상 상태 확인: 2분 동안 SLO를 만족하지 못하면 주입하지 않는다(AWS FIS "first define the steady state").
2. 개선 전 실험: 주입하고, 7장 체계대로 대응하고, 연쇄 관찰표를 채운다.
3. 포스트모템을 쓴다.
4. 개선 단계를 하나 적용하고 같은 실험을 다시 한다. 이 단계를 반복한다.
5. 단계별 비교표를 만든다.

개선을 한꺼번에 넣지 않고 한 단계씩 넣는다. 그래야 "어떤 개선이 얼마나 효과가 있었나"를 나눠서 보여 줄 수 있다. 개선 후 재실험에서도 대응 절차를 똑같이 수행하고 시간을 잰다.

### 8.2 안전 장치

| 중단 조건 | 막으려는 것 |
|---|---|
| Prometheus나 Alertmanager가 응답하지 않으면 즉시 중단 | 측정할 수 없는 실험 |
| Spot vCPU 합계가 24를 넘으면 중단 | 비용 폭주와 한도 도달 |
| 장애 주입 시간이 10분을 넘으면 주입을 멈춘다 | 끝나지 않는 장애 |
| 복원 작업이 60분을 넘으면 안전 스냅샷으로 되돌린다(S3) | 복구 불가 |
| FIS 실험에 CloudWatch 알람 중단 조건 연결 | 노드를 지나치게 회수하는 것 |

- 한 번에 시나리오 하나만 한다.
- 실행기는 중단 시그널을 받으면 Chaos 리소스를 지우고 FIS 실험을 멈춘다.

### 8.3 측정 지표

| 지표 | 정의 |
|---|---|
| 탐지 시간 | 주입 시작 → 첫 증상 알림 |
| 선언 시간 | 첫 알림 → 등급 확정 |
| 완화 시간 | 주입 시작 → 완화 조치 완료 |
| 복구 시간 | 6.4 정의 |
| 원인 파악 시간 | 첫 알림 → 원인 확정 |
| 등급 | 7.2 기준 |
| 예산 소진량 | 6.2 공식 |
| 사용자 영향 | 기능 묶음별 실패율, 지연 p95, 채점 완료율 |
| 연쇄 범위 | 영향을 받은 서비스 수와, 연쇄 관찰표에서 실제로 일어난 항목 |

## 9. 시나리오 상세

### 9.1 S1 잘못된 배포로 core 연쇄 장애

**주입**

- "비용 절감" 명목으로 core 메모리 제한을 낮추는 PR을 병합한다. Argo CD가 자동 동기화한다.
- 값은 1일차에 정한다. 기동과 준비 상태 검사는 통과하고 k6 부하에서만 OOMKilled가 나는 값을 찾는다.
- 기동이 실패하는 변경은 쓰지 않는다. 롤링 업데이트에서 새 파드가 준비되지 않으면 기존 파드가 남아 장애가 나지 않기 때문이다. 검사를 통과한 뒤에 깨지는 변경이라야 실제 배포 사고와 같다.
- 커밋 메시지는 `chaos(S1):`로 시작한다.

**가설**: 10분 안에 탐지하고, 최근 변경에서 원인을 찾아 되돌림으로 30분 안에 완화한다.

**연쇄 관찰표** (실험에서 하나씩 일어났는지 확인한다)

| 순서 | 예상 연쇄 | 확인 방법 |
|---|---|---|
| 1 | core OOMKilled → 재시작 반복 → CrashLoopBackOff 대기 시간이 최대 5분까지 늘어난다 | 파드 이벤트, 재시작 횟수 |
| 2 | 파드가 1개라 재시작 동안 핵심 기능 전면 불가 | `CoreUnavailable` |
| 3 | AI 서비스의 core 호출 실패 | AI 에러율, ai-llm 로그 |
| 4 | core가 Judge 콜백을 쓴다면 채점 결과가 조용히 유실된다 | 채점 완료율, judge 로그 |
| 5 | core가 살아나는 순간 재시도와 SSE 재연결이 몰린다 | 요청량, 지연 |
| 6 | 막 뜬 core가 몰린 부하에 다시 무너진다 | 재시작 간격 |
| 7 | 재연결로 DB 커넥션이 몰린다 | Hikari 대기 커넥션, RDS 연결 수 |
| 8 | HPA가 확장하려 하지만 노드 여유가 없어 Pending | `PodsPending` |

**개선 단계**

| 단계 | 개선 | 계층 | 기대 효과 |
|---|---|---|---|
| 1 | Argo CD 배포 이벤트를 Grafana 주석으로 표시, `PodCrashLooping` 알림 | 관측 | 원인 파악 시간 단축 |
| 2 | HPA 최소 2, PDB `minAvailable: 1`, 노드 분산, JVM 힙 비율(`-XX:MaxRAMPercentage`) 설정 | 쿠버네티스, 애플리케이션 설정 | 한 파드가 죽어도 전면 불가가 되지 않음 |
| 3 | Argo Rollouts 카나리: 50% → 분석 5분 → 100%. 핵심 기능 에러 비율 7.2% 초과나 재시작 발생 시 자동 중단과 롤백 | 배포 파이프라인 | 사람이 개입하기 전에 자동 복구 |
| 4 (선택) | Cloud 저장소 CI에서 값 파일 검증: 메모리 제한이 요청보다 작지 않은지, JVM 힙 설정과 메모리 제한이 맞는지 | 배포 파이프라인 | 잘못된 변경이 병합 전에 막힘 |

- 단계 3은 레플리카 2개라 트래픽 분배기 없이 나눌 수 있는 최소 단위가 50%다. 분석 지표가 서비스 전체 기준이라 작은 회귀는 놓칠 수 있다.
- 단계 4 이후에는 같은 PR이 CI에서 막히므로, 우회해서 병합한 경우의 결과를 단계 3과 같게 본다.
- 연쇄 4번이 확인되면 Judge 콜백 재시도 설정(`CALLBACKS_MAX_TRIES`, `CALLBACKS_TIMEOUT`)을 조정하고, 앱 쪽에는 콜백 실패 시 조회로 보완하는 개선을 제안한다.

### 9.2 S2 스팟 노드 회수

**주입**: AWS FIS `aws:ec2:send-spot-instance-interruptions`로 application 노드 1대에 회수 2분 전 알림을 보낸다. 대상은 core 파드가 있는 노드로 고른다.

**가설**: 노드 1대가 사라져도 핵심 기능 가용성 목표를 지키고, 5분 안에 원래 용량으로 돌아온다.

**연쇄 관찰표**

| 순서 | 예상 연쇄 | 확인 방법 |
|---|---|---|
| 1 | 노드의 core, auth, battle, AI 파드가 동시에 사라진다 | 파드 이벤트 |
| 2 | 레플리카가 1개라 해당 기능 묶음이 함께 전면 불가 | 증상 알림 |
| 3 | 남은 노드 1대로 옮기지만 용량이 모자라 일부 Pending | `PodsPending` |
| 4 | 새 노드는 같은 AZ 같은 유형에서 스팟 용량을 찾아야 하므로 늦거나 실패할 수 있다 | 노드 그룹 이벤트, 새 노드 Ready 시각 |
| 5 | 파드가 한꺼번에 기동하며 DB 커넥션과 CPU가 몰린다 | Hikari, RDS 연결 수 |
| 6 | 노드 종료 전에 파드가 정상 종료되지 않으면 처리 중 요청이 실패한다 | k6 실패 시점 |

EKS 관리형 노드 그룹이 회수 알림을 받으면 노드를 비우는지는 1일차에 확인한다. 비우지 않으면 회수 순간 파드가 강제로 죽는다.

**개선 단계**

| 단계 | 개선 | 계층 | 기대 효과 |
|---|---|---|---|
| 1 | core, auth, battle HPA 최소 2, PDB, 노드 분산(`topologySpreadConstraints`) | 쿠버네티스 | 노드 하나가 죽어도 각 서비스 하나는 남음 |
| 2 | application 노드 최대 3대, 핵심 기능 서비스에 우선순위 클래스 | 인프라, 쿠버네티스 | Pending이 나도 핵심 기능이 먼저 자리를 잡음 |
| 3 | 노드 그룹을 서브넷 두 곳(AZ 두 곳)으로 확장, 인스턴스 유형 추가 | 인프라 (Terraform) | 같은 AZ, 같은 유형이 한꺼번에 회수되거나 용량이 없는 위험 감소 |
| 4 (선택) | 스팟 회수 알림을 EventBridge에서 받아 Discord로 전달, 종료 전 정리 시간 조정 | 관측, 애플리케이션 설정 | 회수 2분 전에 미리 알고, 처리 중 요청 실패 감소 |

- 단계 3에서 AZ를 나누면 RDS와 다른 AZ 사이의 통신이 생긴다. 지연 변화를 함께 잰다.
- vCPU 최대치는 system 2 + stateful 2 + judge 4 + application 12 = 20이다.
- stateful 노드(클러스터 안 DB 세 개)도 1대이고 스팟이다. 같은 방식으로 반복할 수 있으나 범위에서 제외하고 위험으로 기록한다.

### 9.3 S3 RDS 장애

두 단계로 나눈다. S3a는 DB가 잠시 사라질 때 서비스가 어떻게 무너지는지를 보고, S3b는 DB를 잃었을 때 얼마나 복구할 수 있는지를 본다.

**S3a 연결 차단**

- 주입: Chaos Mesh NetworkChaos로 core, auth, battle → RDS 연결을 5분 동안 끊는다.
- 가설: DB가 필요 없는 요청은 계속 성공하고, 차단이 풀리면 1분 안에 자동 복구된다.

| 순서 | 예상 연쇄 | 확인 방법 |
|---|---|---|
| 1 | Hikari 풀 10개가 연결을 기다리다 고갈되고 요청 스레드가 묶인다 | `DbConnectionPoolExhausted` |
| 2 | 준비 상태 검사가 DB 상태를 포함해 실패하고, 모든 core 파드가 서비스에서 빠진다 | 엔드포인트 수 |
| 3 | DB가 필요 없는 요청까지 503 | 기능 묶음별 실패율 |
| 4 | core를 호출하는 AI 서비스도 실패 | AI 에러율 |
| 5 | 차단이 풀려도 풀이 바로 회복되지 않는다 | 복구 시간 |
| 6 | 회복 순간 재시도와 재연결이 몰린다 | 요청량, RDS 연결 수 |

**S3b 삭제와 복원**

- 준비: 실행 전에 수동 스냅샷을 만든다. 이 스냅샷은 안전망이며, 개선 전 측정에는 쓰지 않는다.
- 주입: RDS 인스턴스를 삭제한다.
- 가설: 복구 목표 시간 안에 복원되고 데이터 손실은 허용 범위 안이다.
- 개선 전에는 백업이 없으므로 Terraform으로 새로 만들고 시드를 넣는 것이 유일한 복구 경로다. 데이터 손실은 "시드 이후 전부"로 기록한다.
- 복원 후 대응에 포함하는 작업:
  - 새 엔드포인트로 Secrets Manager `DB_URL` 갱신
  - 파드 재시작
  - Terraform 상태 정리
- 복구 목표 시간과 허용 손실 범위는 미리 정하지 않는다. 개선 전 값을 먼저 재고 그 값으로 목표를 정한다. AWS Well-Architected REL13-BP01 "복구 목표를 정의하라"의 순서를 따르되 근거 없는 숫자를 먼저 두지 않기 위해서다.

**개선 단계**

| 단계 | 개선 | 계층 | 다시 할 실험 |
|---|---|---|---|
| 1 | 준비 상태 검사에서 DB 분리: `/actuator/health/readiness`로 바꾸고 `MANAGEMENT_ENDPOINT_HEALTH_GROUP_READINESS_INCLUDE`에서 DB를 뺀다 | 쿠버네티스, 애플리케이션 설정 | S3a |
| 2 | Hikari `connection-timeout`을 줄여 요청 스레드가 오래 묶이지 않게 한다. DB 원인 알림과 RDS CloudWatch 지표 대시보드 | 애플리케이션 설정, 관측 | S3a |
| 3 | `backup_retention_period = 1`, `deletion_protection = true`, `skip_final_snapshot = false` | 인프라 (Terraform) | S3b. 삭제 보호가 실수 삭제를 막는지 먼저 확인하고, 보호를 풀고 삭제한 뒤 특정 시점 복원으로 복구 |
| 4 (선택) | Multi-AZ의 비용과 장애 조치 시간 비교. 켠다면 장애 조치 재부팅으로 측정 | 인프라 (Terraform) | 장애 조치 재부팅 |

- 단계 3에서 삭제할 때 자동 백업을 남기도록(`--no-delete-automated-backups`) 해야 특정 시점 복원이 가능하다. 이 절차를 런북에 적는다.
- 단계 4는 비용이 늘어난다. 측정 후 켜지 않기로 결정하면 그 이유와 수치를 기록한다.

## 11. 일정

7일 안에 끝낸다. 클러스터는 작업하는 날마다 `up.sh`로 띄우고, 개선 내용은 Git에 남겨 다음 날 그대로 재현한다.

| 날 | 내용 | 끝났다고 보는 기준 |
|---|---|---|
| 1 | 공통 구성 요소(k6, 가짜 Gemini 서버, 실행기), SLO 규칙과 알림, EnvoyProxy `replicas: 2`, 사전 확인(아래) | `up.sh` 한 번으로 모두 뜨고 알림이 Discord에 옴 |
| 2 | 대응 체계 문서, FIS 템플릿, Chaos Mesh, 기준선 3회, 시험용 파드 종료 | 기준선 3회 모두 핵심 기능 요청 1,000건 이상. 알림 → 장애 스레드 → 포스트모템 양식까지 이어짐 |
| 3 | S1 개선 전 실험, 대응, 포스트모템, 개선 단계 1~3 재측정 | S1 단계별 비교표 |
| 4 | S2 개선 전 실험, 대응, 포스트모템, 개선 단계 1~3 재측정 | S2 단계별 비교표 |
| 5 | S3a 개선 전 실험, 대응, 포스트모템, 개선 단계 1~2 재측정 | S3a 단계별 비교표 |
| 6 | S3b 개선 전 삭제와 재생성, 개선 단계 3 적용 후 특정 시점 복원 | 복구 시간과 데이터 손실 범위 전후 수치 |
| 7 | 런북 4종, 최종 보고서, 수치 대조. 시간이 남으면 선택 단계 | 보고서 수치가 실험 기록, S3 결과와 일치 |

각 시나리오의 개선 단계 4(S1 CI 값 검증, S2 스팟 회수 알림과 종료 정리 시간, S3 Multi-AZ 비교)는 선택 단계다. 7일차에 시간이 남으면 하고, 못 하면 보고서에 "다음 개선 후보"로 적는다.

1일차 사전 확인:

- core가 Judge 콜백을 쓰는지, AI 호출이 비동기인지 (BE 코드)
- `/actuator/health`에 DB 상태가 포함되는지
- S1에 쓸 메모리 제한 값
- EKS 관리형 노드 그룹이 스팟 회수 알림에 노드를 비우는지

하루 일정이 밀리면 다음 시나리오의 개선 단계를 하나씩 줄여 7일 안에 맞춘다. S3은 위험이 가장 커서 대응에 익숙해진 뒤인 5~6일차에 한다. S3b는 RDS를 지우므로 하루를 따로 잡는다.

## 13. 위험

| 위험 | 대응 |
|---|---|
| S3b 복원 실패 | 실행 전 수동 스냅샷을 만들고, 복원 확인 전에는 지우지 않는다. 60분을 넘으면 스냅샷으로 되돌린다 |
| S3b 후 Terraform 상태와 실제 리소스가 어긋남 | 복원 절차에 `terraform import`나 상태 정리를 넣고, 마지막에 `terraform plan` 변경 없음을 확인한다 |
| S2에서 스팟 용량 부족으로 새 노드가 안 뜸 | 결과로 기록한다. 한도 증가는 요청하지 않는다 |
| S1 메모리 값이 매번 다르게 동작함 | 기준선과 같은 k6 프로필을 쓰고, 3회 중 OOMKilled가 재현되는 값만 쓴다 |
| 대응자가 장애를 설계한 사람이라 원인을 미리 안다 | 탐지 시간은 알림 시각으로만 잰다. 연쇄 관찰표 항목은 실험 전에 결과를 예측해 적고, 실제와 다른 점을 보고서에 적는다 |
| 일정 지연 | 선택 단계(각 시나리오 단계 4)를 먼저 빼고, 그래도 밀리면 11장 기준대로 개선 단계를 줄인다 |
