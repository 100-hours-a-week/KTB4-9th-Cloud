작성 2026-11-24. 1차 설계서 `2026-11-10-v3-john-fault-injection-design.md`와 1차 결과(`v3-john/chaos/REPORT.md`, `EVALUATION.md`)를 이어받는다.

## 1. 의도와 이유

1차 실험의 S1(메모리 축소 배포)과 S2(노드 한 대 회수)는 개선 전 구성을 일부러 약하게(레플리카 1, PDB 없음) 두고 교과서적인 개선(레플리카 2, PDB)으로 막은 실험이었다. 결과는 맞지만 "기본을 안 해 놓고 기본을 했다"로 읽힌다. `EVALUATION.md`는 S1 단계 3·4의 무중단이 이중화·카나리 효과를 증명하지 못한다는 점도 확인했다.

2차의 목적은 **실제 운영에서 흔히 일어나고, 합리적인 운영 구성(이중화가 이미 된 상태)으로도 막히지 않는 장애**를 일으키고, **설계 판단과 트레이드오프가 들어간 개선**을 한 단계씩 넣어 숫자로 보이는 것이다. 결과는 사용자의 이력서·포트폴리오에 "어떤 위험을, 어떤 판단으로, 얼마의 비용으로, 얼마나 줄였나"로 쓰인다.

성공의 모습:

- 개선 전에 실제로 아픈 장애가 난다(핵심 기능 SLO 위반, 여러 서비스로 번짐)
- 각 개선이 그 장애의 특정 고리를 끊고, 그 효과가 3회 반복 측정에서 흩어짐보다 크게 보인다
- 적어도 한 개선은 비용과 가용성의 교환 비율을 숫자로 보인다

### 4.1 사전 작업: 실제 요청 기반 SLI 알림

1차 S3a에서 Envoy 클러스터 지표가 엔드포인트 0개·시간 초과를 놓쳤다. 2차 실험 전에 다음을 넣는다.

- 기능 묶음별 downstream 기준 오류율 기록 규칙: 경로(HTTPRoute)별 5xx와 시간 초과를 요청 수로 나눈다. 1차의 묶음 정의(핵심·주요·AI)를 따른다
- 이 규칙으로 `CoreErrorBudgetBurnFast` 같은 빠른 소진 알림을 다시 정의하거나 짝 알림을 만든다. promtool 단위 테스트를 붙인다
- 탐지 시간(MTTD)은 이 알림 기준으로 잰다

### 4.2 지표

| 지표 | 정의 |
|---|---|
| 탐지 시간 | 주입 시작 → 실제 요청 SLI 알림 firing |
| 완화 시간 | 주입 시작 → 완화 시작(사람의 `mitigate` 또는 자동 조치 시작) |
| 복구 시간 | 주입 시작 → 핵심 오류율(1분 창)이 0.5% 안으로 1분 유지 |
| 영향 범위 | 판정 구간에 오류율이 목표를 넘은 서비스 수와 묶음 |
| 핵심 SLO 유지율 | 판정 구간 동안 핵심 묶음 1분 오류율이 0.5% 안이었던 시간 비율 |
| 예산 소진 | 1차와 같은 계산(4주 예산 대비) |
| 비용(S2') | 개선 구성의 시간당 노드 비용 차이(온디맨드·스팟 가격, 노드 수) |

## 5. 기준 구성(개선 전)

현재 main(2026-11-24, PR #88까지)을 그대로 개선 전으로 쓴다. 주요 값:

- auth, core, battle: HPA 최소 2(core·battle 최대 3, auth 최대 2), PDB minAvailable 1, 노드 분산 `ScheduleAnyway`, JVM 힙 75%, CPU 요청 500m(HPA 기준 140%), Hikari 최대 풀 10·연결 대기 3초, 헬스 검사 DB 제외
- core: Argo Rollouts 카나리(50% → 5분 분석 → 100%), 분석 조건 오류율·재시작
- application 노드 그룹: 스팟, AZ a·c, 유형 5개, 최대 3대. 우선순위 클래스 `cosmos-core-journey`(auth, core)
- 모니터링(Prometheus, Alertmanager, Tempo): application 노드, 레플리카 1
- RDS: db.t4g.medium 단일 AZ, 자동 백업 1일, 삭제 보호

## 6. 시나리오

### 6.1 S1' 연결 풀 확대 배포로 공유 RDS 연결 고갈

**운영에서의 모습**: 피크 시간 지연을 줄이려고 "DB 연결 풀을 늘리자"는 core 설정 PR이 들어온다. 리뷰에서는 문제가 없어 보이고 core 배포도 정상이다. 얼마 뒤 다른 팀이 auth를 평소처럼 배포하는데, 새 auth 파드가 DB 연결을 얻지 못해 로그인이 실패한다. 터진 것은 auth 배포인데 원인은 앞서 들어간 core PR이다.

**주입**

- core 값 파일의 `SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE`를 10에서 N으로 올리는 PR을 main에 병합한다(1차 S1의 PR 병합 방식 재사용). Hikari 기본값으로 최소 유휴 연결 수가 최대 풀과 같아 파드가 뜨자마자 N개를 연다
- **촉발(사용자 결정 2026-11-24)**: core PR 배포가 끝나고 정해진 시간(예: 3분) 뒤 auth를 평소 배포 방식으로 재시작한다(롤링 재시작, 값 변경 없음). 새 auth 파드는 기존 파드가 연결을 쥔 채로 연결 10개를 새로 요청하므로 상한을 넘는다. 같은 방식으로 battle 재시작 회차를 둘지는 빌더 재량이다
- 부하는 열린 모델로 기준 초당 요청 수를 일정하게 유지한다(계단 부하는 쓰지 않는다. 확장으로는 장애가 나지 않을 수 있다는 검토 결과에 따름)
- **N 보정(사전 작업)**: RDS `max_connections`를 실측한다(파라미터 그룹 기본값은 인스턴스 메모리로 정해진다). core 배포(카나리 포함)는 상한 아래에서 끝나고, 이어지는 auth 롤링 재시작에서 새 auth 파드의 연결이 상한을 넘는 N을 고른다. 1차 실측 평상시 연결 수는 약 60이었다
- 보정 점검: 개선 전 구성에서 3회 중 3회, auth 재시작 뒤 로그인(핵심 묶음 auth 경로) 오류율이 목표를 넘어야 주입값으로 확정한다. 어떤 N으로도 재현되지 않으면 결과를 기록하고 사용자에게 알린 뒤 후보 B·C로 넘어간다

**가설(개선 전)**: core 카나리 분석은 core 자체 지표만 보므로 배포를 통과시킨다. 이후 auth 재시작에서 새 연결이 거부되어 로그인이 실패한다. auth는 롤링(`maxUnavailable: 0`)이라 옛 파드가 남아 일부는 버티지만, 새 파드가 준비되지 못하면 롤아웃이 멈추고 옛 파드가 순차 교체되는 동안 실패가 섞인다. 원인(core PR)과 증상(auth 배포 실패)이 다른 서비스라 원인 파악이 늦다. 대응자가 auth 배포를 먼저 되돌리는 오판을 할 수 있다

**연쇄 관찰표**

| 순서 | 예상 연쇄 | 확인 |
|---|---|---|
| 1 | PR 배포, core 카나리 통과(core는 정상) | Rollout 상태, AnalysisRun |
| 2 | core 연결이 2 × N으로 늘어 RDS 여유가 줄어듦 | CloudWatch `DatabaseConnections` |
| 3 | auth 정기 배포(재시작), 새 파드가 연결 10개 요청 → "Too many connections" | 앱 로그, RDS 연결 수 |
| 4 | 새 auth 파드 준비 실패 또는 요청 실패, 로그인 오류 | 묶음별 SLI, Deployment 상태 |
| 5 | 대응자가 auth 배포를 원인으로 오판할 수 있음 | 대응 기록 |
| 6 | core 풀을 되돌려야 auth가 회복된다. core 파드 재시작 동안 연결이 줄며 회복 | 복구 시간 |

**개선 단계**(단계마다 하나, 3회씩)

| 단계 | 개선 | 끊는 고리 | 측정 |
|---|---|---|---|
| 1 | RDS 연결 수 알림(상한의 80%, CloudWatch 또는 메트릭 수집)과 런북 `db-connection-exhaustion.md` | 탐지와 원인 파악 | 탐지 시간, 원인 파악 시간(대응 기록) |
| 2 | 연결 예산 CI 검사: 모든 Spring 값 파일의 (HPA 최대 + 배포 중 추가 파드) × 최대 풀 합계가 RDS 상한의 80% 이하. 배포 중 추가 파드는 Deployment면 `maxSurge`(현재 1), Argo Rollouts 카나리면 HPA 최대의 25% 올림(Rollouts 기본 maxSurge)으로 센다(설계자 결정) | 사전 차단 | 같은 PR이 CI에서 실패하는지. main 필수 검사 지정은 저장소 관리자 설정이라 사용자에게 요청하고, 안 되면 "검출"까지로 기록 |
| 3 | 영향 범위 카나리: core 카나리 분석에 RDS 연결 수(상한 대비 여유)와 auth·battle 오류율 조건 추가. 연결 여유 조건은 "다른 서비스가 한 번 재배포할 여유(그 서비스 레플리카 × 풀)"가 남는지로 정한다 | 배포 경로에서 자동 중단 | 자동 중단 여부와 시각, auth 재시작 뒤 결과 |
| 4 | 연결 사용 구조: Hikari 최소 유휴 연결을 작게(예: 2) 두는 표준을 차트 기본값으로, 또는 RDS Proxy 도입 중 하나 | 연결 수 자체 감소 | 같은 N에서도 상한을 넘지 않는지, 지연 변화, RDS Proxy면 시간당 비용 |

- 단계 2가 CI에서 PR을 막으면 단계 3·4 실험은 CI를 우회해 같은 PR을 병합한다(1차 S1 단계 5와 같은 규칙). 이 우회는 기록에 남긴다
- 단계 4의 두 안 중 무엇을 할지는 빌더 재량이다. 비용과 앱 영향(최소 유휴 연결은 앱 설정 값이라 값 파일로 가능, RDS Proxy는 Terraform과 엔드포인트 변경)을 비교해 고르고 이유를 적는다

### 6.2 S2' 스팟 일괄 회수와 대체 용량 부족

**운영에서의 모습**: 스팟은 같은 유형·같은 AZ 용량 풀이 한꺼번에 회수되는 일이 잦다. 여러 노드가 동시에 사라지고, 같은 시각 그 풀의 대체 용량도 없다. 남은 노드에 모든 서비스가 들어가지 못한다.

**주입**

- FIS로 application 노드 중 **한 대만 남기고 나머지 전부**(노드가 3대면 2대, 2대면 1대)에 동시에 회수 2분 전 알림을 보낸다. 실험 직전 노드 수와 노드별 파드를 기록한다. 기준 구성의 노드 수(평상시 2~3대, Cluster Autoscaler가 정함)를 바꾸지 않는다. 1대가 남으므로 FIS 중단 알람(InService 0대 1분)은 울리지 않는다. 1차의 `scenarios/s2`를 확장해 대상 인스턴스를 여러 개 받는다(설계자 결정)
- 같은 시각 application 노드 그룹 ASG의 `Launch` 프로세스를 일시 중지해(`suspend-processes`) "대체 스팟 용량 없음"을 만든다. 유지 시간은 주입 유지 시간과 같고, `stop.sh`가 반드시 재개한다(끊겨도 재개되도록 실행기 종료 처리에 포함)
- 관리형 노드 그룹의 ASG를 직접 건드리는 것은 AWS가 권하지 않는 조작이다. 실험 전에 짧은 시험(중지 2분 → 재개)으로 노드 그룹 상태(`describe-nodegroup`의 health issues)가 깨끗하게 돌아오는지 확인하고, 문제가 남으면 대체 방법(스팟 노드 그룹 최대 크기를 현재 노드 수로 잠시 낮춤)으로 바꾼다. 대체 방법은 실제 용량 부족과 Cluster Autoscaler 동작이 다르므로(실패 대기 없이 바로 다음 그룹) 기록에 그 차이를 적는다(설계자 결정)
- 대상 선택: 회수 대상 2대에 core·auth 레플리카가 각각 최소 1개씩 있도록 실험 전 배치를 맞춘다. 모니터링은 개선 전에는 현재처럼 application 노드에 있다
- vCPU 중단 기준: 노드가 줄어드는 실험이라 초과 위험은 낮다. 개선 단계에서 온디맨드 노드가 더해져도 Spot vCPU에 들어가지 않는다(별도 한도)

**가설(개선 전)**: 남은 노드 1대에 모든 파드가 들어가지 못해 대량 Pending이 생긴다. 우선순위가 없으면 어떤 서비스가 자리를 잡을지 무작위이고 핵심 기능이 내려갈 수 있다. 모니터링도 함께 사라질 수 있다. 대체 노드는 ASG가 재개될 때까지 뜨지 않는다.

**개선 단계**

| 단계 | 개선 | 끊는 고리 | 측정 |
|---|---|---|---|
| 1 | 기능 저하 우선순위: 핵심(auth, core, judge-api, Envoy) > 주요(battle) > 부가(ai-llm, mlflow, 배치) 클래스와 선점. 자리가 모자라면 부가 기능이 먼저 내려간다 | 무작위 자리 잡기 | 핵심 SLO 유지율, 묶음별 오류율(부가 기능은 의도적으로 내려감) |
| 2 | 온디맨드 대체: 온디맨드 application 노드 그룹(평소 0대)을 추가하고 Cluster Autoscaler 우선순위 확장기로 스팟 먼저, 스팟 실패 시 온디맨드. 스팟 그룹이 노드를 띄우지 못했다고 판단하는 시간(`max-node-provision-time`, 기본 15분)을 3분으로 줄이는 설정을 이 단계에 포함한다(기본값이면 10분 주입 안에 대체가 일어나지 않는다) | 대체 용량 없음 | 용량 복구 시간(Pending 해소까지), 대체에 쓰인 온디맨드 노드 시간 |
| 3 | 핵심 기반 용량: 온디맨드 노드 1대를 상시 두고 핵심 서비스 레플리카 하나와 모니터링을 그 노드에 배치(노드 친화성) | 핵심·모니터링 동시 소실 | 핵심 SLO 유지율, 모니터링 공백 시간, 시간당 비용 증가 |
| 4 | 회수 알림 자동화: EventBridge(스팟 회수 경고, 재조정 권고) → 영향 노드와 그 위 파드 목록 → Discord | 사람의 탐지 | 탐지 시간(회수 경고 → 알림 도착). 실제 게시 전에 사용자 확인 |

- 단계 2의 Cluster Autoscaler 확장기 설정과 온디맨드 노드 그룹 유형은 빌더 재량이다. 스팟 vCPU 한도와 상관없게 온디맨드로만 대체한다
- 단계 3의 비용은 "개선 전 대비 시간당·월 비용 증가율"과 "그 대가로 얻은 핵심 SLO 유지율 변화"를 한 줄로 쓸 수 있게 기록한다

| S1' 주입으로 RDS 연결이 꽉 차 실험 도구(prepare.sh, 시드)도 접속 못 함 | 원복은 PR 되돌림과 Spring 재시작. 시드 작업은 실험 전에 끝낸다 |
