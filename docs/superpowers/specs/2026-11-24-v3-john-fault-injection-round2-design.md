# v3-john 장애 주입 2차 설계: 채점 장애의 연결 풀 연쇄(S1')와 스팟 회수 손실 제거(S2')

작성 2026-11-24. 1차 설계서 `2026-11-10-v3-john-fault-injection-design.md`와 1차 결과(`v3-john/chaos/REPORT.md`, `EVALUATION.md`)를 이어받는다.

## 1. 의도와 이유

1차 실험의 S1(메모리 축소 배포)과 S2(노드 한 대 회수)는 개선 전 구성을 일부러 약하게(레플리카 1, PDB 없음) 두고 교과서적인 개선(레플리카 2, PDB)으로 막은 실험이었다. 결과는 맞지만 "기본을 안 해 놓고 기본을 했다"로 읽힌다. `EVALUATION.md`는 S1 단계 3·4의 무중단이 이중화·카나리 효과를 증명하지 못한다는 점도 확인했다.

2차의 목적은 **실제 운영에서 흔히 일어나고, 합리적인 운영 구성(이중화가 이미 된 상태)으로도 막히지 않는 장애**를 일으키고, **설계 판단과 트레이드오프가 들어간 개선**을 한 단계씩 넣어 숫자로 보이는 것이다. 결과는 사용자의 이력서·포트폴리오에 "어떤 위험을, 어떤 판단으로, 얼마의 비용으로, 얼마나 줄였나"로 쓰인다.

성공의 모습:

- 개선 전에 실제로 아픈 장애가 난다(핵심 기능 SLO 위반, 여러 서비스로 번짐)
- 각 개선이 그 장애의 특정 고리를 끊고, 그 효과가 3회 반복 측정에서 흩어짐보다 크게 보인다
- 적어도 한 개선은 비용과 가용성의 교환 비율을 숫자로 보인다
- 모든 개선은 측정 근거와 대안 비교를 갖춘 결정 기록이 있다(6.3)

### 4.1 사전 작업: 실제 요청 기반 SLI 알림

1차 S3a에서 Envoy 클러스터 지표가 엔드포인트 0개·시간 초과를 놓쳤다. 2차 실험 전에 다음을 넣는다.

- 기능 묶음별 downstream 기준 오류율 기록 규칙: 경로(HTTPRoute)별 5xx와 시간 초과를 요청 수로 나눈다. 1차의 묶음 정의(핵심·주요·AI)를 따른다
- 이 규칙으로 `CoreErrorBudgetBurnFast` 같은 빠른 소진 알림을 다시 정의하거나 짝 알림을 만든다. promtool 단위 테스트를 붙인다
- 탐지 시간(MTTD)은 이 알림 기준으로 잰다

### 4.2 지표

| 지표 | 정의 |
|---|---|
| 탐지 시간 | 주입 시작 → 실제 요청 SLI 알림 firing |
| 완화 시간 | 주입 시작 → 완화 시작(사람의 `mitigate` 또는 자동 조치 시작) |
| 복구 시간 | 주입 시작 → 핵심 오류율(1분 창)이 0.5% 안으로 1분 유지 |
| 영향 범위 | 판정 구간에 오류율이 목표를 넘은 서비스 수와 묶음 |
| 핵심 SLO 유지율 | 판정 구간 동안 핵심 묶음 1분 오류율이 0.5% 안이었던 시간 비율 |
| 예산 소진 | 1차와 같은 계산(4주 예산 대비) |
| 비용(S2') | 개선 구성의 시간당 노드 비용 차이(온디맨드·스팟 가격, 노드 수) |

## 5. 기준 구성(개선 전)

현재 main(2026-11-24, PR #88까지)을 그대로 개선 전으로 쓴다. 주요 값:

- auth, core, battle: HPA 최소 2(core·battle 최대 3, auth 최대 2), PDB minAvailable 1, 노드 분산 `ScheduleAnyway`, JVM 힙 75%, CPU 요청 500m(HPA 기준 140%), Hikari 최대 풀 10·연결 대기 3초, 헬스 검사 DB 제외
- core: Argo Rollouts 카나리(50% → 5분 분석 → 100%), 분석 조건 오류율·재시작
- application 노드 그룹: 스팟, AZ a·c, 유형 5개, 최대 3대. 우선순위 클래스 `cosmos-core-journey`(auth, core)
- 모니터링(Prometheus, Alertmanager, Tempo): application 노드, 레플리카 1
- RDS: db.t4g.medium 단일 AZ, 자동 백업 1일, 삭제 보호

S2'는 현재 main을 그대로 개선 전으로 쓴다(우선순위 클래스 포함). 개선이 우선순위와 관계없기 때문이다.

## 6. 시나리오

### 6.1 S1' 채점 경로 장애가 core 연결 풀을 통해 핵심 경로 전체로 번짐

(2026-11-24 사용자 결정으로 다시 썼다. 처음 설계 "core 풀 확대 PR이 공유 RDS를 고갈시켜 auth 배포가 실패"는 실측으로 성립하지 않았다. 아래 "처음 설계와 버린 이유" 참고.)

**운영에서의 모습**: 채점 워커가 있는 스팟 노드가 회수되어 워커가 몇 분 사라진다. 제출 요청은 채점 결과를 기다리는 동안 core의 DB 연결을 쥐고 있어서, core 연결 풀(파드당 10)이 제출 요청으로 가득 찬다. 같은 풀을 쓰는 문제 조회와 major-core 경로가 연결을 얻지 못해(획득 제한 3초) 5xx를 낸다. 채점과 상관없는 핵심 경로가 채점 노드 한 대 때문에 멈춘다.

**실제로 관찰한 근거**

| 언제 | 무엇 | 기록 |
|---|---|---|
| 2026-11-24 03:30 KST(기준선 1회차 중) | judge-base-ng 실제 회수(`instance-terminated-no-capacity`) → core 두 파드 연결 10/10, 대기 74~103, 문제 조회 5xx 최대 23/s, major-core 46/s, 문제 조회 p95 4.5초, 채점 유실 359 | `records/round2-baseline.md` 4절 |
| 사전 측정, 풀 10 | 채점 워커 중단 → core 대기 58~88, 문제 조회·major-core 5xx, k6 실패율 4.5%, 채점 유실 971 | `records/s1p-pilot.md` |
| 사전 측정, 풀 131 | 같은 중단 → core 파드당 연결 최대 41, DB 연결 최대 160(상한 303), 문제 조회·major-core 5xx 0, 제출만 빠르게 실패, k6 실패율 0.6% | `records/s1p-pilot.md` |

**주입**: 부하 중(열린 모델, `RATE_BASE` 30) 채점 워커를 5분 멈춘다. KEDA `ScaledObject`에 `autoscaling.keda.sh/paused-replicas: "0"`을 붙여 워커를 0으로 내리고, 원복에서 주석을 지운다. 실제 회수(노드 교체 + 이미지 받기, 약 5분)를 시간이 일정한 방식으로 재현한 것이다. 노드 cordon 방식은 클러스터 오토스케일러가 새 채점 노드를 띄워 중단 시간이 회차마다 달라져 쓰지 않는다(사전 측정에서 확인).

**가설(개선 전)**: 제출 요청이 core 연결을 점유해 풀이 바닥나고, 문제 조회·major-core 경로까지 5xx가 난다. 핵심 SLO 유지율이 떨어지고 영향 범위가 여러 경로로 번진다. 워커가 돌아온 직후 밀린 채점이 한꺼번에 풀리며 한 번 더 흔들릴 수 있다(사전 측정 10:13 재발).

**연쇄 관찰표**

| 순서 | 예상 연쇄 | 확인 |
|---|---|---|
| 1 | 채점 워커 0, 채점 큐에 작업이 쌓임 | 워커 파드 수, judge-redis 큐 길이 |
| 2 | 제출 요청이 채점 대기로 길어지며 DB 연결을 쥠 | 제출 p95, Hikari 활성 연결 |
| 3 | core 풀 10/10, 대기 증가 | `hikaricp_connections_pending` |
| 4 | 문제 조회·major-core 5xx(연결 획득 제한 3초) | 경로별 오류율, 영향 범위 |
| 5 | 워커 복귀 뒤 회복, 밀린 작업으로 재발 가능 | 경로별 오류율 |

**개선 단계**(단계마다 하나, 3회씩. 각 단계는 6.3의 결정 기록을 먼저 쓴다)

| 단계 | 개선 | 끊는 고리 | 측정 |
|---|---|---|---|
| 1 | 탐지와 원인 파악: 연결 풀 대기 알림(이미 만든 `DbConnectionAcquireFailed`와 연결 알림 경로) + 런북 `db-connection-exhaustion.md`를 이 연쇄에 맞게 고침 | 탐지, 원인 파악 | 탐지 시간, 원인 파악 시간(대응 기록) |
| 2 | 게이트웨이 격벽: Envoy Gateway `BackendTrafficPolicy` 회로 차단기로 제출 경로(`journey-core-submit`)의 동시 요청 수를 제한한다. 넘치는 제출은 Envoy가 바로 503으로 돌려보내 core 연결을 점유하지 못한다 | 제출이 풀을 다 잡는 고리 | 문제 조회·major-core 5xx, 영향 범위, 제출 거절 수, 평상시 제출 영향 |
| 3 | 풀 크기 재산정과 연결 예산: 사전 측정(파드당 최대 41)을 근거로 core 풀을 키우고, CI 연결 예산 검사(모든 Spring 서비스의 (HPA 최대 + 배포 중 추가 파드) x 풀 합계 ≤ RDS 상한 303의 80%)로 키운 값이 공유 RDS를 넘지 않게 묶는다 | 풀이 작은 고리, 키울 때의 RDS 고갈 위험 | 같은 지표, DB 연결 최대치, CI 검사 결과 |
| 4(선택) | 촉발 제거: 채점 워커 이중화와 노드 분산 | 워커 한 대 중단 = 채점 정지 | 채점 유실, 제출 실패. S2'와 겹치면 S2'에서 다룬다 |

- 단계는 누적한다(단계 2 실험은 단계 1을 포함)
- 단계 2의 제한 값은 평상시 제출 동시성(기준선 제출률 x 지연)과 core 풀 크기 사이에서 정한다. 근거와 대안(앱 안 별도 풀·세마포어, 제출 시간 제한 단축, 비동기 채점 조회)은 결정 기록에 적는다
- 단계 3 뒤 단계 2를 유지할지는 결과를 보고 결정 기록에 적는다(풀이 충분하면 격벽은 보험)

**처음 설계와 버린 이유**: 처음 설계는 "core 풀을 10에서 N으로 키우는 PR → Hikari 기본값(최소 유휴 = 최대)으로 파드가 뜨자마자 N개를 열어 RDS 여유가 줄고 → 이어지는 auth 롤링 재시작에서 새 auth 파드가 연결을 못 얻음"이었다. 실측은 달랐다.

- 이 앱은 최소 유휴 연결이 10으로 설정되어 있다(`hikaricp_connections_min` 10). 풀을 131로 키워도 평상시에는 수요만큼(23~30)만 연다. 보정 1회차(N=131)에서 auth 재시작은 31초 만에 정상 끝났다
- 지연 사건을 촉발로 바꿔 풀 131에서 채점 워커를 멈춰도 DB 연결은 160에 그쳤고, 오히려 core 전체 장애가 사라졌다. "풀 확대가 위험"이 아니라 "풀이 작아 채점 대기 하나로 핵심 경로가 멈춤"이 실제 위험이다
- auth·battle도 최소 유휴 10이라 이미 쥔 연결을 유지하므로, RDS가 차도 새 연결이 필요할 때만 실패한다. 공유 RDS 고갈이 다른 서비스로 번지려면 지금보다 훨씬 큰 부하가 필요하다

이미 만든 것 중 연결 알림·런북(단계 1), CI 연결 예산 검사(단계 3)는 재사용한다. 영향 범위 카나리(`connectionGuard`)와 최소 유휴 축소(CI 규칙 5)는 이 연쇄를 끊지 않아 2차 실험에서 뺀다(브랜치는 기록으로 남긴다).

### 6.2 S2' 스팟 노드 한 대 회수: 이중화 뒤에도 남는 손실 원인 제거

(2026-11-24 사용자 결정으로 다시 썼다. 일괄 회수·용량 부족 가정은 버렸다. 실제로 관찰한 것은 개별 회수였다: 11-23 19:56 재조정 권고 교체, 20:51 회수 알림.)

**운영에서의 모습**: 스팟 노드 하나가 회수 2분 전 알림 뒤 회수된다. 관리형 노드 그룹이 대체 노드를 먼저 띄우고 옛 노드를 비운다. 서비스는 이중화되어 있지만, 비우는 순간과 그 뒤에 1차 실험과 실제 회수에서 측정된 손실이 남는다.

**주입**: 1차와 같다. FIS로 application 노드 한 대에 회수 2분 전 알림. 일괄 회수나 대체 용량 부족은 넣지 않는다.

**배치 재현(공정 조건)**: 회차마다 회수 대상 노드에 1차 S2 단계 3과 실제 회수(20:51) 때 있었던 배치를 만든다. core 하나, judge-api, Envoy 하나, Prometheus·Alertmanager·Tempo. 다른 노드에는 core·auth·battle 나머지 레플리카가 있다. 배치는 다른 노드를 잠시 cordon하고 해당 파드를 재시작해 만든다. 개선 단계가 배치 자체를 바꾸는 경우(모니터링 분리, 재분산)는 그 개선의 효과이므로 재현을 강제하지 않고 실제 배치를 기록한다.

**개선 전에 남는 손실(측정 근거)**

| 손실 | 근거 |
|---|---|
| 비우기 중 처리 중 요청 실패(5xx, 연결 리셋) | 1차 s2-step3 핵심 5xx 33 |
| 채점 유실(judge-api 레플리카 1) | 1차 s2-before 57, s2-step3 38 |
| 모니터링 공백 | 실제 회수 20:51, 약 2분 30초 |
| 회수·교체 뒤 배치 쏠림 | 1차 노드 그룹 교체 뒤 Spring 6개 한 노드, Envoy 2개 한 노드 |

**개선 단계**(단계마다 하나, 3회씩. 각 단계는 6.3의 결정 기록을 먼저 쓴다)

| 단계 | 개선 | 없애려는 손실 | 측정 |
|---|---|---|---|
| 1 | 종료 정리: Spring 정상 종료(`SERVER_SHUTDOWN=graceful`, 종료 단계 제한 시간)와 `preStop` 대기(엔드포인트 제거가 Envoy에 퍼질 시간) | 비우기 중 처리 중 요청 실패 | 회수 구간 5xx·연결 오류 수, k6 실패 수 |
| 2 | 게이트웨이 재시도: Envoy Gateway `BackendTrafficPolicy`로 연결 실패·리셋·503에 한해 재시도. 멱등 요청(GET) 경로만, 제출(POST)은 제외 | 남은 요청 실패 | 같은 지표, 재시도 횟수, 조회 p95 변화 |
| 3 | judge-api 이중화와 PDB, 노드 분산 | 채점 유실 | 채점 유실 수, 제출 p95 |
| 4 | 모니터링 분리: Prometheus·Alertmanager·Tempo를 온디맨드 노드 1대로 | 모니터링 공백 | 공백 시간, 시간당·월 비용 증가 |
| 5 | 재분산: descheduler로 분산 규칙 위반 파드를 주기적으로 옮김 | 배치 쏠림 | 회수·교체 뒤 서비스별 최대 노드 쏠림(같은 노드 레플리카 수), 재분산까지 시간 |

- 우선순위는 1~4가 먼저, 5는 선택이다
- 단계 4의 비용은 "시간당·월 비용 증가율"과 "얻은 것(공백 0초)"을 한 줄로 쓸 수 있게 기록한다

### 6.3 개선 결정 기록(모든 개선 단계 공통)
